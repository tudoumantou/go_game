# R2.1 缓存原子变更契约

> 基线：2026-10-19，R1 完成（`f5a265d`）之后
> 上游：[剩余功能开发计划](superpowers/plans/2026-10-18-remaining-development.md) R2.1
> 参考实现：签到（`internal/game/module/signin/signin.go`）—— 状态、资产、奖励全在一次快照提交里

## 1. 要解决的问题

缓存权威链路已经能保证「一份快照一次 CAS」，但模块写法还停留在「内存 + SQL 双写」：

```go
// quest.onClaim（现状）
ctx.State.AddItem(1001, itemCount)                 // 改内存，等快照提交
m.repo.Upsert(..., statusClaimed, rec.Progress)    // 另开一条 SQL 路径
```

三个真实故障：

| 场景 | 结果 |
|---|---|
| Redis CAS 失败 | SQL 已记「已领取」，奖励没进快照 → 玩家丢奖励且无法重领 |
| SQL 成功、进程崩溃 | 内存奖励随进程消失，SQL 却是 claimed |
| Kafka 重投 / 重复请求 | 只有 `GrantItemsMsg` 有业务键，模块领奖没有 → 重复发奖 |

## 2. 契约

### 2.1 原子单元

**一次 Actor 消息 = 一份 Snapshot = 一次 CAS。**

模块 handler 内只允许改内存：

- 业务状态 → `ctx.State.SetExt("<module>", raw)`
- 资产 → `ctx.State.AddItem / RemoveItem / AddExp`
- 经验 → `Profile.Exp`（已随快照）

**禁止在 handler 里直接写 MySQL 业务事实**。写库是 Write-Behind 的事：Actor 提交 Redis 成功后，由进程内 worker / 独立 flusher 按版本合批落库。

Tier-1 严格资产（充值到账、跨服结算）例外：它们需要持久化事实 + 对账，走 R2.3 单独设计，不受本契约约束。

### 2.2 两类幂等，不要混用

| 类型 | 场景 | 幂等依据 | 存储位置 | 生命周期 |
|---|---|---|---|---|
| A 类 异步投递 | 充值回调、Kafka 重投、离线补偿 | `AppliedGrants["<domain>:<bizID>"]` | 快照 + `player_writebehind.applied_grants` | 与业务单号同级，永久 |
| B 类 主动领取 | 任务、活动、副本首通、邮件附件 | 业务状态里的「已领取」事实（`claimed` 集合） | 模块 `Ext` | 随业务状态清理 |

B 类**不要**往 `AppliedGrants` 里塞键：玩家一年点上千次领取，而 `AppliedGrants` 每次 CAS 都整份传输、整份落库，会持续膨胀。已领取事实本来就属于业务状态，跟着业务状态走。

### 2.3 未知提交

`Commit` 的结果分三种，模块不需要自己判断，但要知道语义：

| 结果 | 处理 | 对业务的影响 |
|---|---|---|
| 明确失败 | 回滚内存到消息前（`RollbackAware`） | 重试是安全的 |
| 未知（超时 / 连接断） | 保留 pending，后续消息先核对版本 | 重试不会重复发奖 |
| 成功但回包丢失 | 下次请求命中幂等（A 类查键、B 类查状态） | 客户端重试拿到 already |

## 3. 新增 API

`PlayerState` 增加两个方法，`module.Context` 增加一个封装：

```go
// PlayerState
ClaimBiz(key string) bool // 占用业务键；已存在返回 false（幂等命中）
HasBiz(key string) bool   // 只读查询

// Context：幂等执行业务，fn 返回错误时自动撤销键标记
func (c *Context) ApplyOnce(key string, fn func() error) (applied bool, err error)
```

`ApplyOnce` 的语义：

1. `key == ""` → 不启用幂等，直接执行 `fn`（用于不需要键的普通请求）
2. 键已存在 → 返回 `(false, nil)`，**不执行** `fn`
3. 键不存在 → 占用键 → 执行 `fn`
4. `fn` 返回错误 → 撤销键标记并返回错误（键不能因为一次配置错误被永久占死）

## 4. 迁移模板（以任务领奖为例）

**Before**（双写）：

```go
ctx.State.AddItem(1001, itemCount)
if err := m.repo.Upsert(ctx, playerID, questID, statusClaimed, progress); err != nil {
    return err
}
```

**After**（状态进快照）：

```go
// Data 进 Ext["quest"]：进度 + 已领取集合
d, err := quest.Load(ctx.State)
if err != nil {
    return err
}
if d.Claimed[questID] {
    return reply(ctx, alreadyClaimed)
}
if d.Progress[questID] < target {
    return reply(ctx, unfinished)
}
d.Claimed[questID] = true
for _, g := range rewards {
    ctx.State.AddItem(g.ItemID, g.Count)
}
ctx.State.MarkDirty("bag")
return quest.Save(ctx.State, d)   // 与资产同一次 CAS
```

`player_quest` 由「自增 id 主键的流水表」改为 `player_id` 主键的单行表，模块侧用 `RegisterFlat` 一行接入（主键恰为 `player_id` 时）。若保留多行结构，则用手写 `Persister`（`DeleteXxxByPlayer` + `ListXxxByPlayer`），但状态仍必须进 `Ext`。

## 5. 边界

- **快照大小**：单模块 `Ext` 建议 < 4KB。超过说明该数据不该进快照（应是可分页查询的业务表），要么拆表走只读缓存，要么接受「不进快照」的读路径。
- **A 类键的唯一性**：`<domain>:<bizID>` 必须由上游保证全局唯一。充值用订单号，邮件用 mail_id，跨服用 battle_id。
- **不做的事**：本契约不提供跨玩家事务（公会、交易），也不提供「部分成功」——一次消息要么整体生效，要么整体不生效。

## 6. 验收用例

| 用例 | 期望 |
|---|---|
| `ApplyOnce` 同键调用两次 | 第二次 `applied=false`，资产只加一次 |
| `ApplyOnce` 内 `fn` 返回错误 | 键被撤销，资产未变，再次调用可重新执行 |
| Redis CAS 失败 | 内存回滚，资产与状态都不生效 |
| 提交成功、回包丢失 | 重试命中幂等，返回 already |
| 进程重启后 A 类键 | 从 `applied_grants` 恢复，仍幂等 |
| 消费 + 奖励 | 余额不足时不发奖；发奖成功时扣费同时生效 |
