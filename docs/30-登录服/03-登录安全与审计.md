# 登录安全与审计

登录是爆破的首选目标：成本高（查库、签 token、写审计）、收益大（成功一次就拿到凭证）。本文讲清登录服的三道防线——按 IP 的登录频控、旁路审计日志、失败锁定与错误码规范——以及它们为什么这样设计。

## 概述

登录安全的三道防线，分工与位置各不相同：

| 防线 | 位置 | 防什么 | 失败处理 |
| --- | --- | --- | --- |
| IP 限流 | `handler.AuthHandler.GuestLogin` 入口 | 脚本爆破（每秒几十次试设备号） | 429 + 1004 + Retry-After |
| 审计日志 | `loginAudit`（Kafka 旁路） | 事后追溯：风控分析、客服查证 | 只 warn 不阻断登录 |
| 错误码规范 | `internal/common/errcode` + proto | 客户端误判失败原因、内部错误透出 | 兜底 ErrParam，永不漏码成 0 |

三者的共同理念：**安全判定前置于业务成本发生之前**（限流在解 JSON 之前）、**旁路不拖累主链路**（审计失败只 warn）、**错误信息分层**（客户端拿码，服务端拿详情）。

## 核心设计

### IP 限流：位置与参数

频控放在 handler 而不是 service（`internal/login/handler/limit_test.go:3` 的注释：「爆破发生在拿到 token 之前，而 service 只负责『校验 + 签发』，不该关心来源 IP」）。且在**解析 body 之前**——爆破请求连 JSON 都不必解：

```go
// internal/login/handler/auth.go:108
// 频控放在解析 body 之前：爆破请求连 JSON 都不必解，直接回 429。
if h.limiter != nil && !h.limiter.Allow(clientIP(r)) {
	w.Header().Set("Retry-After", "60")
	writeJSONStatus(w, http.StatusTooManyRequests, map[string]any{
		"code": 1004, "msg": "登录过于频繁，请稍后再试",
	})
	return
}
```

参数：默认 20 次/分钟/IP（`config.DefaultLoginPerMinute`），令牌桶换算成每秒 rate + 突发 10——正常玩家重试几次不会被拦，而脚本爆破（每秒几十次）立刻失效。`Retry-After: 60` 让客户端按分钟级退避，业务码 1004（`ERR_CODE_RATE_LIMITED`）让客户端弹「操作过于频繁」而不是「服务器故障」。

**只信 RemoteAddr，不信 X-Forwarded-For**：没有反代时后者可被伪造，每次换个假 IP 就能绕过。部署了反代的场景再按可信代理链扩展——这是安全默认值的选择：宁可暂时误伤（NAT 后共享 IP 的玩家），不留给绕过口子。

装配在 `internal/login/server.go:157`：

```go
// 登录频控：默认 20 次/分钟/IP；配置负数则关闭（排查问题时的临时开关）
if perMin := s.cfg.Limit.LoginLimit(); perMin > 0 {
	s.authHandler.SetLoginLimiter(ratelimit.NewKeyed(perMin/60, 10, 10*time.Minute))
	s.logger.Info("login rate limit enabled", "per_min", perMin)
} else {
	s.authHandler.SetLoginLimiter(nil)
	s.logger.Warn("login rate limit disabled by config")
}
```

注意 handler 构造时也建了默认限流器（`NewAuthHandler`，`internal/login/handler/auth.go:73`）——「漏配不能变成不限流」，server 层再按配置覆盖。

### 审计：旁路解耦，容忍丢失

每次登录尝试（成功/失败）都构造 `LoginEvent` 经 `loginAudit` 投递到 Kafka topic `gs.login.log`，游戏服消费落 `login_log` 表，供风控与客服追溯：

```go
// internal/login/audit.go:25（节选）
// loginAudit 把登录事件写到 gs.login.log，由游戏服消费落 login_log 表。
//
// 生产失败只记日志：登录是主链路，不能因为审计链路抖动把玩家挡在门外。
// 每条事件用 account+毫秒 做 biz_id，消费端不做去重（流水允许重复行）。
type loginAudit struct {
	producer *pkgmq.Producer
	logger   *log.Logger
}

func (a loginAudit) Log(ctx context.Context, ev handler.LoginEvent) {
	if a.producer == nil {
		return
	}
	msg := pkgmq.LoginLogMsg{
		AccountID: ev.AccountID,
		PlayerID:  ev.PlayerID,
		IP:        ev.IP,
		Device:    ev.Device,
		Result:    ev.Result,
		Reason:    ev.Reason,
		At:        time.Now().UnixMilli(),
	}
	// biz_id 带毫秒时间戳：同一账号连点两次登录也会得到不同 id，
	// 重复行可区分；配合分区键保证同账号事件有序
	bizID := fmt.Sprintf("login-%d-%d", ev.AccountID, msg.At)
	env, err := pkgmq.NewEnvelope(bizID, pkgmq.TopicLoginLog, strconv.FormatInt(ev.AccountID, 10), msg)
	// ...
}
```

四个设计点：

**① 解耦是彻底的。** `record` 无返回错误，producer 为 nil（未配 Kafka）时静默，`warn` 出口甚至防 logger 为 nil 把主流程带崩。代价是极端情况下流水可能丢失——用「允许重复、容忍丢失」换主链路可用性。

**② 分区键用 account_id 字符串。** 同一账号的登录事件落同一分区，消费端按账号有序处理——重放/乱序攻击的检测依赖顺序。

**③ Result 用 int32 不用 error。** 审计要记录的是「事实」而不是错误对象，字符串化后的 Reason 更适合跨服务消费。失败事件同样带 accountID（service 找到了账号但后续失败），便于定位失败发生在哪一步。

**④ 流水不做业务去重。** 重复消费只产生重复行，不影响玩家状态——事实记录的语义。

### 失败锁定与错误码规范

登录失败的「锁定」当前由 IP 限流承担（额度耗尽即天然锁定该 IP 一分钟），账号级锁定由 `account.status` 封禁承担（见 `02-账号体系与封禁.md`）。错误码规范是第三块：

数值单一事实源在 `api/proto/common/v1/errcode.proto`——客户端（多语言）与服务端从同一份定义生成，杜绝「两边枚举值手抄不一致」；`internal/common/errcode/errcode.go` 提供 Go 侧常量别名与中文文案表（文案不进 wire，可独立热更）。分段规则按业务域占段：0 OK；1001+ 通用/登录态；2001+ 账号/角色；3001+ 道具；4001+ 社交/聊天；5001+ 邮件；6001+ 战斗。

登录相关的码：

| 码 | 常量 | 文案 | 出现处 |
| --- | --- | --- | --- |
| 1002 | `ErrTokenExpired` | 登录已过期，请重新登录 | 网关 HandshakeResp（token 无效） |
| 1004 | `ErrRateLimited` | 操作过于频繁，请稍后再试 | 登录 IP 限流 429 |
| 1005 | `ErrServerBusy` | 服务器繁忙 | 登出时 token 作废失败（`../20-网关层/02-路由与消息分发.md`） |
| 2001 | `ErrAccountBanned` | 账号已被封禁 | 游客登录 403 |

`errcheck_test.go` 守护两条规则：模块自建码不得与 proto 已定义值撞车（撞了客户端会按 proto 文案提示错误的失败原因——提交 `7452c87` 修过 4 处真 bug）；不同模块不能共用同一个码值（客户端无法反推是哪个模块出错）。`errcode_test.go` 的 parity 测试守护 proto/Go/文案表三方一致，漏加 CI 即红。

「proto 语义码」与「模块段码」两套并存是现状（errcode 包注释明确说明，别被误导）：proto 那套覆盖跨模块共性语义，模块段码（如 scene 41xx）覆盖各自玩法。`FromError/New` 是给「将来接入层统一错误通道」预留的封装，当前无调用点。

## 关键代码解析

### clientIP 与防御式解析

```go
// internal/login/handler/auth.go:162
// clientIP 取直连地址；网关/反代场景可再按 X-Forwarded-For 扩展。
// 知识点：net.SplitHostPort 处理 "ip:port" 形式，失败时回退整个
// RemoteAddr——防御式解析，宁可多带信息也不丢 IP。
func clientIP(r *http.Request) string {
	host, _, err := net.SplitHostPort(r.RemoteAddr)
	if err != nil {
		return r.RemoteAddr
	}
	return host
}
```

`TestClientIP` 覆盖三种输入：`1.2.3.4:5678 → 1.2.3.4`、`[::1]:5678 → ::1`、`no-port → no-port`（解析不了原样返回，不 panic）。不限流时这个函数也会被调用（审计流水记 IP），必须对任何输入都有确定行为。

### 测试时钟注入

`limit_test.go` 的 `clock` 展示了令牌桶测试的标准手法——`SetClock` 注入可推进时钟，精确控制令牌补充而不真睡：

```go
// internal/login/handler/limit_test.go:29（节选）
// TestGuestLoginRateLimited 额度耗尽后回 429 + 1004，且带 Retry-After。
//
// 断言在 auth 之前返回：h.auth 为 nil，若真走到业务层会 panic——
// 这本身就是「频控必须前置」的证明（也省掉造 AuthService 的桩）。
func TestGuestLoginRateLimited(t *testing.T) {
	h := NewAuthHandler(nil) // auth 为 nil：任何走到业务层的路径都会 panic

	l := ratelimit.NewKeyed(1, 1, time.Minute)
	now := &clock{t: time.Unix(1700000000, 0)}
	l.SetClock(now.Now)
	h.SetLoginLimiter(l)

	// 先把该 IP 的唯一令牌用掉
	require.True(t, l.Allow("1.2.3.4"))
	// ...
	require.Equal(t, http.StatusTooManyRequests, w.Code)
	require.Equal(t, "60", w.Header().Get("Retry-After"))
	require.Contains(t, w.Body.String(), "1004")
}
```

`TestGuestLoginRateLimitDisabled` 则验证关闭路径：limiter 为 nil 时不 panic，非法 JSON 先返回 400——说明确实跳过了频控、走到了解析。

## 小结

登录安全的三道防线各自守一段：**IP 限流守入口**（前置于业务成本，429 + 分钟级退避，只信直连地址）；**审计守事后**（旁路解耦彻底，容忍丢失换主链路可用，分区键保证同账号有序）；**错误码守语义**（单一事实源在 proto，分段按业务域，parity 与撞车有 CI 守护）。当前没有账号级密码（游客制），渠道登录（P7）接入后，密码错误次数锁定将与 status 封禁合流。包频率与内部号隔离在网关侧，见 `../20-网关层/04-限流与安全防护.md`。
