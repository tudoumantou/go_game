# R2.3 充值双栅栏与最终一致设计

> 基线：2026-10-23，R2.1 缓存原子变更契约落地之后
> 上游：[剩余功能开发计划](superpowers/plans/2026-10-18-remaining-development.md) R2.3
> 参考实现：`internal/login/service/recharge_service.go`（订单状态机）、`internal/game/mq/recharge_consumer.go`（发货）、`pkg/writebehind`（资产落库）

## 1. 要解决的问题

R2.1 契约规定「一次 Actor 消息 = 一份 Snapshot = 一次 CAS」，普通数据走 内存 → Redis → MySQL 的异步投影。但充值涉及钱，暴露了三个单栅栏答不上来的问题：

| 场景 | 只有 Redis 权威链路会怎样 |
|---|---|
| 发货后进程崩溃，快照未落库 | 道具奖励随进程消失，`applied_grants` 也不在——对账能发现，但期间玩家来问「钱付了货没到」 |
| 快照落了、delivered 确认丢了 | 订单永远停在 PAID，玩家邮箱里却躺着第二封充值邮件（重投） |
| Kafka 重投 + 幂等键过期（TTL 24h 后的迟来单） | Redis SETNX 判定失效，重复发货 |

结论：**钱的事实不能由缓存当权威**。充值需要一条独立于快照链路的持久化事实链，本文档称「双栅栏」。

## 2. 总体结构：两条链路，各管一段

```
渠道回调 ──► login 服 PayCallback
                │ ① 订单 CAS: PENDING → PAID（MySQL 先行）
                ▼
            Kafka gs.recharge.order（Key=order_id 保序）
                │
                ▼
        游戏服 RechargeConsumer
                ├─ 在线：GrantItemsMsg → Actor 加道具
                │        ② applied_grants 与资产同快照、同 CAS、同 MySQL 事务
                └─ 离线/异服：deliverOffline 写持久邮件
                         ③ mail.biz_id 唯一键（MySQL 先行）
                │
                ▼
            Kafka gs.recharge.delivered
                │ ④ 订单 CAS: PAID → DELIVERED
                ▼
         login 服 MarkDelivered + 对账兜底（每小时重投 PAID 未 DELIVERED）
```

两条链路的分工：

- **订单链路（login 服，MySQL 权威）**：钱的状态机，每一步 CAS 推进，不经 Redis 权威链路；
- **资产链路（游戏服，快照权威）**：道具到账走正常 write-behind，但幂等键 `applied_grants` 与资产同生共死。

## 3. 栅栏一：订单状态机（MySQL 优先）

`recharge_service.go` 的全部规则：

| 规则 | 实现 | 防什么 |
|---|---|---|
| 金额只信服务端 | `CreateOrder` 从商品表推 `amountFen`，无视客户端传价 | 98 元报成 1 分 |
| 回调幂等三层 | 状态预判（已 PAID/DELIVERED 直接成功）→ CAS 推进（`WHERE status=0`）→ RowsAffected=0 按「被别人抢先」处理 | 渠道重试、并发回调 |
| **状态先行** | 先 CAS 置 PAID，再发 Kafka；消息发送失败只记日志 | 「消息到了状态没到」窗口内游戏服拒收；反向顺序（先消息后状态）崩溃时会产生「消息已发但状态 PENDING」的单，被对账重投变成**重复发货** |
| 对账补偿 | 每小时扫 PAID 未 DELIVERED 重投 | 消息丢、消费者重启、确认丢 |

## 4. 栅栏二：applied_grants 与资产原子同体

R2.1 §2.2 定义的 A 类幂等：`AppliedGrants["<domain>:<bizID>"]`，充值键为 `recharge:<order_id>`。

关键性质——它与资产**不是两份数据，而是一份**：

```
Snapshot.Items[1001] += N          ─┐
Snapshot.AppliedGrants["recharge:O2026..."] = true ─┼─ 同一次 Lua Commit、同一个 MySQL 事务
player_writebehind.applied_grants（落库）          ─┘
```

- 发奖和记账要么都成立，要么都不成立（`persistSnapshots` 单事务）；
- 进程重启、Kafka 重投、Redis 故障后恢复，判定依据都在 MySQL 里，不依赖 Redis 幂等键的存活；
- `RechargeConsumer` 的 Redis SETNX（`idem:gs.recharge.order:{order_id}`，24h TTL）只是**第一道快筛**，不是凭据——TTL 过期的迟来单仍有 applied_grants 和订单状态机兜底。

## 5. 离线路径：mail.biz_id 唯一键

玩家不在线/不在本服时走 `deliverOffline`：订单号写入 `mail.biz_id` 唯一键，重复投递 `created=false`。这条路径的幂等由 **DB 唯一键**保证（跨实例、跨重启的最终防线），邮件与附件同事务落库，写库成功即视为交付，随即发 delivered 确认。

## 6. 故障矩阵：每个洞都被某一层兜住

| 故障 | 订单链路 | 资产链路 | 最终结果 |
|---|---|---|---|
| Kafka 消息丢失 | 每小时对账重投 | — | 补发货 |
| delivered 确认丢失 | 订单停在 PAID → 对账重投 | 幂等挡重复发货 | 状态收敛，不多发 |
| 游戏服发货后崩溃 | — | applied_grants 已在上一笔落库或从未落库 | 落库=到账；未落库=对账重投后到账 |
| Redis 故障（提交窗口） | — | 内存 pending 快照，`finishPending` 核对版本后补提交 | 不丢不重 |
| Redis 幂等键 TTL 过期后的迟来重投 | 订单状态机拒重复 | applied_grants / mail.biz_id 拒重复 | 拒收 |
| 玩家删角后残留订单 | `persistSnapshots` COUNT 校验拒写 | 整批回滚 | 不产孤立数据 |

**两条链路互为对方的对账凭据**：订单说 PAID 而资产没有对应 applied_grants → 重投；资产有 applied_grants 而订单不是 DELIVERED → 补确认。任何单点丢失都会在下一个对账周期收敛。

## 7. 为什么不开「先写 MySQL 再上缓存」的旁路

一个曾评估过的方案（记为方案 B）：Actor 处理 `GrantItemsMsg` 时先同步 UPSERT `player_grant_log`，成功再 AddItem + Commit。**未采纳**，原因：

1. **与 CAS 模型竞态**：Redis 权威模式下 Actor 内存是逻辑真相源，旁路直写 MySQL 会让同一份资产出现两个写入方，整份快照的 diff 提交可能把旁路结果覆盖回去，需要额外的合并协议；
2. **双源真相**：`applied_grants` 已经在快照里，旁路表是同一事实的第二份存储，迁移期还要处理格式分裂；
3. **收益仅是延迟**：旁路把「资产最终一致」提前到「资产强一致」，但订单链路本就是 MySQL 先行——玩家感知的「钱货两讫」以订单 DELIVERED 为准，不依赖资产写入时刻。

维持方案 A（双栅栏 + 对账）的代价是资产最终一致，收益是不破坏 R2.1 契约。若未来出现「发货延迟可感知」的渠道投诉，再评估旁路。

### 7.1 方案 B'（已落地）：版本推进取代旁路日志表

上面三条否决理由在后续实现里被逐条消解，因此以 **B'** 的形式落地：

| 当初的否决理由 | B' 怎么处理 |
| --- | --- |
| 与 CAS 模型竞态：旁路直写后，快照 diff 提交可能把它覆盖回去 | 同一事务推进 `player_writebehind.version`；异步落库的栅栏判定「快照版本 > 库版本」不成立即跳过这份快照。同步路径同时清脏标记，不产生 Commit，也就不存在「覆盖」 |
| 双源真相：旁路表是 `applied_grants` 的第二份存储 | **不新增表**。复用 `player_writebehind.applied_grants` 同一行同一字段，与版本推进同事务写入 |
| 收益仅是延迟 | 收益是**掉电不丢**：AOF `everysec` 最多丢 1 秒，而订单此时已 DELIVERED——丢的是钱，不是延迟 |

实现要点（`Repository.SaveForce` + `Actor.grantSync`）：

```
资产 + 幂等键同事务 → 事务内 version+1 → 删 Redis 快照 → 回执
```

删缓存失败**要回执 err**：静默吞掉会让「重登读旧值」一直持续到人工介入；上抛给 Kafka
重投，重投走幂等命中分支补删一次，形成自愈闭环。

判据是 `GrantItemsMsg.Sync`：充值/交易置真；邮件领取这类可重建的奖励保持异步。


## 8. 落库侧并发：writebehind 分片错峰

充值订单不走 writebehind，但普通玩家的攒批落库要扛高并发。`pkg/writebehind` 的 `Worker.Run` 采用与 `pkg/flush` 同思路的错峰调度（12.4.3 分散轮询）：

- 一个 tick 内 10 个分区按 `stagger = interval/Partitions` 依次启动，任一刻只有一个分区的合批事务在写 MySQL，削平 tick 边界的写尖峰；
- 单玩家落库延迟上界从 `interval` 变为约 `2×interval`（本分区处理完还要等后面的分区）——对签到/背包类数据可接受；
- 分区处理慢于步长自动顺延，单 goroutine 串行不会并发写同一批表；
- 每分区独立 30s 子超时，单分区卡死不拖垮全局。

测试：`TestRunStaggersPartitionsAndDrains` 验证错峰不跳分区、排空后空转不碰库。
