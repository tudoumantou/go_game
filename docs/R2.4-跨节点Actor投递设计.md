# R2.4 跨节点 Actor 投递设计（P0）

> 基线：2026-11-03，架构评估「按线上大项目标准」缺口清单的 P0 项
> 参考实现：`pkg/actor/remote.go`（远程化契约）、`internal/game/remote/remote.go`（发送端）、`internal/game/player/manager.go`（位置解析）、`internal/game/server.go`（装配与接收侧）
> 上游文档：[服务器框架设计文档](game_study-服务器框架设计文档.md) §5 Actor 系统

## 1. 要解决的问题

原架构里 Actor 是**单进程**的：`PID` 只有 ActorID 没有节点地址，`System.Send` 永远在本进程内投递。多 game 节点部署时：

| 场景 | 单进程设计的表现 |
|---|---|
| 玩家从 game-1 登录，Kafka 充值消息被 game-2 的消费者收到 | `Players.GetOrSpawn` 在 game-2 **就地拉起第二个 Actor**——两份内存各自 CAS 同一份 Redis 快照，后写覆盖先写（双写分叉） |
| game-1 上的好友给在线在 game-2 的玩家发私聊 | game-1 本地找不到 Actor，投递失败，消息丢 |
| 战斗/场景模块要推送到别的节点的玩家 | 无路可走 |

三条路径的共同缺口：**「这个玩家在哪」没有答案，「找到之后怎么投过去」没有通道**。P0 只修这一件事，不动分片模型、不改消息语义、不引入新的基础设施。

## 2. 方案选型：中心服中转，不是节点间直连

远程投递有两条路：

| | 中心服中转（采纳） | game ↔ game 直连 |
|---|---|---|
| 基础设施 | 复用现成的 `center.Client.SendRelay` / `OnRelayPush`（9.3），**零新增** | 每节点建 gRPC 服务端 + 客户端池 |
| 节点发现 | 不需要：presence 表里存的 nodeID 即路由键 | 要先查 etcd 拿 addr 再建连，多一跳发现服务 |
| 代码量 | 一个信封 + 两个 handler 钩子 | 新 proto、新 service、连接池、健康检查 |
| 延迟 | 内网多一跳（<1ms） | 少一跳 |
| 语义 | 尽力而为，不持久化不重投 | 可以做强语义，但那是 P1+ 的事 |

选型逻辑：**下行推送（好友私聊、系统推送）恰好容得「尽力而为」**——丢一条由客户端重连拉全量权威状态兜底；而请求-响应类消息（带 Done channel 的）天然不走远程（见 §6）。用不上的强语义不值得预付复杂度。

## 3. 分层契约

### 3.1 `PID.Node`：地址即数据

```go
type PID struct {
    ID   string // "player:42" 或 "scene:1001"
    Node string // "" = 本地；非空 = 远程节点 ID（= cfg.Server.Name）
}
```

`Node` 为空即本地——**单机部署零感知**，所有既有 `Send(pid, msg)` 调用点不用改。

### 3.2 `RemoteSender`：出节点的唯一出口

```go
type RemoteSender interface { Deliver(to *PID, msg any) error }
```

`System.SendWithSender` 的路由决策（`pkg/actor/system.go`）：

```
target.Node != "" && target.Node != 本节点 NodeID
    ├─ Remote != nil → remote.Deliver（跨节点）
    └─ Remote == nil → 错误（远程 PID 按本地找，找不到显式失败）
target.Node == "" 或 == 本节点
    └─ 本地信箱投递（原路径）
```

「配了多节点却没注 Relay」属于装配错误，**宁可每条远程消息显式失败，不静默丢**。

### 3.3 `RemoteMessage`：显式序列化契约

```go
type RemoteMessage interface {
    RemoteTypeURL() string                    // 注册表键，如 "game_study.player.PacketMsg"
    MarshalRemote() ([]byte, error)           // 消息体序列化
}
```

没有走 `encoding/gob`/`protobuf Any` 自动反射，而是**显式实现 + type_url 注册表**：

- 消息能不能跨节点是**编译期决定**的（没实现接口就发不出去），不是运行期发现；
- 注册表 `RegisterRemote(typeURL, decode)` 重复注册直接 panic——两个包注册同一个 type_url 是装配错误，静默覆盖会让消息解码到错误的类型上；
- 新增可远程消息 = 实现两个方法 + init 注册，不需要动框架。

目前已注册：`game_study.player.PacketMsg`、`game_study.player.PushMsg`（`internal/game/player/remote.go`）。

### 3.4 信封：JSON，带类型路由

```go
type RemoteEnvelope struct {
    ActorID string // 目标 Actor（= PID.ID）
    TypeURL string // 消息类型
    Payload []byte // MarshalRemote 的产物
}
```

选 JSON 不选 protobuf：relay payload 已经是 `[]byte`，JSON 免 protoc 依赖、可 `jq` 调试、体量在推送场景（几十字节到几 KB）无所谓。消息体本身仍是各消息自己的 `MarshalRemote`（当前是 `json.Marshal`）——信封与载荷分层，将来载荷换 protobuf 信封不用动。

## 4. 位置解析：presence 表即路由表

`player.Manager` 的两个入口，分工按「要不要付 Redis RTT」划：

| 方法 | 本地未命中时 | 用途 |
|---|---|---|
| `Get` | 直接 false，**零 IO** | 会话绑定、本节点保存等「本节点一定持有」的热路径 |
| `Resolve` | 查 presence：归属别节点 → 返回 `PID{Node: owner}`；不在线 → false | 跨节点推送（好友私聊、系统推送） |
| `GetOrSpawn` | 查 presence：归属别节点 → **返回远程 PID，不本地 Spawn**；否则本地拉起 | 登录绑定（`bindActor`） |

`GetOrSpawn` 的跨节点守卫是**双写分叉的第一道闸**：本地未命中 + 归属在别节点时返回远程 PID，`SendWithSender` 自动走中转投到 owner 节点——那边的 Actor 早就在线，消息进它的信箱，由它处理。presence 查询放在写锁外：bind 路径低频，但锁内 IO 会放大成所有 `GetOrSpawn` 的尾延迟。

presence 故障（Redis 抖）时 `IsOnline` 报错按「不在线」处理：**降级为本地 Spawn**（旧行为）。此时若玩家真在别节点在线，会短暂双 Actor——由 `bindPlayer` 的顶号守卫兜底（见 §5），且故障窗口内客户端无感知。

## 5. 顶号守卫：登录入口的咬合

`bindPlayer`（`server.go:789`）在拉起 Actor **之前**先原子占用在线状态：

```
presence.TrySetOnline(playerID, 本节点)
    ├─ ok                       → 继续绑定
    ├─ !ok 且 owner == 本节点    → 本节点旧会话（重连），继续走顶号逻辑
    └─ !ok 且 owner == 别的节点  → 拒绝绑定（"player is online on node X"）
```

与 `GetOrSpawn` 守卫形成纵深：**登录入口**挡跨节点顶号，**投递入口**挡跨节点误 Spawn。两条路径共用同一个 nodeID 口径（presence 写入值 = `cfg.Server.Name` = `actorCfg.NodeID` = Sender 的 nodeID），四者同源才不会对不上。

## 6. 语义边界：什么能远程，什么不能

| 类别 | 例子 | 远程？ | 理由 |
|---|---|---|---|
| 下行推送 | `PushMsg`（飘字/通知）、`PacketMsg` 转发 | ✅ | 尽力而为可接受，丢了客户端重连补 |
| 状态查询/命令 | 本地 mailbox 消息 | ❌（默认） | 没实现 `RemoteMessage`，编译期就发不出去 |
| 请求-响应 | `GrantItemsMsg`（带 `Done chan error`） | ❌ **显式拒绝** | channel 不可序列化；`Sender.Deliver` 对非 RemoteMessage 直接报错，调用方走原重试/对账路径 |

这条边界是**刻意保守**的：当前没有任何消息「需要」强一致远程 RPC——跨节点要保证结果的两条路（Kafka 重投、对账补偿）已经存在，P0 不需要新建第三条。

## 7. 接收侧闭环

```
game-1 玩家 A 的 Actor
    │ Send(远程 PID)
    ▼
actor.System.SendWithSender ──► gameremote.Sender.Deliver
    │ ① 类型断言 RemoteMessage（非远程显式拒绝）
    │ ② EncodeRemote → RemoteEnvelope(JSON)
    │ ③ SendRelay(relayID="game-1-<seq>", toNode="game-2")
    ▼
中心服 RelayRequest ──► 按 toNode 路由 ──► RelayPush
    ▼
game-2 centerHandler.OnRelayPush
    │ ④ DecodeRemoteEnvelope(payload) → (actorID, msg)
    │ ⑤ actorSys.DeliverRemote(actorID, msg) → 本地信箱
    ▼
game-2 玩家 A 的 Actor（同一个 "player:42" 名字，同一份状态）
```

relay_id = `<本节点>-<原子序号>`，中心服按它做幂等/ACK，进程内唯一即可。

`OnRelayPush` 的容错：解码失败记 Warn（信封格式错误，说明有旧版本节点）；`DeliverRemote` 返回 `ErrActorGone` 记 Debug——玩家已下线，客户端重连会拉全量，丢一条下行推送不构成正确性缺口。

## 8. 故障矩阵

| 故障 | 表现 | 兜底 |
|---|---|---|
| 中心服不可用 | `SendRelay` 报错，`Deliver` 上抛 | 推送路径记日志丢弃（语义即尽力而为）；登录路径 `TrySetOnline` 失败放行绑定（Warn） |
| RelayPush 丢 | 无重投 | 客户端重连拉全量权威状态 |
| 目标玩家已下线 | `DeliverRemote` → `ErrActorGone` | 记 Debug；邮件类走 `deliverOffline` 落持久邮件（既有路径） |
| presence Redis 故障 | `IsOnline` 报错 | 按不在线降级：GetOrSpawn 本地拉起，登录 TrySetOnline 失败放行；顶号守卫 + 对账兜底 |
| 新旧版本节点混跑（type_url 不匹配） | 信封解码失败 | Warn 日志；灰度期保证 RemoteMessage 集合先扩后缩 |
| 配了多节点但忘注 Remote | 远程 PID 按本地投递失败 | 装配错误显式报错（§3.2），不静默丢 |

## 10. 明确不做的（P1+ 候选）

- **强一致远程 RPC**（带超时/重试/追踪的请求-响应）：当前无需求，Kafka + 对账已覆盖；
- **Actor 迁移**（玩家从 game-1 滚到 game-2 时搬状态）：当前靠「踢下线 + 重连拉全量」，迁移是优化不是正确性；
- **节点间直连 + etcd 发现**：中心服中转够用时不做；
- **relay 持久化/重投队列**：语义是尽力而为，做持久化等于把 Kafka 再造一遍。
