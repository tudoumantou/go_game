# 重构方案：业务开发提效（缓存落库架构不变）

> 基线：2026-11-03，`a23070f`（P0 跨节点投递落地之后）
> 审视范围：12.4 万行 Go 代码，五进程 + 两个场景框架 + 24 个业务模块
> 约束：**Actor 分片模型、Redis 快照权威 + CAS、writebehind 合批错峰、充值双栅栏——一条不改**

## 0. 一页结论

问题不在架构，在**每个新功能要写的样板和要碰的文件数**。三个数字：

| 指标 | 现状 | 目标 |
|---|---|---|
| 新增一个玩法要碰的文件 | 6-7 个（proto/xml/sql/模块/robot/集成测试/注册） | 4 个（+ 1 条脚手架命令生成骨架） |
| 简单模块平均行数 | 330 行（业务约占 1/3） | 150-180 行（业务占 2/3） |
| 24 个模块中用上 Thin 基座的 | 5 个 | 17 个（关系型 3 个走 TxModule，4 个空占位不动） |

**做法**：不重写、不换框架、不动数据链路。按模块粒度增量迁移，每个 PR 可独立编译、独立测试、独立上线。

真正要引入的第三方库只有 4 个（testify / lo / errgroup / automaxprocs），其余经评估**明确不引**——理由见 §5，包括 Wire 已于 2025.8 被 Google 归档这一关键事实。

## 2. 三条红线（不改的东西）

| 红线 | 为什么不能动 |
|---|---|
| **Actor 分片 + mailbox 串行** | 业务无锁的前提；1024 分片与玩家数无关；P0 已补跨节点 |
| **Redis 快照权威 + 版本 CAS** | R2.1 契约：一次消息 = 一份快照 = 一次 CAS；回滚语义由它保证 |
| **writebehind 合批 + 分片错峰** | 落库尖峰的解法；改成就地写库等于把线上打挂 |
| **充值双栅栏** | 钱的事实链，订单状态机（MySQL）+ applied_grants 同快照同事务 |

本方案所有改动都在**业务层与装配层**，不触碰 `pkg/actor`、`pkg/writebehind`、`pkg/cache` 的核心路径。

## 3. 改造方案

### A0. 模块基座三档：先选档，再写代码（已落地）

**问题**：24 个模块无论有没有状态，都被要求走「快照 + CAS + 编解码 + 回滚」全套。榜单查询只是代理一次中心服调用，也要写 7 个接口方法；缓存权威模式下每条消息还要 clone 一份含背包/属性/Ext 的 State 并做两次 JSON Marshal——**即使 diff 为空、不产生 Redis 写，这份开销也白付**。

**三档划分**（判据：处理器里有没有写 `ctx.State`）：

| 档位 | 适用 | 基座 | 新增模块成本 | 快照开销 |
|---|---|---|---|---|
| **Plain** | 零状态：榜单查询、聊天转发、静态表 | `module.NewPlain` | 1 行装配 + 处理器 | **零**（`IsStateless` 让 Actor 直接分发） |
| **Thin** | 单玩家状态：签到、任务、背包 | `module.NewThin` | 3-5 行装配 + 处理器 | 正常 CAS |
| **无基座** | 关系型事务：好友、公会、队伍 | —（直写事务） | 手写 7 方法 + 事务 | 不走快照 |

**Plain 的关键不只是少写代码**：它实现 `module.StatelessAware`，玩家 Actor 在 `Receive` 里据此短路——

```go
case *PacketMsg:
    if a.canBypassCache(msg.MsgID) {   // loaded && 无未决提交 && 无待重载 && 模块无状态
        a.receive(ctx)                  // 直接分发：不 clone、不 marshal、不 CAS
        return
    }
    a.receiveCached(ctx)                // 原快照流程
```

顺带的好处：这种"声明式跳过"是**结构性正确**的——判错方向的后果不对称（漏判只多付开销，误放行会被三个前提挡住），不存在静默丢数据的路径。

**已落地**：`module.Plain` 基座 + `Registry.IsStateless` + `Actor.canBypassCache`，`rank` 模块已迁移（198 → 180 行，且纯读请求不再 clone 状态）。单测覆盖 dispatch/重复注册 panic/生命周期钩子/`MsgIDs` 副本/`IsStateless` 判定，以及快路径的 6 种前提组合。

**下一个候选**：`chat`（若历史消息走 Redis 而非快照）、`skill` 的只读列表部分（升级仍需 Thin）。

### A. 模块层：Thin 全面推广 + 补两个变体（最高 ROI）

**现状问题**：Thin 解决了「简单 CRUD 模块」的样板，但两类模块用不上：

| 模块类型 | 例子 | 现在为什么用不上 |
|---|---|---|
| 事件消费型 | quest / activity / copy | Thin 没有 `OnEvent` 钩子 |
| 关系型事务 | friend / guild / team | Thin 头注释已明确「不建议」——复杂度在事务不在样板 |

**改造**：

1. **给 Thin 加 `ThinOnEvent` 选项**（约 15 行），把 quest/activity/copy 三个事件型模块迁进来。事件消费是纯转发：`OnEvent(ctx, evt) { if h, ok := m.events[evt.Type]; ok { h(ctx, evt) } }`。
2. **推 9 个简单模块到 Thin**：battle / mail / shop / skill / rank / equip / partner / chat / scene——均为「有 `OnMessage`、无 `OnEvent`、无直写事务」。其中 battle 最大（669 行）且带跨服钩子（`OnMatchResult`/`OnBattleSync` 等非接口方法，不受 Thin 影响），放在该批次最后验证。
3. **关系型 3 个模块（friend/guild/team）保留原形态**，但抽一个 `module.TxModule` 基座（约 60 行）：统一「开事务 → 业务 → 提交/回滚 → 错误码映射」骨架，模块只写 `func(tx *sql.Tx) error` 里的内容。这三家现在各自手写 `BeginTx/defer Rollback/Commit`，重复度高。
4. 不动的 4 个：`register`（空白导入，无 `OnMessage`）、`level`/`create`/`recharge`（空目录）。

**模块全量分类（24 个）**：

| 分类 | 数量 | 模块 | 处置 |
|---|---|---|---|
| 已用 Thin | 5 | signin / profile / loginreward / item / attr | 不动 |
| 简单模块 | 9 | battle / mail / shop / skill / rank / equip / partner / chat / scene | PR-1 迁移 |
| 事件型 | 3 | quest / activity / copy | PR-1（先加 ThinOnEvent） |
| 关系型事务 | 3 | friend / guild / team | PR-2（TxModule） |
| 空/占位 | 4 | register / level / create / recharge | 不动 |

**收益**：12 个模块 × 约 55-70 行样板 ≈ **省 700-850 行**，且新增模块时只需要写处理器。

**风险**：极低。Thin 已被 5 个模块验证（含单测 7 项），迁移是纯机械替换，每个模块一次 PR 或一个 PR 批量。

**示意（quest 迁移后）**：

```go
// before：45 行骨架 + 20 行常量 + 14 行 switch
func (m *Module) Name() string                { return stateKey }
func (m *Module) MsgIDs() []uint32            { return []uint32{msgIDListReq, ...} }
func (m *Module) Init(ctx *module.Context) error  { return nil }
func (m *Module) OnMessage(ctx *module.Context, msgID uint32, body []byte) error {
    switch msgID {
    case msgIDListReq:   return m.onList(ctx)
    case msgIDAcceptReq: return m.onAccept(ctx, body)
    case msgIDClaimReq:  return m.onClaim(ctx, body)
    }
    return nil
}
func (m *Module) OnSave(context.Context) error    { return nil }
func (m *Module) OnLogin(*module.Context) error   { return nil }

// after：只剩三件事
m.Thin = module.NewThin("quest",
    module.ThinLogger(logger), module.ThinErrCode(codeSystem),
    module.ThinRespOf(respOf), module.ThinOnEvent(m.onEvent),
)
m.Handle(codec.MsgQuestListReq, m.onList)
m.Handle(codec.MsgQuestAcceptReq, m.onAccept)
m.Handle(codec.MsgQuestClaimReq, m.onClaim)
```

### B. 协议层：泛型处理器，业务只写纯函数（试点）

**现状问题**：每个处理器都在重复 `proto.Unmarshal` → 校验 → 业务 → `proto.Marshal` → `Reply`。48 个 `onXxx` 里这套仪式占了相当比例。

**改造**：在 Thin 之上叠加一层泛型 API（**不改现有契约，纯增量**）：

```go
// 框架侧（写一次，约 40 行）
func ThinHandleProto[Req, Resp proto.Message](
    t *Thin, reqID, respID uint32,
    fn func(*Context, Req) (Resp, error),
) {
    t.Handle(reqID, func(ctx *Context, _ uint32, body []byte) error {
        req := newReq[Req]()
        if err := proto.Unmarshal(body, req); err != nil { return err }
        resp, err := fn(ctx, req)
        if err != nil { return err }
        return ctx.Reply(respID, mustMarshal(resp))
    })
}
```

业务侧变成：

```go
// before：15 行
func (m *Module) onClaim(ctx *module.Context, body []byte) error {
    var req gamev1.QuestClaimReq
    if err := proto.Unmarshal(body, &req); err != nil { return err }
    // ... 业务
    resp := &gamev1.QuestClaimResp{Code: codeOK}
    out, err := proto.Marshal(resp)
    if err != nil { return err }
    return ctx.Reply(codec.MsgQuestClaimResp, out)
}

// after：5 行，签名即契约
m.HandleProto(codec.MsgQuestClaimReq, codec.MsgQuestClaimResp,
    func(ctx *module.Context, req *gamev1.QuestClaimReq) (*gamev1.QuestClaimResp, error) {
        // ... 业务，直接 return &gamev1.QuestClaimResp{Code: codeOK}, nil
    })
```

**收益**：单处理器省 8-10 行 × 48 个 ≈ **400-500 行**，更重要的是**类型安全**——响应类型写错编译期就报，不再靠 `respOf` 工厂手工映射。

**风险**：中。泛型 API 与现有 Thin 并存，先在 2-3 个新模块试点（如签到改版、新玩法），验证后再推广。**不做全量替换**，老模块迁移与否随缘。

### C. 装配层：server.go 1,396 行 → 4 个文件（已完成）

**实施结果**：`server.go` 1,397 → **465 行**，拆成 4 个文件：

| 文件 | 行数 | 职责 |
|---|---|---|
| `server.go` | 465 | Server 结构、New、Start（启动顺序的目录）、readiness、Shutdown、ID 表维护 |
| `server_start.go` | 420 | 14 个 `initXxx` 方法（每步一个，顺序约束写在文件头） |
| `server_session.go` | 415 | 会话绑定（OnBind/OnUnbind/OnClientPacket/kick） |
| `server_adapters.go` | 304 | 层间适配器（chatMessenger/centerHandler/rankQuerier…） |

拆法上没有做「5 个独立装配器」那么激进：`Start` 保持在一个文件里当目录，
各步骤的方法集中放 `server_start.go`。理由是**启动顺序本身是最重要的信息**，
拆到多个文件后读者反而要跳来跳去。三处不能调换的依赖写在 `server_start.go`
文件头（中心服先于 Actor、场景先于模块、跨服池先于 battle）。

### C'. 原来设想的 5 个装配器（未采纳，仅记录）

**现状问题**：`server.go` 一个函数从配置加载一路干到 Kafka 消费者起完，任何新增基础设施（比如上次的 center 客户端提前）都要在这个文件里找位置。12 个 `New(...)` 5-6 参数。

**改造**（纯搬运，无行为变化）：

```
internal/game/
  server.go          # 只剩生命周期：Config → Start → Run → Shutdown（目标 ≤ 300 行）
  bootstrap_infra.go # DB/Redis/Kafka/etcd/center 客户端/跨服连接池
  bootstrap_actor.go # Actor 系统 + 场景 + 玩家管理器 + 预加载
  bootstrap_module.go# 24 个模块的构造与注册（一张表）
  bootstrap_mq.go    # Kafka 消费者组 + 依赖注入
```

模块注册改成一张表，新增模块只加一行：

```go
var moduleSet = []func(deps) module.Module{
    func(d) module.Module { return bag.New(d.Repo, d.Logger) },
    func(d) module.Module { return signin.New(d.Repo, d.Logger) },
    // 新增模块：加一行
}
```

**收益**：server.go 可读性；新增模块的注册成本从「找位置 + 改 3 个地方」变成「加一行」。

**风险**：低。纯代码搬移，`go build` + 全量测试可验证。**明确不引入 DI 框架**——理由见 §5。

### D. 测试层：testify + 测试夹具

**现状**：28,343 行测试，断言全部手写 `if err != nil { t.Fatalf(...) }`，无 mock 库（sqlmock 只覆盖 SQL）。

**改造**：

1. 引入 `github.com/stretchr/testify`：`require.NoError/Equal/Eventually`，机械替换，**不改测试语义**。

   **实施进度（第二轮完成）**：累计转换 **约 1,830 处**，测试代码净减 **3,050 行**。
   项目内 `if ... { t.Fatal }` 从 1,808 处降到 **215 处（−88%）**。

   覆盖的形态：错误断言、单一比较、`char ||` 复合条件（拆成多条等价断言）、
   `if x := f(); cond` 初始化语句、`r.t.Fatalf` 非标准接收者。
   无法覆盖的 215 处中：34 处是块内多语句（断言外还有副作用），
   其余在 4 个因变量类型冲突回滚的文件里。

   `||` 的拆法是本轮的关键：`if A || B { fail }` 的通过条件是 `!A && !B`，
   等价于分别断言 A、B 为假——比生成 `require.False(t, A || B)` 可读得多。

   原始说明（第一轮）——三类需要人工判断的形态：

   | 形态 | 例 | 为什么不能机械转 |
   |---|---|---|
   | init 语句 | `if got := f(); got != want` | 要拆成两行，且 `got` 可能还用于消息格式化 |
   | 复合条件 | `if a != nil \|\| b == 0` | 对应的 require 调用不唯一（Error + 条件组合） |
   | 块内多语句 | `if x { t.Log(...); t.Fatal(...) }` | 断言之外的副作用要保留 |

   还有一个**必须记住的语义坑**：`if err == nil { t.Fatal }` 断言的是「err 非 nil」，
   对应 `require.Error`；机械映射成 `require.Nil(t, err)` 会把断言完全写反
   （且测试仍然"通过"，因为真实调用大多不返回错误）。这类错误只能靠
   「转换后逐包跑测试」发现。
2. 抽 3 个夹具（`testkit` 包）：`NewTestActor(t)`（内存 repo + miniredis + 单分片 System）、`NewTestDB(t)`（sqlmock 预置表）、`NewTestKafka(t)`。
3. 断言风格统一后，新增测试的模板从 30 行降到 10 行。

**收益**：`require` 替换手写断言通常省 **20-25%** 测试代码 ≈ 5,000-6,000 行，且失败信息更完整（打印期望值与实际值）。

**风险**：极低。testify 是 Go 事实标准，无运行时依赖（只在 `_test.go`）。

### E. 工具链与脚手架

| 项 | 做法 | 收益 |
|---|---|---|
| **并行加载** | `golang.org/x/sync/errgroup` 替换手写 `WaitGroup`（preload.go 等 3-4 处） | 代码少 40%，错误传播统一 |
| **集合操作** | `github.com/samber/lo`：`lo.Map/Filter/GroupBy/Find/Chunk` | 业务代码里 map→slice 聚集的循环少 100+ 行 |
| **GOMAXPROCS** | `go.uber.org/automaxprocs` 一行 import | **K8s 限 CPU 时避免按宿主机核数开 P 导致调度抖动，游戏服必备** |
| **定时任务** | 评估 `robfig/cron/v3` 统一 13 处 `time.NewTicker`（对账/活动刷新/榜单结算） | 可选，收益中等，优先级最低 |
| **新增模块脚手架** | `make new-module NAME=xxx`：生成 proto 骨架 + DDL + 模块文件（含 Thin 装配）+ 集成测试骨架 + 两处注册 | **把 7 步流程压到 1 条命令 + 填业务**，这是提效的终点 |

## 4. 预期收益汇总

| 项 | 代码量变化 | 业务侧体验 |
|---|---|---|
| A. Thin 推广 + 变体 | −700 ~ −850 行 | 新模块只写处理器 |
| B. 泛型协议处理器 | −400 ~ −500 行 | 处理器从 15 行降到 5 行，类型安全 |
| C. 装配拆分 | ±0（搬运） | 注册改一行；server.go 可读 |
| D. testify | **−3,050 行**（约 1,830 处断言） | 剩余 215 处（34 块内多语句 + 4 个冲突文件） |
| E. 工具链 | −150 ~ −200 行 | errgroup/lo/automaxprocs |

合计净减 **约 6,000-7,000 行**（占总代码 5%），但**新增功能的边际成本下降更明显**：一个简单玩法从「6-7 个文件、330 行模块、手写 7 个接口方法」变成「1 条脚手架命令 + 150 行纯业务」。

## 5. 第三方库决策表（含明确不引入的）

| 库 | 结论 | 理由 |

| `stretchr/testify` | ✅ 引入 | 测试事实标准，零运行时成本，收益确定 |
| `samber/lo` | ✅ 引入 | 零依赖泛型工具，map/slice 操作高频 |
| `x/sync/errgroup` | ✅ 引入 | Go 官方扩展库，替换手写 WaitGroup |
| `go.uber.org/automaxprocs` | ✅ 引入 | K8s 环境 GOMAXPROCS 正确性，游戏服标配 |
| `robfig/cron/v3` | ⚠️ 可选 | 13 处 ticker 收敛有价值，但非瓶颈，优先级最低 |
| **`google/wire`** | ❌ **不引入** | **已于 2025.8 被 Google 归档**。且本项目装配是一次性启动代码，手写装配器（方案 C）已足够清晰 |
| `uber-go/dig` / `fx` | ❌ 不引入 | 运行时反射 + 隐式依赖：装配错误从编译期推到启动期，与"大项目要可预测"相悖；本项目装配是线性 5 段，用不上容器 |
| `jmoiron/sqlx` | ❌ 不引入 | `gendb` 已生成 52 张表的 `Scan` 函数（5,289 行），sqlx 的 `StructScan` 零额外收益 |
| `gin` / `echo` | ❌ 不引入 | login 服仅 10 余个 HTTP 端点，Go 1.22 的 `http.ServeMux` 已支持方法+路径模式匹配 |
| `gorm` / `ent` | ❌ 不引入 | 会绕开 `gendb` 生成链路与 `Querier`（同时接受 `*sql.DB`/`*sql.Tx`）的契约，且 ORM 的隐式查询在游戏服热路径不可接受 |
| `go-playground/validator` | ⚠️ 可选 | HTTP 参数校验可简化；但游戏协议参数校验多为业务语义（"等级不够"），通用校验器帮不上 |
| `sony/gobreaker` | ⚠️ 后续 | 跨服/中心服熔断，属于可靠性建设，不在本次提效范围 |

## 6. 实施路线（4 个 PR，每个可独立上线）

| PR | 内容 | 规模 | 验证方式 |
|---|---|---|---|
| **PR-1** | Thin 加 `ThinOnEvent` + 迁移 12 个模块（9 简单 + 3 事件型） | ~20 文件 | 全量测试 + `-race`；每模块注册前后行为一致 |
| **PR-2** | 关系型 3 模块抽 `TxModule` 基座 | ~6 文件 | friend/guild/team 集成测试（事务/唯一键冲突路径） |
| **PR-3** | 引入 testify，机械替换断言 + 3 个 testkit 夹具 | ~40 文件 | `go test ./...` 全绿；覆盖率不变 |
| **PR-4** | ✅ server.go 拆 4 文件（1397→465）+ `make new-module` 脚手架 | 5 文件 + Makefile + tools/newmodule | 全量测试 + 脚手架单测（生成物可编译） |

**顺序理由**：PR-1/2 直接减少业务样板（用户最痛）；PR-3 独立无风险可并行；PR-4 涉及装配层，放最后。

**每步验收标准**：`go build ./...` + `go vet ./...` + `go test ./...` + 关键包 `-race` 全绿，且**线上行为零变化**（无功能改动，纯结构重构）。

## 7. 明确不做的事

| 不做 | 理由 |
|---|---|
| 换 Actor 框架（protoactor / asynkron） | 自研分片 Actor 已满足需求（1024 分片 + 跨节点 + 背压），引入外部框架等于重写调度层 |
| 引入 DI 容器 | 见 §5；装配是一次性启动代码，手写装配器更可预测 |
| 换 ORM | `gendb` + `Querier` 契约已解决 90% CRUD，ORM 在热路径不可控 |
| 合并 worldmap / scenemap 两套场景框架 | 二者是刻意独立的（SLG 大地图 vs ARPG 场景），合并会引入跨域耦合 |
| 拆分 `pkg` 为独立模块（multi-module） | 当前单体 monorepo 编译 3 秒，拆分收益为零、维护成本为正 |
| 全面替换老模块到泛型处理器（方案 B） | 试点验证后再定，不做无收益的大面积改动 |
