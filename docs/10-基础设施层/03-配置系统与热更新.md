# 03 配置系统与热更新

一句话定位：`pkg/config` 是全项目唯一读 YAML 的地方，「读文件 → 环境变量展开 → 解析 → normalize → Validate」五步流水线把配置错误全部拦在启动期；运行期的热更新分两条互不相同的通道——进程级配置（服务发现/开关）需重启，游戏数值配置走 `pkg/gamedata` 的原子快照替换。

## 1. 概述

配置系统要回答三个问题：

1. **一份配置怎么适配多种环境**：`configs/<service>/<service>-<env>.yaml` 按「服务 × 环境」拆分（dev/test/docker/prod），敏感信息（MySQL DSN、Redis 密码）用 `${VAR}` 注入不进仓库。
2. **配错了什么时候暴露**：`Load` 的 Validate 一步硬失败——存在性（name/env/监听地址）与跨字段约束（min_idle ≤ pool_size、shard_count 为 2 的幂）不过就不启动，不留到运行期。
3. **漏配和关掉怎么区分**：以 `LimitConfig` 为代表的三值语义——**0 = 用内置默认（默认是开启的，漏配不能变成不限流）；负数 = 显式关闭（排查问题时的临时开关）；正数 = 按配置值**。

「热更新」在本项目里特指**游戏数值配置**（gamedata）的运行期原子替换，完整设计见 [`../docs/配置热更新.md`](../../docs/配置热更新.md) 与本文第 5 节；进程级配置（监听地址、etcd 地址、分片数）编译/启动期决定，改了必须重启。两条通道的能力边界在 `../docs/配置热更新.md` 里有一张明确的「能/不能」表。

## 3. 核心设计

### 3.1 五步流水线

```go
func Load(path string) (*Config, error) {
	raw, err := os.ReadFile(path)
	if err != nil {
		return nil, fmt.Errorf("read config %s: %w", path, err)
	}
	expanded := os.ExpandEnv(string(raw))

	var cfg Config
	if err := yaml.Unmarshal([]byte(expanded), &cfg); err != nil {
		return nil, fmt.Errorf("parse config %s: %w", path, err)
	}
	cfg.normalize()
	if err := cfg.Validate(); err != nil {
		return nil, fmt.Errorf("validate config %s: %w", path, err)
	}
	return &cfg, nil
}
```

1. **ReadFile**：文件不存在/权限错在此暴露；
2. **ExpandEnv**：`${VAR}` 替换为环境变量值，**未设置的变量展开为空串**（不是报错）——这正是 normalize 要过滤空值的原因；
3. **yaml.Unmarshal**：按 struct tag 映射，类型不符在此暴露；
4. **normalize**：清理空值，让「未配置」归一成空列表；
5. **Validate**：跨字段约束，硬失败。

错误链全程 `%w` 包装，运维看到的是一条完整路径（`validate config configs/game/game-dev.yaml: actor.shard_count(1000) 必须是 2 的幂`），而不是孤立的底层错误。

### 3.2 normalize：空列表 = 功能关闭

```go
func (c *Config) normalize() {
	c.Kafka.Brokers = filterNonEmpty(c.Kafka.Brokers)
	c.Redis.Addrs = filterNonEmpty(c.Redis.Addrs)
	c.Etcd.Endpoints = filterNonEmpty(c.Etcd.Endpoints)
	c.RPC.EtcdEndpoints = filterNonEmpty(c.RPC.EtcdEndpoints)
}
```

环境变量未设置时 `${KAFKA_BROKERS}` 会展开成空串，YAML 解析出一个 `[""]` 列表；过滤后 broker 列表为空 → Kafka 自动降级禁用。**为什么不在解析前就报错**：本地开发/单功能部署经常不配 Kafka/Etcd，「空列表 = 功能关闭」让同一份配置骨架适配多种部署形态。`filterNonEmpty` 预分配 `cap=len(in)`：最坏情况一次分配到位，不触发 append 翻倍扩容。

### 3.3 Validate：两类约束

```go
func (c *Config) Validate() error {
	if c.Server.Name == "" {
		return fmt.Errorf("server.name 不能为空")
	}
	if c.Server.Env == "" {
		return fmt.Errorf("server.env 不能为空")
	}
	if c.Server.TCPAddr == "" && c.Server.HTTPAddr == "" && c.Server.GRPCAddr == "" {
		return fmt.Errorf("server 至少需要一个监听地址（tcp_addr/http_addr/grpc_addr）")
	}
	if len(c.Redis.Addrs) > 0 && c.Redis.MinIdleConn > c.Redis.PoolSize {
		return fmt.Errorf("redis.min_idle_conns(%d) 必须 ≤ pool_size(%d)", c.Redis.MinIdleConn, c.Redis.PoolSize)
	}
	if c.Actor.ShardCount > 0 && c.Actor.ShardCount&(c.Actor.ShardCount-1) != 0 {
		return fmt.Errorf("actor.shard_count(%d) 必须是 2 的幂", c.Actor.ShardCount)
	}
	// ...
	if c.Map.Enabled {
		if err := c.Map.Validate(); err != nil {
			return fmt.Errorf("map: %w", err)
		}
	}
	return nil
}
```

- **存在性**：name/env/至少一个监听地址——这三个错了进程根本跑不起来，越早炸越好。
- **跨字段约束**：`min_idle ≤ pool_size`（否则连接池启动即 panic）、`shard_count` 为 2 的幂（actor 分片用位掩码寻址，必须 2 的幂；flush 分片用取模寻址，只校验非负——两种寻址方式的差别在 [`01-Actor模型.md`](01-Actor模型.md) 与 [`06-缓存cache与writebehind.md`](06-缓存cache与writebehind.md) 分别展开）。
- **按需校验**：`map.enabled` 为 false 的进程（gateway/game/login…）不执行地图段校验——未启用地图的进程不该因为配置里没有 map 段而启动失败。

`x&(x-1) != 0` 是判 2 的幂的经典位运算：2 的幂二进制只有一位 1，减 1 后低位全变 1，相与为 0；外层 `> 0` 必须保留——0 的 `0&-1` 也是 0，会被误判为 2 的幂。

### 3.4 LimitConfig：三值语义

限流配置最容易被关掉的方式是「新增一个配置文件、忘了写 limit 段，然后线上毫无防护」。三值语义把这种情况变成不可能：

```go
// 语义：0 = 用内置默认（默认是**开启**的，漏配不能变成不限流）；
// 负数 = 关闭该类限流（排查问题时的临时开关）。
type LimitConfig struct {
	PacketRate     float64 `yaml:"packet_rate"`      // 默认 20
	PacketBurst    float64 `yaml:"packet_burst"`     // 默认 40
	ChatIntervalMS int     `yaml:"chat_interval_ms"` // 默认 1000
	LoginPerMin    float64 `yaml:"login_per_min"`    // 默认 20
}

const (
	DefaultPacketRate     = 20
	DefaultPacketBurst    = 40
	DefaultChatIntervalMS = 1000
	DefaultLoginPerMinute = 20
)

// PacketLimit 返回连接级限流参数；rate<=0 表示关闭。
func (c LimitConfig) PacketLimit() (rate, burst float64) {
	if c.PacketRate < 0 {
		return 0, 0
	}
	rate, burst = c.PacketRate, c.PacketBurst
	if rate == 0 {
		rate = DefaultPacketRate
	}
	if burst == 0 {
		burst = DefaultPacketBurst
	}
	return rate, burst
}
```

三类限流的默认值与取值处：

| 配置 | 默认 | 消费方 | 说明 |
| --- | --- | --- | --- |
| `packet_rate`/`packet_burst` | 20/40 | 网关（`internal/gateway/server.go:190`） | 每连接每秒包数 + 突发容量；够正常客户端登录后连发十几个请求，又能压住「一个连接把 Actor 信箱打满」的刷包 |
| `chat_interval_ms` | 1000 | 游戏服装配（`internal/game/server_start.go:247`）→ 聊天模块 | 聊天最小间隔，比包级限流更严：聊天写库 + 推对手 + 进 Kafka，成本高得多；chat 模块自带 `NewKeyed(1, 3, ...)` 兜底，装配层用配置值覆盖 |
| `login_per_min` | 20 | 登录服（`internal/login/server.go`） | 每 IP 每分钟登录次数；登录要查库、签 token，是爆破的首选目标 |

消费方统一按「rate > 0 才装限流器」的模式接线：

```go
if rate, burst := s.cfg.Limit.PacketLimit(); rate > 0 {
	s.router.SetPacketLimiter(ratelimit.NewKeyed(rate, burst, 5*time.Minute))
	s.logger.Info("packet rate limit enabled", "rate", rate, "burst", burst)
} else {
	s.logger.Warn("packet rate limit disabled by config")
}
```

令牌桶实现（按 key 分桶、惰性清理、虚拟时钟注入）见 [`07-限流shutdown与工具包.md`](07-限流shutdown与工具包.md)。

### 3.5 时间字段：字符串 + ParseDuration

```go
func ParseDuration(s string) (time.Duration, error) {
	if s == "" {
		return 0, nil
	}
	return time.ParseDuration(s)
}
```

**为什么 Duration 字段在 YAML 里是字符串**：yaml.v3 对 `time.Duration` 只认 int64（纳秒），写 `"45s"` 会直接类型报错；用字符串 + 显式 ParseDuration 把格式控制权拿回来。空串返回 `(0, nil)`：约定「未配置」= 零时长，调用方用 `GetXxx` 系列方法再套默认值——**解析层不塞默认，默认集中在取值处**，避免两套默认值各自漂移：

```go
func (c *Config) GetDialTimeout() time.Duration {
	d, err := ParseDuration(c.RPC.DialTimeout)
	if err != nil || d == 0 {
		return 5 * time.Second
	}
	return d
}
```

`err != nil || d == 0` 双条件兜底：解析失败（配了非法值如 "abc"）与未配置都回落默认——拨号超时是安全参数，配错时用默认值比启动失败更合理（其余关键字段仍由 Validate 拦）。

### 3.6 值字段而非指针：缺段 = 零值

Config 各段是嵌套**值**字段（非指针）——YAML 缺段时自动为零值，业务侧读出来就是「未配置」，不需要判指针 nil。MapConfig 注释把这一点说得很直白：「旧配置文件不带 `map:` 段时，`Enabled=false`，Validate 跳过地图校验，现有进程完全无感」。

MapDefaults/ApplyDefaults 是「补零值」的样板：只补零值不覆盖显式配置——地图参数里没有合法取 0 的语义（尺寸/速率/容量为 0 都是错误配置），因此补零安全；任何非法值仍会在 Validate 中报错。

## 4. 关键代码解析

### 4.1 各进程如何用配置

六个进程入口结构一致（`cmd/game/main.go` 等）：

```go
cfg, err := config.Load(*configPath)
if err != nil {
	// 启动失败：配置错不是能「带病运行」的问题
}
```

之后各组件只吃 `*Config` 的自己那段。以游戏服装配 Actor 系统为例（`internal/game/server_start.go:163`）：

```go
actorCfg := actor.Config{
	ShardCount:  s.cfg.Actor.ShardCount,
	MailboxSize: s.cfg.Actor.MailboxSize,
	Logger:      s.logger, // panic 恢复时记录堆栈（不再静默吞掉）
	NodeID:      s.cfg.Server.Name,
}
if s.centerCli != nil {
	actorCfg.Remote = gameremote.NewSender(s.centerCli, s.cfg.Server.Name, s.logger)
}
s.actorSys = actor.NewSystem(actorCfg)
```

配置段到组件是严格的一对一：actor 段 → `pkg/actor.NewSystem`、redis 段 → `pkg/cache.New`、flush 段 → `writebehind` worker 参数、limit 段 → 各限流器。`pkg/config` 不反向依赖任何业务包，保持「叶子层」。

### 4.2 配置样例：一个段落的读法

`configs/game/game-dev.yaml` 是最全的一份（游戏服用到的段都有）：

```yaml
server:
  name: game-01
  env: dev
  grpc_addr: "0.0.0.0:9100"

actor:
  shard_count: 1024            # 2 的幂
  mailbox_size: 4096           # 每 Actor 有界信箱容量

flush:                         # 10 分片分时落库（worker 共享连接池）
  shard_count: 10
  interval: 60s
  stagger: 6s                  # 相邻 worker 唤醒间隔（错峰）
  batch_rows: 500
  dirty_ttl: 10m

limit:                         # 限流：0 = 用内置默认（默认开启），负数 = 关闭该项
  packet_rate: 20
  packet_burst: 40
  chat_interval_ms: 1000
  login_per_min: 20

shutdown:
  register_drain: 3s           # 摘注册后等网关感知，再停 RPC（滚动发布）
  total_timeout: 60s
  drain_timeout: 30s           # 等在途消息（actor.Drain）
  flush_timeout: 30s           # 等 Redis 脏数据落库
```

`register_drain` 这个字段背后是一次真实事故：立即停 RPC 会让「注册已摘除但网关 resolver 还没感知」这段时间的请求打到已关闭实例——滚动发布实测约 0.63% 失败窗口（`175e320`），配置化成 3s 显式等待后归零。停机四阶段的编排见 [`07-限流shutdown与工具包.md`](07-限流shutdown与工具包.md)。

### 4.3 ${VAR} 注入与 Admin Token 的降级

```yaml
admin:
  token: ${ADMIN_TOKEN}        # 未设置则展开为空 → 只接受本机来源
```

`os.ExpandEnv` 不支持 `:-` 默认值写法，所以「未设置 = 空串」的降级逻辑在消费方：AdminConfig 的注释写明「Token 为空时管理接口只接受本机来源（127.0.0.1/::1）——默认部署不必额外配置也能给运维用 curl；一旦暴露到内网/公网就必须配 Token」。

## 5. 热更新：进程配置 vs 游戏数值

| 维度 | 进程级配置（本文的 YAML） | 游戏数值（gamedata） |
| --- | --- | --- |
| 例子 | 监听地址、etcd 端点、分片数、限流阈值 | 道具表、掉落表、活动周期 |
| 生效方式 | 重启进程 | `gamedata.Replace` / `LoadDir` 运行期原子替换 |
| 一致性 | 每个进程独立加载 | 各进程各自应用，运维保证同一份输入 |
| 回滚 | 改回 YAML 重启 | `Rollback()` 回到上一快照（保留一层） |
| 失败语义 | 启动失败（Validate 硬失败） | 整批拒绝，旧快照保留 |

热更新的核心机制（`pkg/gamedata/tables.go`）：编译期把 XML embed 进二进制作基线快照，运行期 `Replace(map[string][]byte)` 构造新 Tables → 校验 → **原子换指针**；读取方 `Cur()` 一次原子读，无锁。版本号形如 `编译期哈希+本次内容哈希前 8 字节`，只保留一层，反复热更新不会让版本串无限变长。

热更新的读取方约定（任何查配置的业务代码都要遵守）：

1. **每条消息内查一次配置**，不要跨消息缓存 `*Cfg` 指针——热更新后旧指针仍指向旧快照，消息内自洽，但跨消息会读到过期值；
2. 需要多处使用时，在同一次处理内取到局部变量再传递。

热更新的能力边界、输入格式（一张表一个 JSON 文件）、五条校验规则（表名必须存在/JSON 可解码/主键唯一/表非空/patch 非空）与「领取记录存事实不存配置 ID」的规范，完整见 [`../docs/配置热更新.md`](../../docs/配置热更新.md)。

**协议、消息号、DDL 不在热更新范围内**：它们编译进二进制，改号必须发版并同步客户端（见 [`02-网络层与编解码.md`](02-网络层与编解码.md) 的 wireBaseline 防线）。

## 6. 演进记录

- **`cda0e9e` fix(config): 三处「配置写了但代码没读」的漂移**——skill_upgrade 消耗旧实现是 `cost = Col3 * level` 线性公式，表里的 100/300 阶梯完全没被读；mail_template 模板零引用，改文案得改发送端；shop 归属硬编码 `defaultShopID = 1`，商品挂到别的商店限购会串。三处全部改为按表查值并补校验。教训写进提交信息：「运营照表调数值、玩家侧毫无变化，而且不报错——比缺功能更坑」。这也解释了为什么 gamedata 的热更测试要用「改回旧实现」的变异测试来守。
- **`1051ef9` feat(limit): 补业务限流（网关包频率 / 聊天频控 / 登录防爆破）**——LimitConfig 三段与该提交同期落地，「0=默认开启/负数=关闭」语义在 limit_test.go 用三个测试钉死。
- **`01c45c1` feat(worldmap): 补齐规划器与运行时，SLG 地图框架可端到端运行**——MapConfig 段 + MapDefaults/ApplyDefaults 引入，`map.enabled` 按需校验保证旧进程无感。
- **`175e320` chore(r11): 滚动发布暴露 0.63% 失败窗口**——催生 `shutdown.register_drain` 配置项（摘注册后等网关 resolver 感知再停 RPC）。
- **`e6a554d` fix(game): 游戏服未消费写穿队列，在线数据永不落库**——与 flush 段相关的真实缺陷：进程内 writebehind worker 未启动导致 Redis 脏队列无人消费；`DisableInlineWritebehind` 开关的存在价值即「只启动游戏服也能落库，与独立 flusher 并存时安全」。

## 8. 小结

配置系统的设计可以归纳为四句话：

1. **单一入口**：`pkg/config` 是全项目唯一读 YAML 的地方，五步流水线（读 → 展开 → 解析 → normalize → Validate）前四步容错、最后一步硬失败；
2. **三值语义防静默失效**：`0=默认开启`、`负数=关闭`、`正数=配置值`——漏配永远不会变成「功能悄悄关了」；
3. **两套默认值各就其位**：常量层的兜底默认（`Default*`）与取值层的 `GetXxx` 回落分开，避免漂移；
4. **热更新只覆盖游戏数值**：YAML 管进程形态（改了就重启），gamedata 管玩法数值（原子换指针、只滚一层），协议与 DDL 永远走发版。
