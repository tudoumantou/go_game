# 游戏服启动流程解析

重点看 [cmd/game/main.go](../cmd/game/main.go) 和 [internal/game/server.go](../internal/game/server.go)。本章描述当前实现，启动顺序图不代表每个异步初始化都已完成。

## 1. main 之前发生什么

Go 初始化依赖包和包级变量，再进入 main。游戏配置不是在 config.init 中读取，而是由 main 显式调用 config.Load。生成的策划表是编译产物，不是 Game.Start 遍历宿主机 XML 逐表加载。

入口中 `version` 的默认值是 dev，可由构建时 ldflags 注入。五个 cmd 各自是独立 main 包，可用 `go build ./cmd/game`，不需要像参考项目那样逐个指定同目录的入口文件。

## 2. 入口层顺序

```text
flag.Parse
  → 先构造默认日志
  → config.Load：读文件、展开环境变量、解析、规范化、校验
  → 用配置日志级别重新构造日志
  → signal.NotifyContext：监听 SIGINT / SIGTERM
  → game.New：创建 Server 和会话索引
  → Server.Start：阻塞运行
  → 原设计期望创建 shutdownContext 并调用 Shutdown
```

默认 logger 存在的意义是配置坏了也有错误输出。配置成功前不能指望 cfg.Log.Level 可读。New 应只组装轻量对象；可能失败的外部连接主要在 Start 中建立。

## 3. Game.Start 内部顺序

| 顺序 | 建立的能力 | 后面谁依赖它 |
|---|---|---|
| 1 | metrics HTTP 服务 | 启动期间也能观察状态 |
| 2 | MySQL、Repository、RoleService | 建角、预加载、模块 Repo |
| 3 | Redis、Presence、Deduper | 在线路由与消费去重 |
| 4 | 后台构建/维护 IDTable | 存在性查询；未 ready 时回退 DB |
| 5 | ActorSystem.Start | 玩家消息的执行环境 |
| 6 | CrossPool、CenterClient、battle 模块 | 匹配和跨服能力注入 |
| 7 | 注册 profile、attr、bag、item、battle 及数据库模块 | MsgID → Module 路由 |
| 8 | Flusher.Start、PlayerManager、Preloader | 状态归属和持久化调度 |
| 9 | Kafka 生产者与消费者 | 异步投递 |
| 10 | 注册 Game 到 etcd 并保活 | Gateway 发现目标 |
| 11 | 注册 GameService 并异步启动 gRPC 监听 | 接受 BIND 与客户端包 |
| 12 | 启动中心 Report 与跨服连接 | 节点注册、房间通信 |
| 13 | 等待 ctx.Done | 持续运行 |

读这张表要注意三个时序窗口：指标端口早于业务就绪；etcd 注册早于 gRPC goroutine 真正监听；中心/跨服流可能在 Started 日志后才连通。启动日志不是所有依赖的提交屏障。

## 4. 容器级顺序与进程内顺序

Compose 的 service_healthy 适合等待 MySQL、Redis、etcd、Kafka；业务 service_started 只表示容器已启动。gRPC DNS 在目标容器刚创建时可能暂时返回零地址，客户端退避重连会恢复。

容器里 `127.0.0.1` 指自己。当前 `game-docker.yaml` 用 `game:9100` 作为绑定并注册的地址，是单实例 Compose 中的折中；生产应把监听地址与对其他节点公布的地址分开设计。

## 5. 首个玩家为什么不在 Start 时加载

Start 建好玩家管理器，但只有会话绑定某个角色时才 GetOrSpawn。Actor 首次 Bind 执行 preload：并行查 player、player_attr、player_item、player_equip、activity_record，再调用模块 OnLogin。

五个查询并发不等于一个 SQL 或一次网络往返；它们可能占用五个连接，耗时受最慢查询与连接池排队共同影响。并行加载结束后才组装 State，避免发布半成品对象。

预加载失败时的实际传播也要核对：当前 BindMsg 未带接收者 PID，ctx.Respond 不能自动让 RPC 层等待 BindResult。因此“已经入队绑定”和“角色初始化成功”不是同一状态。

## 6. 模块不是每个玩家创建一份

Game.Start 注册的 Module 对象由 Registry 共享。玩家数据应放在 Context.State、按 player_id 索引的容器或独立实例中。不要在共享 Module 上加 `currentPlayer`、`lastReward` 一类字段，误以为它只被一个玩家调用。

## 7. 停服的设计目标与现状

推荐顺序是停止新流量 → 摘除发现 → 等待已接收任务 → 确认保存提交 → 关闭 MQ/流 → 停 Actor → 关闭 DB/Redis/metrics。

当前入口存在需要练习修正的路径：Start 在 context 取消后返回 ctx.Err，main 的 `if err != nil` 分支会 os.Exit(1)，后面的 Shutdown 可能不执行。另一方面，persistPlayer 只提交 SaveMsg，Flusher.FlushAll 并没有等待 SQL 完成的确认。这两点使“配置了 stop_grace_period 就一定保存完”无法成立。

教学修正，放在练习工程入口，**不是当前代码的行为描述**：

```go
// 主动停止应走清理流程；真正的启动失败仍需报错。
startErr := srv.Start(ctx)
if startErr != nil && ctx.Err() == nil {
    logger.Error("start failed", "err", startErr)
}
// 清理使用独立 context，不能继承已经取消的 ctx。
stopCtx, cancel := context.WithTimeout(context.Background(), 60*time.Second)
defer cancel()
if err := srv.Shutdown(stopCtx); err != nil {
    logger.Error("shutdown failed", "err", err)
}
// 实际工程还要统一决定失败退出码，并清理部分初始化的资源。
```

完整改造需要 SaveAck（提交后确认）、拒绝新消息、排空已接受任务和故障测试，仅修改入口条件不足以证明数据安全。

## 8. 怎么跟着调试

设置断点：main → game.New → Start → RoleService.Create → bindPlayer → Actor.onBind → Preloader.Load → Registry.Dispatch → profile.onPlayerInfo → sendToClient。

观察四组值：session→account、session→player、player→session、player→PID。它们的建立顺序能解释为什么“登录成功但读角色信息失败”。

```bash
# 只读观察已有容器。
docker compose -f deploy/docker-compose.yaml logs --tail=100 game gateway center cross
curl --fail http://127.0.0.1:9102/readyz
# 查看 Game 在 etcd 注册了什么。
docker compose -f deploy/docker-compose.yaml exec -T etcd   etcdctl get /services/ --prefix
```

readiness 的检查范围以各服务实现为准，不能把 HTTP 200 当作跨服、Kafka 和所有玩家数据均健康的证明。
