# 70-05 虚拟时钟改造

> 专题：消灭测试里的 `time.Sleep`，把「等时间流逝」换成「显式推进时间」或「等条件成立」。
> 涉及提交：`3f07d63`（中心服）、`01a90d6`（场景空闲超时）、`80b0e55`（玩家心跳）、`497e603`（停机竞争，同根问题）。
> 结论：中心服三个包的 sleep 全部清零；相关用例从「偶发红」变成「确定绿」。

## 1. 问题家族：一切「和时间赛跑」的测试

这一轮遇到的 flaky 有同一个根：**测试用睡眠代替同步**。三种典型形态：

| 形态 | 例子 | 为什么错 |
| --- | --- | --- |
| 睡固定时间等结果 | `time.Sleep(100ms)` 后断言队列已消费 | 负载高时 100ms 没消费完；负载低时白睡 100ms |
| 两个 timer 竞争 | `select { case <-time.After(20ms): … }` vs 步骤阻塞 80ms | 高负载下两个 timer 同时到期，select 随机选，行为不确定 |
| 依赖真实定时器计数 | 150ms 内 loop 跑了几拍 | CI 机器负载直接决定通过与否（见 [70-01](01-定时器测试flaky修复.md)） |

## 2. 方案：注入时钟，而不是注入睡眠

### 2.1 配置层的 Clock

`pkg/config` 的 `Config.Clock` 是总开关：

```go
// 语义（config.go，意会）：
type Config struct {
	// Clock 返回当前时间。默认 time.Now；
	// 测试注入可推进的时钟，生产零感知。
	Clock func() time.Time
	// now 同理会话/缓存的各类 TTL 计算都走它
}
```

测试里的推进方式（`atomic.Int64` 存 UnixNano，`Advance` 拨快）：

```go
var clock atomic.Int64
now := func() time.Time {
	return time.Unix(0, clock.Load())
}
cfg := config.Default()
cfg.Clock = now
clock.Store(time.Now().UnixNano())
// ……测试里
clock.Add(30 * time.Second) // 「时间过去 30 秒」，不睡
```

### 2.2 三处改造实录

**中心服 relay/registry/matcher**（`3f07d63`）：三个包里散落的 `time.Sleep` 全部替换为虚拟时钟推进。典型场景是「租约即将过期」的用例：以前睡到 TTL 边缘（慢且 flaky），现在把时钟拨到 TTL 边缘（瞬间且确定）。

**场景空闲超时**（`01a90d6`）：场景空闲 N 秒后关图的用例，原来睡真实 N 秒——**这是全仓库最慢的测试之一**。改虚拟时钟后毫秒级完成。

**玩家心跳**（`80b0e55`）：这个用例展示了第三种手法——**等条件成立**：

```go
// 改之前的写法（意会）
time.Sleep(50 * time.Millisecond)
require.True(t, actor.Heartbeated())

// 改之后：轮询等条件，超时兜底
require.Eventually(t, func() bool {
	return actor.Heartbeated()
}, 2*time.Second, time.Millisecond) // 条件一成立就走，不再白睡
```

选型规则：**系统内部有时钟（TTL、超时判定）→ 注入虚拟时钟；系统在等外部条件 → 轮询等条件**。

### 2.3 同根问题：停机的结构化同步

`497e603` 修的两个 flaky 属于「两个 timer 竞争」形态，手法升级为**结构化同步**（channel 显式放行）：

```go
// 改之前：20ms 超时 vs 80ms 阻塞，select 竞争
ctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond)
err := m.Run(ctx)

// 改之后：手动 cancel + channel 显式放行，步骤故意不响应 ctx
started := make(chan struct{})
release := make(chan struct{})
m.Register("drain-inflight", PhaseDraining, func(context.Context) error {
	close(started)
	<-release
	return nil // 故意不响应 ctx：模拟「跑完了但预算恰好用尽」
})
ctx, cancel := context.WithCancel(context.Background())
done := make(chan error, 1)
go func() { done <- m.Run(ctx) }()
<-started
cancel()     // 预算耗尽（生产里是 WithTimeout 到期）
close(release)
```

为什么这比拨时钟更彻底：它连「预算什么时候耗尽」都是测试显式决定的，两个 timer 竞争的结构被彻底拆掉。修之前约 1/300 失败，修之后负载下各 100 次通过。完整分析见 [70-10](10-停机flaky与持续集成.md)。

## 3. 限流器也照方服药

`pkg/ratelimit` 的令牌桶同样注入了时钟（`SetClock`），测试精确控制补充速率与清理时机：

```go
// NewKeyed 创建分桶限流器；idle<=0 时用 10 分钟。
//
// rate<=0 表示不限制（Allow 恒 true）——用配置关掉限流时不必改调用点。
func NewKeyed(rate, burst float64, idle time.Duration) *Keyed { … }

// SetClock 注入时钟（测试用；须在首次 Allow 之前调用）。
func (k *Keyed) SetClock(now func() time.Time) { … }
```

「须在首次 Allow 之前调用」是个有意的约束：时钟中途更换会让 `last` 与令牌数的计算出现跳变，测试要换时钟就该新建限流器。

## 4. 效果与验证

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 场景定时器用例耗时 | 150ms | 8ms |
| 场景空闲超时用例 | 睡真实 N 秒 | 毫秒级 |
| 中心服 sleep 处数 | 若干 | 0 |
| 停机用例失败率 | ~1/300 | 0/100（负载下） |
| `-race` 重复 | 偶发红 | 30 次全绿 |

## 5. 经验沉淀

1. **测试里的每个 `time.Sleep` 都是一笔技术债**，它让测试同时变慢和变 flaky——两样全占。
2. **时钟是依赖，不是环境变量**。把它做成可注入的 `func() time.Time`，和把 DB 做成可注入的 repo 是同一件事。
3. **默认值必须等于原行为**：`Clock == nil` 时用 `time.Now`，生产零感知（同 [70-01](01-定时器测试flaky修复.md) 的 `NewTimer` 纪律）。
4. **拨时钟优于等条件优于睡眠**：能显式驱动就不要被动等待；必须等外部条件时，用 `Eventually` 轮询 + 超时兜底，不要睡固定值。
