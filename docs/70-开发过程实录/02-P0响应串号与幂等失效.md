# 70-02 P0：响应串号与幂等失效

> 专题：一个请求发出两条响应，客户端从此「每个响应晚一拍」，所有幂等错误码被前一条残留的 `code=0` 顶掉。
> 涉及提交：`dcd8354`（修复）、`07a6a1d`（静态检查固化）。
> 结论：6 个模块删除 handler 内显式回包；`go test ./...` 与集成测试全绿（21 用例）。

## 1. 现象：断言拿到 code=0，服务端明明回的是 5002

集成测试 P6/P6B 的「重复领取」用例失败：客户端断言拿到 `code=0`（成功），而服务端日志明确显示回的是 `5002`（邮件已领取）/ `7104`。更怪的是，这个失败时隐时现——有时候全绿，有时候一片红。

## 2. 根因：一条请求，两条响应

模块系统里 `module.Typed` 的约定是：**handler 返回 nil 后，由框架自动回包**。但有 6 个模块（quest/mail/bag/shop/battle/copy）的 handler 里又显式 `reply` 了一次。于是每个成功请求发出两条响应：

```text
客户端请求 N ──► 服务端
服务端响应 N-1 ──► 客户端读走   ✓（这是请求 N-1 的第一条）
服务端响应 N   ──► 客户端读走   ✗（其实是请求 N-1 多出来的第二条！）
服务端响应 N+1 ──► 客户端读走   ✗（其实是请求 N 的响应）
```

连接里永远**多压着一条**，客户端读到的每个响应都比自己的请求晚一拍。表现就是：

- 成功请求看起来正常（晚一拍但 code=0）；
- **幂等错误码（5002/7104/4005）全部被前一条残留的 `code=0` 顶掉**——玩家重复领奖永远「成功」；
- 单测抓不到：单测直接调 handler，不经过 Typed 的自动回包路径；
- 集成测试只能间接暴露：现象是「幂等失效」，看起来像业务逻辑错，很容易查错方向。

`quest.go` 改前的样子（提交 `dcd8354` 的 diff）：

```go
func (m *Module) onClaim(ctx *module.Context, req *gamev1.QuestClaimReq, resp *gamev1.QuestClaimResp) error {
	// …校验、发放…
	if raw, err := proto.Marshal(&gamev1.BagChangeNotify{Changes: module.ToItemChanges(changes)}); err == nil {
		resp.Rewards = raw
	}
	if err := reply(ctx, msgIDClaimResp, resp); err != nil {   // ← 就是这一行
		return err
	}
	if ctx.AddExp != nil {
		ctx.AddExp(expGain)
	}
	return nil   // ← Typed 看到 nil，又自动回一次
}
```

## 3. 修复：删掉手动回包，统一交给 Typed

```go
func (m *Module) onClaim(ctx *module.Context, req *gamev1.QuestClaimReq, resp *gamev1.QuestClaimResp) error {
	// …校验、发放…
	if raw, err := proto.Marshal(&gamev1.BagChangeNotify{Changes: module.ToItemChanges(changes)}); err == nil {
		resp.Rewards = raw
	}
	// 发经验（Actor 内部会推送等级变化）；仍在同一条消息内，随同一份快照提交。
	if ctx.AddExp != nil {
		ctx.AddExp(expGain)
	}
	// 回包由 module.Typed 统一完成：这里再 reply 一次会让客户端收到两条响应，
	// 多出来的那条留到下一次请求时被当成新响应读走。
	return nil
}
```

连带清理：

- `mail.replyTake`、`bag.replyUse` 两个「只做 marshal + reply」的薄包装随之删除（它们正是问题写法 `m.replyXxx(ctx, resp)` 的温床）；
- 通知类推送（`BagChangeNotify` 等）**不受影响**——协议号不同，是 handler 直接发，不是回本请求响应；
- 顺带发现 `scene.onSync` 找不到场景时 `return nil`，Typed 用零值回包，客户端拿到的 `code=0` 与「同步成功」无法区分——补回早已定义但没用上的 `codeNotIn(4005)`。

## 4. 为什么必须静态检查，而不是靠测试

这次事故暴露了一个测试盲区，提交 `07a6a1d` 的原话：

> 刚修的重复回包问题，单元测试和集成测试都只能间接暴露（前者直接调 handler，不经过 Typed；后者表现为「幂等失效」，看起来像业务逻辑错）。所以固化成静态检查，进 CI。

`internal/game/module/convention_test.go` 用 `go/ast` 做检查：

```go
func checkFile(t *testing.T, path string) {
	fset := token.NewFileSet()
	f, err := parser.ParseFile(fset, path, nil, 0)
	// 1) 收集 Typed 绑定：handler 名 → 响应号常量名。
	//    module.Typed(MsgXxxResp, m.onXxx)
	typed := map[string]string{}
	ast.Inspect(f, func(n ast.Node) bool {
		call, ok := n.(*ast.CallExpr)
		if !ok { return true }
		sel, ok := call.Fun.(*ast.SelectorExpr)
		if !ok || sel.Sel.Name != "Typed" || len(call.Args) != 2 { return true }
		m, ok := call.Args[1].(*ast.SelectorExpr)
		if !ok { return true }
		typed[m.Sel.Name] = exprString(call.Args[0])
		return true
	})
	// 2) 检查这些 handler 的函数体里有没有回「本请求响应号」的调用。
	…
}
```

判定规则的三个精细之处（`isResponseReply`）：

1. **只认响应，不认推送**：`ctx.Reply(msgIDBagChange, ...)` 这类通知合法——依据是发的协议号是否等于该 handler 的响应号；
2. **薄封装按违规算**：`m.replyTake(ctx, resp)` 这种看不到协议号的形态，只要是「只传 resp 的 reply 辅助函数」就按违规处理——这正是 mail/bag 出过事的写法；
3. **防空扫自检**：`require.Greater(t, scanned, 10)`——目录扫空了（比如路径写错）测试必须失败，而不是「没扫到所以通过」。

## 5. 验证：双向变异

静态检查最怕「写得好看但抓不到人」，所以做了双向变异：

| 注入的变异 | 期望结果 | 实际 |
| --- | --- | --- |
| 在某 Typed handler 里加一次响应回包 | 检查失败并给出文件行号 | 抓到 ✓ |
| 加一次通知推送（协议号不同） | 检查通过 | 通过 ✓ |

## 6. 测试侧的连带修复

修复生产代码的同时，集成测试自身也带着伤（`dcd8354` 提交信息）：

- P12 的 seed 按新 schema 写整份 JSON（`player_equip`/`activity_record` 两表早已改成整份 JSON 落库，seed 还按旧列结构插）；
- 活动进度断言改用 `Eventually`——落库已是 write-behind 异步，「写完立刻查库」的断言本来就是错的。

## 7. 经验沉淀

1. **框架自动做的事，业务绝不重复做**。Typed 自动回包是好事，但必须有「不许手动回包」的强制机制，否则每加一个模块就多一次踩坑概率。
2. **测试抓不到的 bug，用静态检查兜底**。前提是检查本身可变异验证，且防「空扫通过」。
3. **现象会骗人**：「幂等失效」看起来像业务逻辑错，实际根因在传输层多了一条包。查这种「时隐时现」先问：连接里有没有多压着一条？
