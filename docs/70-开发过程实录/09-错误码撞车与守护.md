# 70-09 错误码撞车与守护

> 专题：4 处模块自建错误码与 proto 已定义值撞车，客户端按 proto 文案提示，玩家看到错误的失败原因。
> 涉及提交：`7452c87`（撞车修复 + 守护测试 + 网关内部号隔离）。
> 结论：scene 统一 41xx、battle 用 6006/6007；`errcheck_test.go` 把「允许的语义复用」写成白名单，其余撞车一律失败。

## 1. 现象：玩家看到错误的失败原因

错误码有两层（`errcheck_test.go` 包注释的定性）：

1. **proto 的 ErrCode**（`errcode` 包镜像）：跨模块共性语义，客户端与 proto 同源生成，**码值→文案的对应关系在客户端**；
2. **各业务模块的 codeXxx**：按模块分段（41xx 场景、5xxx 邮件、6xxx 战斗、7xxx 任务），模块内自洽，客户端按段兜底。

两层并存本身不是问题，问题是**数值撞车**：模块用了 proto 已定义的某个值但语义不同，客户端按 proto 的文案提示，玩家看到的就是错的。本轮抓出 4 处：

| 模块码 | 值 | 撞上的 proto | 玩家实际看到 |
| --- | --- | --- | --- |
| scene `codeNoScene`（不在场景） | 4001 | `CHANNEL_CLOSED` | 「频道未开放」 |
| scene `codeBusy`（场景繁忙） | 4003 | `CHAT_TOO_FAST` | 「发言太频繁」 |
| battle `codeAlreadyIn`（已在队列） | 6001 | `BATTLE_NOT_FOUND` | 「战斗不存在」 |
| battle `codeModeClosed`（玩法未开放） | 6004 | `BATTLE_FULL` | 「战斗已满」 |

修复：scene 统一 **41xx**、battle 改用 **6006/6007**；与 proto 语义一致的部分（bag 三码、chat 4001、mail 三码、battle 6002/6003）**保持不动**——那是真的复用，不是撞车。

## 2. 守护：白名单 + 禁止跨模块共用

`internal/common/errcode/errcheck_test.go` 把规则固化为测试：

```go
// semanticReuse 允许与 proto 共用码值的情形：模块 → 码值 → 期望的 proto 名。
//
// 只有**语义真的相同**才能登记。新增一条等于承诺「客户端按 proto 文案提示
// 这个码时，玩家看到的话是对的」。
var semanticReuse = map[string]map[int32]string{
	"bag": {
		3001: "ERR_CODE_ITEM_NOT_EXIST",
		3002: "ERR_CODE_ITEM_NOT_ENOUGH",
		3004: "ERR_CODE_ITEM_NOT_USABLE",
	},
	"chat":    {4001: "ERR_CODE_CHANNEL_CLOSED"},
	"mail":    {5001: "ERR_CODE_MAIL_NOT_FOUND", 5002: "ERR_CODE_MAIL_TAKEN", 5003: "ERR_CODE_NO_ATTACHMENT"},
	"battle":  {6002: "ERR_CODE_BATTLE_TOKEN_INVALID", 6003: "ERR_CODE_RESULT_REPORTED"},
}

// codeDecl 匹配模块里的业务码常量声明（缩进的 codeXxx int32 = N）。
var codeDecl = regexp.MustCompile(`(?m)^\t(code\w+)\s+int32\s*=\s*(\d+)`)
```

检查逻辑两条规则：

1. **撞 proto 值必须登记白名单**：`TestModuleCodesDoNotClashWithProto` 扫描 `internal/game/module/*` 的所有 `codeXxx int32 = N` 声明，命中 proto 已定义值却不在白名单 → 失败；
2. **不同模块不能共用同一个码值**：客户端无法反推是哪个模块出错——比如 team 借 guild 的 6101，两个模块都可能回 6101，客户端按 guild 的文案提示就错了。

白名单的注释写明了登记的含义：「新增一条等于承诺客户端按 proto 文案提示这个码时，玩家看到的话是对的」——把「允许复用」从潜规则变成显式承诺。

## 3. 同提交的另一件事：网关内部号隔离

`7452c87` 还补了一条注释声称已久、代码一直没有的隔离：

> router.OnPacket 在 pre-auth 之后加显式检查：9000+ 只能走 gRPC。原来靠「注册表恰好没注册这些号」兜底——那是碰巧，谁把内部号注册进客户端表，客户端就能触发它。

原来靠「注册表恰好没注册」兜底 = 没有任何保证。补显式白名单检查 + 5 个用例（内部号断连/客户端号放行/pre-auth 放行/未鉴权业务包断连/未知会话不 panic），变异验证能抓到。

## 5. 经验沉淀

1. **错误码是协议的一部分，不是模块的私有财产**。客户端按 proto 文案提示，意味着「码值→文案」的映射权在客户端——模块自建码必须让出 proto 已占用的值。
2. **白名单优于黑名单**：默认拒绝撞车，显式登记的才放行。新增复用的成本是一条注释级的承诺，误复用的成本是玩家看到错误提示。
3. **「注释声称已久」是技术债的报警器**：这次抓到的内部号隔离，注释里早就写了「只能走 gRPC」，代码却没有——看到这类注释，第一反应该是去验证代码，而不是相信注释。
