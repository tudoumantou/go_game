# 70-03 补齐 12 个零测试模块

> 专题：12 个业务模块覆盖率 0%，用一套共享脚手架 + 窄接口把它们拉到 43%~97%。
> 涉及提交：`0833cc5` mail、`4b8e23b` bag、`7798eab` shop、`9d1bb6c` chat、`c231cc2` team、`a53d736` guild、`907f750` equip、`5f93baa` battle、`6134a0b` profile/attr/item/register。
> 结论：模块层测试从「大面积空白」到「每个模块至少覆盖正常路径 + 错误分支 + 幂等」。

## 1. 起点：为什么是 0%

这些模块不是没写测试，是**写不了**：模块直接依赖 MySQL/Redis/Kafka 的真实客户端，测试要么不起容器跑不动，要么起了容器慢到没人跑。于是一行测试都没有，业务逻辑的正确性完全靠集成测试兜——而集成测试此前长期不可编译（见 [70-10](10-停机flaky与持续集成.md)），等于双层放空。

## 2. 两步走：脚手架 + 窄接口

### 2.1 共享脚手架 moduletest

`internal/game/module/moduletest/state.go` 提供内存版 `PlayerState`（18 个方法）与 `Recorder`（下行记录器）。模块测试不用 DB、不用网络：

```go
// 用法意会（各模块 _test.go 的真实形态）
st := moduletest.NewPlayerState()
rec := moduletest.NewRecorder()
m, _, _, _ := newTestModule(repo)   // 模块 + fake repo + ctx
ctx := module.NewContext(st, rec, nil, …)
err := m.Handle(ctx, msgIDTakeReq, reqBody)
require.EqualValues(t, mailTaken, rec.CodeOf(msgIDTakeResp))
```

脚手架本身的演化史见 [60-测试体系/02](../60-测试体系/02-moduletest脚手架.md)。

### 2.2 窄接口：把「数据从哪来」从模块里剥掉

以 mail 为例（`0833cc5`）：模块原来直接持有具体 repo 实现，测试只能起真库。抽出 `mailRepo` 窄接口后：

```go
// mail.go：模块只依赖它需要的方法（意会，真实定义见 mail.go）
type mailRepo interface {
	UnreadCount(ctx context.Context, playerID int64) (int64, error)
	FindByID(ctx context.Context, playerID, mailID int64) (*model.Mail, error)
	// …
}

func New(repo mailRepo, logger *log.Logger) *Module { … }
```

测试注入 `fakeRepo`（内存切片），把「查询失败」「插入失败」「并发未读」这些**故障分支**也变成可构造的输入——这正是 0% → 43% 里那 43% 的含金量：不只是正常路径。

同一手法复制到 chat（`9d1bb6c`，chatRepo）、team（`c231cc2`，teamRepo）、guild（`a53d736`，guildRepo）。**抽接口的动机不是「设计优雅」，是「让故障可注入」**——每个 fakeRepo 都带 `unreadErr`/`insertErr` 这类字段就是证据。

## 4. 踩坑：Recorder 把空响应当「没回包」

 equip 补测试时抓到一个脚手架自身的 bug（`907f750`）：

```go
// 改之前——空 proto 响应序列化后是 0 字节，
// append([]byte(nil), body...) 返回 nil，把「回了空包」误判成「没回包」
func (r *Recorder) Send(msgID uint32, body []byte) error {
	r.last[msgID] = append([]byte(nil), body...)
	r.count[msgID]++
	return nil
}

// 改之后——make + copy，空包也是「回了一个 0 字节的包」
func (r *Recorder) Send(msgID uint32, body []byte) error {
	r.mu.Lock()
	defer r.mu.Unlock()
	buf := make([]byte, len(body))
	copy(buf, body)
	r.last[msgID] = buf
	r.count[msgID]++
	return nil
}
```

这个 bug 会让「回了空响应」的用例报「没收到回包」——**测试工具的 bug 比没工具更坑**，因为它污染所有结论。修它的 commit 和补 equip 测试在同一个提交里，因为它是被 equip 的用例逼出来的。

## 5. 验证：每模块三处变异

「测试写了」不等于「测试有用」。每个模块的修复都配三处变异验证，举 equip 的例子（`907f750` 提交信息）：

| 变异 | 期望 |
| --- | --- |
| 去掉重复穿戴的幂等短路 | 用例失败 |
| 卸下加成的符号写反 | 用例失败 |
| 去掉槽位冲突检查 | 用例失败 |

三处全部被抓，才认为这 13 个用例有效。battle 的三条不变量（令牌校验、重复上报、状态迁移）同理。

## 6. 可复制的模式

这轮之后，「给模块补测试」有了固定配方：

1. 模块依赖的 repo 抽窄接口（只留模块真正调的方法）；
2. fake repo 带 `xxxErr` 字段，故障分支可构造；
3. 用 `moduletest` 的 `PlayerState` + `Recorder` 驱动 handler；
4. 用例覆盖：正常路径、每个错误分支、幂等（重复请求）；
5. 三处变异验证测试有效；
6. 顺带删死代码（chat 的 `reply` 就是这轮删的）。

## 7. 小结

0% 覆盖的根因往往不是「懒」，是**依赖不可替换**。把数据来源换成窄接口、把执行环境换成内存脚手架之后，补测试从「一个专题」变成「一个下午」。这也为后面的 Stateful 迁移（[70-04](04-P1迁往Stateful.md)）提供了安全网——没有这张网，谁也不敢动 7 个模块的持久化代码。
