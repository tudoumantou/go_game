# 70-06 登出与跨节点真顶号

> 专题：补上「登出」这件本就不该缺的事；把跨节点顶号从「拒绝新连接」改成「接管并踢旧」。
> 涉及提交：`2e28e12`（登出/顶号/封禁）、`a23070f`（跨节点 Actor 投递，前置）、`9c3f9a4`/`18e3e61`（R2.5 会话令牌）。
> 结论：登出全链路（协议+顺序+语义）；同节点与跨节点顶号行为一致。

## 1. 登出：之前完全没做

### 1.1 协议与顺序

新增 `LogoutReq/Resp`（消息号 100/101，连接管理段，`api/proto/gate/v1/handshake.proto`）。网关 `handleLogout` 的顺序被注释定为**正确性的一部分**（`internal/gateway/router/router.go:367`）：

```go
// handleLogout 处理主动登出：作废 token → 回包 → 断连。
//
// 顺序不能变：先作废再回包再断连。
//   - 先作废：回包代表「已登出」，若回包后作废失败，客户端会以为 token 已失效；
//   - 回包后才断：conn.Send 是同步 raw.Write，返回即已交给内核；
//     先断会导致客户端收不到 LogoutResp，只能靠读 EOF 猜结果。
//
// 不作废成功也要断连：token 还在是安全隐患，但把连接留着更糟
// （用户会继续用一条「已登出」的连接发业务包）。回 code=1005 让客户端重试。
```

三个分支的语义都经过推敲：

| 情况 | 行为 | 理由 |
| --- | --- | --- |
| 作废成功 | `code=0`，回包，断连 | 回包即代表「已登出」 |
| 作废失败 | `code=1005`，仍断连 | token 没删掉却回成功，客户端会以为登出了，而 token 在 TTL 内还能重放；但留着连接更糟 |
| 无 Redis 单测环境（revoker 未注入） | 不 panic，仍断连 | 测试装配不齐时不能炸 |

配套抽出 `TokenRevoker` 接口，与 `Validator` **分开**——提交信息里的理由：校验失败 = 拒绝登录；作废失败 = 用户以为登出了但凭证还有效。两种失败语义完全不同，混在一个接口里迟早被同一个调用方用错。

### 1.2 断连之后发生什么

登出断连触发游戏服 `OnUnbind` → Actor 下线 → 模块 `OnLogout` 钩子 → 落库。这条路径与掉线、被踢**完全同构**，所以登出不需要新机制，只需要把「上游」做对。

## 2. 跨节点顶号：从「拒绝」到「接管」

### 2.1 旧行为为什么不成立

早先的实现：同节点顶号（踢旧的），跨节点**拒绝新的**——玩家换设备时如果网关把连接路由到另一个游戏服，就会看到「已在其它节点登录」的报错。同节点顶号、跨节点报错，行为不一致；而顶号的产品语义明明是「新登录挤掉旧会话」，与连接落在哪个节点无关。

### 2.2 claimOnline：接管而非拒绝

`internal/game/server_session.go` 的自由函数版 `claimOnline`（为可测试性把逻辑与 Server 绑定版分开，测试可注入 fake presence）：

```go
// claimOnline 占用玩家在线归属；被别的节点持有时先通知对方踢人再强制接管。
//
// 为什么是「接管」而不是「拒绝」：顶号的产品语义是「新登录挤掉旧会话」，
// 与连接落在哪个节点无关。……
//
// 时序：notify 是异步通知（远程投递单向、不等待），随后立刻覆盖 presence。
// 旧节点的 Actor 可能还活着一小会儿，但它的快照提交会被围栏令牌（epoch）
// 挡掉——这正是 R2.5 设计的目标场景，不需要在顶号路径上额外加锁等待。
func claimOnline(ctx context.Context, p onlinePresence, self string, playerID int64,
	ttl time.Duration, notify func(nodeID string, playerID int64)) (tookOver bool, err error) {
	ok, owner, err := p.TrySetOnline(ctx, playerID, self, ttl)
	switch {
	case err != nil:
		// 占用失败不阻断绑定：Redis 抖动时宁可双开一会儿，也别让玩家登不进来。
		// 双开的窗口由围栏令牌兜底（后写者胜），最终一致。
		return false, nil
	case ok || owner == self:
		return false, nil
	}
	if notify != nil {
		notify(owner, playerID) // 异步 KickMsg，不等待 ACK
	}
	if err := p.SetOnline(ctx, playerID, self, ttl); err != nil {
		return true, fmt.Errorf("force online after remote kick: %w", err)
	}
	return true, nil
}
```

三个决策各有分寸：

1. **Redis 抖动不阻断登录**（`err != nil` 分支）：可用性优先，双开窗口由 epoch 围栏兜底；
2. **通知是异步的**：远程投递单向、不等待 ACK——presence 已切换，旧 Actor 的提交会被围栏令牌挡掉，不需要在顶号热路径上加锁等待；
3. **强制接管也可能失败**（`SetOnline` 报错）：这时返回错误让绑定失败，因为 presence 与真实持有者已经不一致，继续绑定会产生两个「自认为是权威」的节点。

### 2.3 KickMsg：跨节点踢人的Actor投递

被顶号节点收到的是玩家 Actor 的 `KickMsg`（`a23070f` 引入的跨节点投递能力，`internal/game/player/actor.go`）：

```go
// kickRemotePlayer 通知持有该玩家的节点踢掉本地会话。
//
// 发不出去不算失败：presence 已被覆盖，旧节点的提交会被围栏令牌挡住，
// 它自己的心跳/UNBIND 也会让它下线，只是晚一点。
func (s *Server) kickRemotePlayer(nodeID string, playerID int64) {
	if nodeID == "" || s.actorSys == nil {
		return
	}
	pid := &actor.PID{ID: player.ActorID(playerID), Node: nodeID}
	if err := s.actorSys.Send(pid, player.KickMsg{FromNode: s.cfg.Server.Name}); err != nil {
		s.logger.Warn("notify remote kick failed", …)
	}
}
```

接收端 Actor 通过 `SetKickHook` 回调 `kickLocalPlayer` → `kickSession`——**与同节点顶号走同一条下线路径**（发 KickNotify → 客户端断开 → UNBIND → OnLogout 落库）。两条路径共享同一套副作用，这是「行为一致」的代码级保证，而不是两份各自正确的实现。

### 2.4 bindPlayer：三张表同一把锁

```go
// 三张表在同一把锁内完成「读旧会话 → 写新映射」：old 是被顶号的旧会话
// （0 表示首次绑定）。players2sess 是顶号判定的唯一权威，必须先于
// kick 完成切换，否则旧连接的迟到 UNBIND 会命中错误的会话身份。
s.mu.Lock()
old := s.players2sess[playerID]
s.sessions[sessionID] = playerID
s.players2sess[playerID] = sessionID
accountID := s.accounts[sessionID]
s.mu.Unlock()

if old != 0 && old != sessionID {
	s.kickSession(old, "login_elsewhere")
}
```

`players2sess` 先切换再踢旧，保证旧连接迟到的 `UNBIND` 会被 `OnUnbind` 的 stale 判定忽略（否则会把仍在线的权威会话打成离线——详见 [50-游戏服/03](../50-游戏服/03-会话管理与顶号踢人.md)）。

## 3. 账号封禁拦截（同提交的另一半）

`2e28e12` 同时补了登录服的账号状态校验：`account.status` 四态（正常/冻结/注销/未知）全部 **fail-closed**——未知状态按拒绝处理。封禁两步生效：拒新会话（登录时拦截）+ 踢旧会话（走 [70-07](07-封禁与GM踢人链路.md) 的踢人链路）。细节见 [30-登录服/02](../30-登录服/02-账号体系与封禁.md)。

## 4. 验证

- 登出：协议往返、作废失败回 1005、无 revoker 不 panic、断连后 Actor 下线落库；
- 顶号：同节点踢旧、跨节点接管（fake presence + 远程投递替身）、`SetOnline` 失败路径、stale UNBIND 不影响权威会话；
- 变异验证：把 `notify` 挪到 `SetOnline` 之后（旧节点晚一步收到通知，presence 已切换——测试断言「接管后旧会话被踢」立即失败）、去掉 stale 判定（旧 UNBIND 把新会话打成离线，被抓）。

## 5. 经验沉淀

1. **「拒绝」是产品没想清楚的信号**。跨节点顶号拒绝新连接，本质是把技术限制（单进程 Actor）暴露成产品异常；正确的做法是补技术能力（跨节点投递），让产品语义成立。
2. **顺序即正确性**。登出的「先作废再回包再断连」、顶号的「presence 先切换再踢旧」，都不是风格问题，是写反了就出数据问题的硬约束——所以要写进注释，并且用测试钉死。
3. **两条路径共享一套副作用**。同节点踢人与跨节点踢人最终都收敛到 `kickSession`，避免「各自正确」的两份实现慢慢漂移。
