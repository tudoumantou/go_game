# 模块开发约定

> 这份文档只回答一件事：**新增一个玩法时，代码该写在哪、不该写在哪。**
> 框架层的设计理由见 `docs/缓存架构设计.md`，这里只给可执行的规则。

## 1. 先选形态：有没有内存态

| | 有内存态（大多数玩法） | 无内存态（社交/内容类） |
|---|---|---|
| 底座 | `module.Define[Data]` | `module.Thin` |
| 数据在哪 | 玩家快照 `Ext[stateKey]` | 独立表，每次现查现写 |
| 落库 | 随快照 CAS 提交，异步合批 | 请求内直接写库（事务） |
| 快照守卫 | `Guard(module.RequireCache)` | 无（不参与 CAS） |
| 例子 | 签到 / 商店 / 技能 / 装备 | 邮件 / 聊天 / 好友 / 队伍 / 公会 |

判据一句话：**数据是不是「这个玩家的一份」？** 是 → 内存态；是「一对多」或「跨玩家共享」→ 独立表。

```bash
# 有内存态：表要有 @flat:<模块名>，主键必须是 player_id
make new-module NAME=dailyawd MSGS=DailyAwdInfoReq,DailyAwdClaimReq TABLE=player_daily_awd

# 无内存态：独立表，走 Thin + store
make new-module NAME=mailbox MSGS=MailboxListReq:MailboxListResp STORE=mail
```

## 2. 文件分工

| 文件 | 只放 | 禁止出现 |
|---|---|---|
| `module.go` | stateKey、Define/New、路由注册 | 任何业务判断 |
| `types.go` | 状态结构、`newData`、`validate` | 取数逻辑、外部调用 |
| `handler.go` | 业务流：取状态 → 判规则 → 调 Repo/store → 回包 | SQL、`*db.DB`、缓存 key 拼装、长循环 |
| `store.go` | 表访问（只调 gendb 生成的函数） | 业务规则、错误码 |
| `persist_gen.go` | 生成物，不手改 | —— |

`handler.go` 是唯一需要天天打开的文件，它应该**全是业务**。如果一个 handler 超过 60 行，通常是里面混了本该下沉的东西。

这条规则不靠自觉：`.golangci.yml` 的 `depguard` 已经禁止 `**/module/*/handler.go`
import `database/sql` / `pkg/db` / `pkg/model` / `pkg/writebehind`。写错了是
**CI 红**，不是 review 时说一句。参考实现见 `internal/game/module/mail/`。

## 3. handler 的硬规则

1. **错误分支一行**：`return c.FailCode(resp, errcode.ErrXxx)`，不写 `resp.Code = int32(...)` 再 `return nil`。
2. **服务端真故障用 `c.Fail(resp, err)`**：它记 Warn 日志并带 error；业务拒绝（满包/已领取/参数非法）用 `FailCode`，不要污染告警。
3. **顺序即正确性**：先预检（不改状态）→ 再扣费 → 最后发货。反过来必然出现「钱扣了货没到」。
4. **幂等键先于副作用**：`c.State.HasBiz(key)` 要在真正发货前判断，否则重复请求会重复发奖。
5. **不要在 handler 里 `context.Background()`**：请求该用的 ctx 就是 `c.Ctx`；查询超时已由 DSN 层兜底（`pkg/db` 注入 `readTimeout`）。

## 4. SQL 从哪来

按优先级三档，**不许跳档**：

1. **`tools/gendb` 生成**（首选）。schema 表前加注解即可：
   `@findby` / `@listby` / `@listin` / `@lockby` / `@locklistby` / `@deleteby` / `@countby` / `@update` / `@updateby`。
   列名在生成期校验，拼错直接失败。
2. **`pkg/flush` 构建器**（合批写）。`BuildBatchUpsert` / `BuildBatchDeleteWhere`。
3. **手写 SQL**（例外）。只允许出现在 `store.go` / `pkg` 层，且必须：
   - 是生成器表达不了的只读查询（JOIN / EXISTS / 聚合）；
   - 登记进 `docs/功能实现状态.md` 的「手写 SQL 例外清单」；
   - 有 sqlmock 钉住语句与参数。

判断标准：**业务函数里出现 SQL 字符串 = 违规**，无论它多简单。

## 5. 跨玩家读别人数据

- **只读**：`c.Peers.View(ctx, playerID)` / `ViewMany` —— Redis 快照优先（比库新），miss 回落 MySQL，不回填，只给展示字段。
- **要看别人的背包/邮件明细**：不提供。需要展示就定义自己的只读视图。
- **要改别人的状态**：只能 `Peers.Send` 投消息给对方 Actor。直读别人内存是数据竞争，Actor 的串行保证会当场失效。
- **改完是异步的**：先回「已发起」，结果由服务端推送。这是隔离的代价，不是缺陷。

## 6. 新增功能的标准流程

```bash
# 0) 先想清楚：有内存态还是独立表（见 §1）
# 1) schema 加表（独立表还要加 @findby 等注解）
vim sql/schema/game.sql
# 2) 生成 model
make gen-db
# 3) 生成模块骨架
make new-module NAME=xxx MSGS=XxxListReq,XxxClaimReq TABLE=player_xxx
# 4) proto 加 message 与 // @msg
vim api/proto/game/v1/game.proto
# 5) 全量生成（codec / msgid / gamedata）
make gen
# 6) 写业务：只改 handler.go（必要时 types.go / store.go）
# 7) 注册
vim internal/game/server_start.go   # s.modules.Register(xxx.M)
# 8) 验收
go build ./... && go test ./internal/game/module/xxx/
```

## 7. 常见错误

| 症状 | 原因 |
|---|---|
| `make gen` 报 `undefined: model.XxxFlat` | schema 里该表没有 `-- @flat:<模块名>`，或模块名与 stateKey 不一致 |
| 表建好了但 `ListXxxByPlayer` 不存在 | 表没有 `player_id` 列（gendb 只给有该列的表生成按玩家查询） |
| 落库后字段是零值 | `@codec` 的 `db` tag 写错列名，或列名在 schema 里不存在（生成期会拦） |
| 玩家重复登录数据错乱 | 模块自己持了跨请求状态（模块实例是全局单例，状态必须放 Data） |
| 改了代码但线上没生效 | 忘了 `make gen`，或改的是 `persist_gen.go`（生成物会被覆盖） |
