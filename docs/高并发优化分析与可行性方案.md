# 高并发优化分析与可行性方案

## 1. 当前能承诺什么

本项目有分片 Actor、共享 gRPC 连接、增量背包写库、并行预加载、Kafka 和指标代码。这说明具备可分析的机制，不等于已经证明十万在线或支付级可靠性。本文没有进行容量压测；所有吞吐目标都需要固定硬件、数据规模和负载来测。

## 2. 先把正确性纳入性能目标

| 优先级 | 代码证据 | 风险 | 建议验证与改造 |
|---|---|---|---|
| P0 | mailbox.push 满时丢旧 | 新消息返回成功，旧保存/奖励已丢 | 控制/经济消息不可丢；拒绝新投递或持久排队 |
| P0 | persistPlayer 忽略 Send 错误并返回 nil | 落库成功率指标与 SQL 提交脱节 | SaveAck 带提交结果，失败回脏 |
| 回归 | preload 替换 State 后已重绑 hook | 新加载路径可能漏装回调 | 保留在线修改触发 dirty 的回归用例 |
| P0 | cmd main 对 ctx.Err 直接 os.Exit | 清理路径不可达 | 正常取消走 Shutdown，配合排空测试 |
| P0 | MQ 死信错误被忽略 | 未持久转交仍提交 offset | DLQ 确认成功后提交，否则保留重试 |
| P1 | Flusher.FlushAll 单次只取一批 | 停服剩余 dirty | 截止时间内循环至空并确认 SQL 完成 |
| P1 | onBind / onSave 同步 SQL | 同片玩家受慢库影响 | I/O 线程池 + 版本化快照 + 完成消息 |
| P1 | Gateway.Send 同步写 | 慢客户端阻塞下行来源 | 单写者、有界字节预算与超时断开 |

这些是按源码推导的风险点。改造时先复现，再修改，不能为了吞吐忽略已经接收的经济操作。

## 3. Actor 调度热点

当前分片循环扫描 allCells 并分配切片；空闲时使用 100ms ticker 等待，新消息没有专门唤醒机制。扫描成本与 Actor 总量相关，空闲角色多时可能花大量时间寻找工作。

`processed` 预算在一轮整个分片中共享，当前代码不是每个 Actor 都获得独立 100 条配额。map 遍历顺序又不是固定公平队列。优化可采用 ready 队列、每 Actor 配额、去重唤醒标记和持续可运行角色的轮转，但需要处理终止与发送的并发安全。

验收：相同分片内一个热玩家与大量冷玩家并存，冷玩家 P99 不持续恶化；空闲时 CPU 应随可运行 Actor 数量下降，而非随总 Actor 数量线性扫描。

## 4. 不要把阻塞 I/O 随便丢给 goroutine

把 SQL 放到后台可以解除分片等待，但若 goroutine 同时改 State，就破坏串行所有权。建议流程：

```text
Actor 校验并取快照/版本
  → 有界 I/O worker 执行 SQL
  → 完成消息回原 Actor
  → Actor 检查版本与提交结果
  → 更新状态 / 清脏 / 回复
```

保存中又发生新修改时，成功确认只能清到本次保存的版本，不能清掉后来的 dirty。事务失败必须可重试；排队容量满需要明确向调用方返回忙或延迟，不能无限创建 goroutine。

## 5. 数据库优化顺序

先看 sql.DB.Stats 的 WaitCount、WaitDuration，再看慢查询、索引和事务长度，最后才考虑增大连接池。N 个并发登录每个做五查询，瞬时连接需求可能约为 5N，池外还有落库和玩法事务。

当前增量背包通过唯一键 `(player_id,item_id)` 支持 UPSERT，比全量删除重插更节省写入。但“表注释分片键 %512”并没有在 Repo 中自动产生 512 张实体表；当前 SQL 多使用固定表名，不能按已完成分库分表估算容量。

Flusher 当前按分钟边界排程，interval/stagger 的配置实际影响要逐项核对。批量上限还要兼顾 SQL 字节数、占锁时间和 max_allowed_packet，不能只看行数。

## 6. 网络与内存预算

近似估算：`总内存 = 连接数×连接状态 + Actor数×状态 + 各类队列容量×平均元素大小 + 配置/运行时/索引`。channel 中存指针仍会保活其引用对象；小切片引用大数组可能让整块缓存无法回收。

gRPC 的 TCP 连接复用降低连接数量，但当前每会话仍有独立 stream、接收循环与映射，不能把 10 万 stream 当作零开销。发送队列应同时限制条数与总字节数。

## 7. Redis 与 Kafka 优化

Redis 批量读取可减少 RTT，但不能把需要原子性的一组规则拆成 pipeline 后宣称等同事务。在线状态 TTL、心跳和掉线清理要共同设计。

Kafka 要监测按 topic/partition 的 lag、重试、死信与业务耗时；增加 partition 会改变键的分配，要求顺序的同玩家事件必须考虑迁移窗口。扩大消费者数不解决“同一个玩家的副作用如何串行”的问题。

## 8. 压测必须分层

```bash
# 先测纯组件，不连接正式数据。
go test ./pkg/actor ./pkg/codec ./pkg/flush -bench . -benchmem
# 连接测试只证明接入容量，不代表玩法吞吐。
go run ./tools/loadtest -mode conn -n 1000 -hold 30s
# 业务冒烟会创建游客和角色，用本地开发环境。
go run ./tools/loadtest -mode smoke -devices 10
```

记录：CPU/核数、内存、Go 版本、镜像版本、连接数、活跃率、消息大小、DB 数据量、P50/P95/P99、错误和丢弃。只测“建连成功”不能证明创角/背包/战斗达到同等容量。

## 9. 交付顺序

第一轮：补提交确认、不可丢经济消息与停服闭环，并回归已修正的 dirtyHook。第二轮：修正调度公平性和唤醒，控制 I/O 并发。第三轮：按 profile 证据降低分配、合并 SQL、调整池。第四轮：才讨论节点迁移、分库分表和更多跨服实例。

每轮都要求同一负载下延迟和错误没有倒退，同时对断线、慢库、重复消息和中途停止做回归。[第 14 章](开发流程/14-测试监控与优雅停服.md)提供验证清单。
