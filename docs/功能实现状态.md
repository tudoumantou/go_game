## 6. 2026-10-19 之后的架构变更（v3.5 → v3.9）

本节不是新功能，是**基座重构**——功能表里的「已实现」不变，但它们的实现方式变了。
逐项详见 [缓存架构设计](缓存架构设计.md) 与 [服务器框架设计文档](game_study-服务器框架设计文档.md) 的演进记录。

| 版本 | 变更 | 对「怎么看这份表」的影响 |
|---|---|---|
| v3.5 | **内存权威**：业务先改 Actor 内存，再同步 Redis 副本；落库由 flusher 从内存走 | 「Redis 权威」的旧描述作废；`Store.Sync` 不是提交语义 |
| v3.6 | **归属索引**（`by_owner:{table}` ZSET）+ `idtab.mappings` | 一对多功能不必各写一条 `WHERE owner = ?` |
| v3.7 | **落库通道收敛**：删 Redis 脏队列 → Worker → MySQL 整条通道（`cmd/flusher` 一并删除） | 部署单元少一个；`pkg/writebehind` 只剩副本读写 + Persister |

### 手写 SQL 例外清单（v3.13）

原则：`internal/game` 的写路径不再出现 SQL 字符串；写语句一律来自 `pkg/model` 的生成函数或 `pkg/flush` 的合批构建器。生成器表达不了的**只读**查询保留手写，逐条登记如下（新增必须在此登记 + 有 sqlmock 测试）：

| 位置 | 语句形态 | 为什么生成器覆盖不了 |
|---|---|---|
| `mail.Repo.ListByPlayer` | `JOIN mail_attachment` + `EXISTS` 子查询 | 列表用 EXISTS 一次带出「有无附件」，避免 N+1 |
| `mail.Repo.HasAttachments` | `SELECT DISTINCT ... WHERE id IN (...)` | IN 的占位符个数运行时决定 |
| `chat.Repo.ListRecent` | `ORDER BY id DESC LIMIT ?` | 会话维度 + 动态 limit |
| `friend.Repo.List` | 两条 `JOIN player` 取名 | 跨表取昵称/等级，不是单表 CRUD |
| `friend.Repo.Blocks` | `friend_block JOIN player` | 黑名单列表要带昵称/等级，同 List 的理由 |
| `team.Repo.FindByPlayer` / `Leave` | `team JOIN team_member` | 用成员行反查队伍，跨表定位 |
| `team.Repo.Members` | 三表 `JOIN` + `COALESCE` | 联 player 取名，缺行降级为空串 |
| `guild.Repo.FindByPlayer` | `guild JOIN guild_member` | 同上 |
| `player.saveDirtyItems` | `pkg/flush` 的 `BuildBatchUpsert` / `BuildBatchDeleteWhere` | 合批语句由通用构建器动态拼装，列名取 `model.Col*` 常量 |
