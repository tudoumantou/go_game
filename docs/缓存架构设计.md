# 缓存架构设计

> 一句话：**两条写入路径**（业务内存优先、充值数据库优先）+ **两张 Redis 表**（数据表 + ZSET 索引表）+ **一套手写的映射声明**。

---

## 1. 两条写入路径（除此之外没有第三种）

### 1.1 业务数据：内存优先（Write-Behind）

签到、背包、任务、伙伴、装备……「丢了玩家要骂、但不用赔钱」的数据走这条。

```
① 内存先增加（Actor 内，权威）
      │
② 数据表写一份          HSET  e:{table}:{id}  {fields}     ← 尽力而为，失败只告警
      │
③ 索引表登记（仅新增/删除时）
      新增  ZADD  by_owner:{table}  {归属者ID}  {实体ID}
      删除  ZREM  by_owner:{table}  {实体ID}
      │
④ 标脏                  flusher.MarkDirty(playerID) → 进程内 10 分片队列
      │
⑤ 定时落库              分片到点 → SaveMsg → Actor 用**内存**写 MySQL
                        （只写变过的表：见下方「落库只写变过的表」）
```

注意 ⑤ 的数据源是 **Actor 内存**，不是 Redis：副本可能落后，拿它落库等于
写回旧值。落库节奏由 `flush.interval`（默认 60s）+ 10 分片错峰决定。

三条铁律：

| # | 铁律 | 违反的后果 |
|---|---|---|
| 1 | **内存先改，再动 Redis** | 反过来会让 Redis 出现内存里没有的数据 |
| 2 | **Redis 写失败不回滚内存** | 副本落后由加载时的版本校验兜住；回滚等于把已生效的操作退掉 |
| 3 | **落库数据源是内存，不是 Redis** | Redis 落后时用副本落库会写回旧值 |

**落库只写「变过的表」**：`State` 记录模块级脏标记（`SetExt` 自动置位），
`repo.Save` 只把这些模块交给 `PersistDirtyModules`。玩家多数轮次只动了金币/
道具，9 张 Ext 表一张都不写——它们本来就是上一次落库后的样子，再 UPSERT
一遍纯属浪费（量随在线人数线性增长）。

| 一轮改了什么 | 落库语句数 |
|---|---|
| 只改金币/等级（最常见的轮次） | 2（player + attr） |
| 改了背包 | 3~4（+ 合批 UPSERT/DELETE items） |
| 改了某个玩法状态 | +1（只写那一张 Ext 表） |

脏标记只在**事务提交成功后**清除（`ClearDirtyModules`）；失败保留，下一轮
重试同一批模块——与 `ClearItemsDirty` 同一套时序。

### 1.2 充值：数据库优先（Write-Through）

充值、交易、订单——**丢了要赔钱**的数据走这条。

```
① 先写数据库（事务提交）
      │  资产 + 幂等键（applied_grants）同一事务
      │
② 调用充值接口（不是裸写缓存）
      │  发货 → 触发礼包购买校验 → 触发充值活动计数 → 触发排行榜/成就
      │
③ 接口内部：写数据表 + 更新内存
      │
④ 回执（此时钱已经在库里）
```

| | 业务（内存优先） | 充值（数据库优先） |
|---|---|---|
| 谁是权威 | 内存 | MySQL |
| 回执时机 | Redis 写完（失败也回） | **MySQL 提交之后** |
| 后续逻辑 | 无（或异步事件） | **必须串行触发**：礼包、活动、成就 |
| 落地代码 | `Store.Sync` + `flusher` | `Repository.SaveForce` + `GrantItemsMsg{Sync:true}` |

**为什么充值不能直接写缓存**：写缓存只解决「可见」，而充值要按顺序触发一串业务动作（买礼包可能解锁活动资格，活动计数可能触发返利）。这些必须在同一个入口里串行执行，不能靠缓存事件驱动。

### 1.3 判定标准（一条）

> **这笔数据丢了，是要赔钱/回滚订单，还是让玩家重新操作一次？**
> 赔钱 → 数据库优先；重做 → 内存优先。

## 2. Redis 的两张表

| 表 | key | 类型 | 内容 | 落库 |
|---|---|---|---|---|
| **数据表** | `e:{table}:{id}` | Hash | 一行记录的字段快照 | ✅ 会 |
| **索引表** | `by_owner:{table}` | ZSET | score = 归属者 id，member = 实体 id | ❌ 索引 |

伙伴的例子：

```
e:partner:2001          Hash   {level: 5, exp: 1200, ...}     ← 数据
by_owner:partner         ZSET
  ├─ member 2001  score 10086
  ├─ member 2002  score 10086
  └─ member 2003  score 10087
```

### 2.1 为什么一个 ZSET 就够

ZSET 的「score + member」正好能表达「实体属于谁」，一个结构同时承担三件事：

| 需求 | 命令 | 复杂度 |
|---|---|---|
| 这个伙伴存在吗 | `ZSCORE by_owner:partner 2001` → 非 nil 即存在 | **O(1)** |
| 这个角色有哪些伙伴 | `ZRANGEBYSCORE by_owner:partner 10086 10086` | O(log N + M) |
| 这个伙伴属于谁 | `ZSCORE by_owner:partner 2001` → `"10086"` | **O(1)** |
| 新增 | `ZADD by_owner:partner 10086 2001` | O(log N) |
| 删除 | `ZREM by_owner:partner 2001` | O(log N) |
| 全服总数 | `ZCARD by_owner:partner` | O(1) |
| 某角色的数量 | `ZCOUNT by_owner:partner 10086 10086` | O(log N) |

第三行是白送的：**`ZSCORE` 返回的就是归属者 id**，删一个实体不需要先知道它属于谁。

### 2.2 为什么不需要单独的「id 映射表」

如果用 Set 存存在性（`SADD ids:partner 2001`）+ 另一个 Set 存列表（`SADD by_owner:partner:10086 2001`），就会有**两张索引、三份写**：

```
新增：HSET 数据 + SADD ids + SADD by_role          ← 3 份
删除：DEL 数据 + SREM ids + SREM by_role           ← 3 份，且要同时改两个 Set
```

而 ZSET 的 member 就是实体 id，`ZSCORE` 的语义与 `SISMEMBER` 完全等价，于是：

```
新增：HSET 数据 + ZADD 索引                        ← 2 份
删除：DEL 数据 + ZREM 索引                         ← 2 份，一次操作消掉「存在性 + 列表归属」
```

**从你的原设计（id 映射 + role 映射 + 数据）的 3 份，降到 2 份。**

### 2.3 为什么不再需要 Pos

原设计里 `Pos` 是「role_id 在映射表里的位置」，用来让 field 能被直接定位（避免 `HSCAN MATCH` 全表扫）。

ZSET 用 score 天然解决了定位问题——`ZRANGEBYSCORE key roleID roleID` 直接按分数区间取，`O(log N + M)`，不需要任何位置编号，也不需要「Pos 必须能由 role_id 算出」这个约束。

### 2.4 「存在」的语义变了，需注意

新结构下，「存在」= **在某人的名下**：

| 场景 | 判定 |
|---|---|
| 正常伙伴（有归属） | 存在 ✅ |
| 孤儿行（`role_id` 为空/NULL） | `ZSCORE` 返回 nil → **判不存在** |

这通常更对：**不属于任何角色的伙伴，对玩家来说就是不存在**。孤儿数据属于脏数据，由 `CleanOrphans` 清理。

若业务上确实有「未分配」状态（抽到但还没上场），给 score `0` 占位——`ZRANGEBYSCORE 0 0` 能单独捞出来，也不会污染任何角色的列表。

### 2.5 一个实体属于多个归属者时

ZSET 的 member 只能有一个 score。所以：

| 场景 | member 形态 |
|---|---|
| 一伙伴一角色（当前） | `{partner_id}` ✅ |
| 一实体多归属（如道具同时属于角色和仓库） | `{owner_type}:{owner_id}:{实体id}` 复合 |

复合 member 的代价是删除时必须知道归属者（拿不到就 `ZSCAN` 找）。所以**能用单 member 就别用复合**。

## 3. 启动加载

```
① 全量拉 (id, 归属者) → 索引表
      SELECT id, role_id FROM partner
        → ZADD by_owner:partner {role_id} {id}
      （分页拉；构建完用临时 key + RENAME 原子切换，再置 ready）

② 数据表按需建（懒加载）
      启动时只建索引，不搬数据——数据在第一次真正读到时才 HGETALL / 回源

③ 例外：全量预载的表（公会、排行榜）
      启动时连整行一起搬：SELECT * FROM guild → HSET e:guild:{id}
      这类表不参与懒加载（数据已在 Redis）
```

**为什么启动只建索引不搬数据**：100 万玩家的伙伴数据全搬进 Redis 会吃掉几个 G。索引本身很轻（一个 ZSET 的 member 约 40–60 字节），数据按需加载即可。

### 3.1 映射必须手写声明

「用哪个字段做归属者」不能自动推断——同一个 `role_id` 列，在伙伴表里是「我的伙伴」，在邮件表里是「我的邮件」，加载时机也不同。

声明在游戏服配置的 `idtab.mappings` 段（`configs/game/game-*.yaml`）：

```yaml
idtab:
  mappings:
    - table: mail               # 邮件：玩家名下多封（本项目已接入）
      by: player_id             # 归属者字段 → ZSET 的 score
      key: id                   # 实体 id → ZSET 的 member（必填：构建分页游标）

    # 下面这项是「整表预热」的形态示例，**当前项目没有这种表**：
    #   - table: guild            # 启动全量搬进 Redis（不懒加载）
    #     key: id                 # preload_all 也要 key（预热分页用）
    #     preload_all: true       # by 可省：没有归属列就只搬数据、不建索引
```

> ⚠️ 当前 `player_partner` / `player_equip` 都是「`player_id` 单行 JSON」——
> 一人多件存在一个 TEXT 列里，**不是一对多表**，配了只会白建一份索引。

| 字段 | 含义 | 不填的后果 |
|---|---|---|
| `key` | 实体 id 列（主键） | 构建/预热没有分页游标，启动校验直接报错 |
| `by` | 归属者字段（`preload_all` 可省） | 非 preload_all 不填 → 启动校验报错；模块 `Expand` 取不到列表 |
| `preload_all` | 启动时是否连数据一起搬 | 该懒加载的被预载（内存浪费）或反之（每次访问打库） |

启动校验会查错+查重：配错的后果是「功能列表为空」且不报错，必须让配置错误第一秒就炸。

> **v3.11 移除了 `load_on_login`**。它原本表示「登录时按角色展开」，v3.9 删掉
> 登录展开入口后就变成「写了不生效」的死配置，留着只会误导。现在「什么时候
> 展开」由模块自己决定（`Expand` 的调用点），配置只管「索引怎么建」。

### 3.2 只有「一对多」的表需要配

| 形态 | 例子 | 需要索引表吗 |
|---|---|---|
| **一对一**（一角色一行） | 签到、属性、任务进度 | ❌ 按 `player_id` 一次查询就够 |
| **一对多**（一角色 N 行） | 伙伴、装备、邮件、好友 | ✅ 必须有 |

给签到配 `by` 是纯浪费——白多一份索引要维护。`idtab.mappings` 里只应该出现真的「一个归属者多行」的表。

## 4. 读取路径

### 4.1 单条读（按 id）

```
① 索引表：ZSCORE by_owner:{table} {id}
      nil → 直接返回「不存在」（不打库、不查数据表）

② 数据表：HGETALL e:{table}:{id}
      命中 → 反序列化进内存

③ MySQL：SELECT * FROM {table} WHERE id = ?
      回填数据表，失败不影响本次返回

④ 进内存（Actor 持有）
```

落地：`IDTable.LoadEntity`（`pkg/cache/idtable.go`）。

### 4.2 按归属者批量读（被访问时）

```
① 索引表：ZRANGEBYSCORE by_owner:{table} {roleID} {roleID}  → [2001, 2002, 2003]
      索引未 ready（启动构建中）→ 回落 MySQL：SELECT key FROM {table} WHERE by = ?
② 数据表：pipeline HGETALL e:{table}:{id} × N（一次往返）
③ 未命中的 → 一条 SELECT * WHERE key IN (...) 批量捞 → pipeline HSET 回填
④ 返回给调用方（模块自己决定放内存、当场用完丢、还是缓存起来）
```

落地：`OwnerIndex.Expand`（`pkg/cache/owner_index.go`）= `Members` + `LoadBatch` + 自愈。

模块接入（只有这一条路，框架不猜格式）：

```go
rows, removed, err := m.index.Expand(ctx, playerID)
if err != nil {
    return m.repo.ListByPlayer(ctx, playerID, limit)  // 回落 SQL
}
for _, r := range rows { /* 列名 → 字符串值，自己解析 */ }
```

配置：`idtab.mappings` 里给这张表配 `by`/`key` 即可。

> **v3.9 删除「登录展开」入口**。v3.6 曾把展开结果挂到 `Actor.prefetch`，
> 由模块 `OnLogin` 经 `Context.Prefetch.OwnerRows(table)` 读。删掉的原因：
>
> 1. **没有消费者**——一个都没有；
> 2. **与当前模块形态不匹配**：有内存态的玩法（签到/装备/伙伴/任务/活动）全是
>    「`player_id` 单行 JSON」，不需要按归属者展开多行；而一对多的模块
>    （邮件/好友/队伍/公会）都无内存态、直查 DB。给后者做登录展开，数据挂在
>    Actor 上只对「登录那一刻」有效，之后新邮件/新好友不会反映——是**错的**；
> 3. 保留的代价是读代码的人以为登录预取在生效。
>
> 真出现「有内存态 + 一对多」的功能时，在它的 `OnLogin` 里调一次
> `OwnerIndex.Expand` 即可（5 行），不需要框架先替它预取。

### 4.3 自愈：读的时候顺手修索引

```
ZRANGEBYSCORE 拿到 id → HGETALL 为空 → 回源 MySQL 也为空
  → 说明索引残留（数据已删但 ZREM 没成功） → 顺手 ZREM 掉
```

落地：`LoadBatch` 把「两处都没有」的 id 收进 `missing` 返回值，`Expand`
调 `Index.Remove` 摘掉并把 removed 报给调用方（记日志用）；清理失败不报错，
定时对账还会兜底。自愈只在 `Expand` 里做一处。

这是「增删两份写不原子」的兜底。成本几乎为零（异常路径才触发），但能防止索引越积越脏。

## 5. 增删改要动什么

以 `mail` 为例（真实接入）：

| 操作 | 数据表 | 索引 | 落库 |
|---|---|---|---|
| **新增邮件** | 缓存留空（懒加载） | `ZADD by_owner:mail {player_id} {mail_id}` | 模块直写 MySQL（先落库再 ZADD） |
| **读取列表** | `Expand` 回填 `e:mail:{id}` | 不动 | — |
| **转移归属** | 不动 | `ZADD` 同 member 新 score（自动覆盖） | — |
| **删除邮件** | `DEL e:mail:{id}` | `ZREM by_owner:mail {mail_id}`（不需知归属者） | 模块直写 MySQL |

有 Actor 内存态的模块（当前无一对多形态）则是另一套：改内存 → `Sync` 写数据表 →
`MarkDirty` → flusher 落库，索引同步在同一个业务分支里 `AddEntity`/`RemoveEntity`。
两者的共同点只有一条：**索引永远跟着数据的真实变更走，不单独维护**。

**新增/删除 = 2 份数据、2 张表**；修改 = 1 份；转移归属 = 1 份（`ZADD` 覆盖 score 本身就是原子操作）。

### 5.1 两个容易漏的点

| 漏什么 | 现象 |
|---|---|
| 只删数据表 | 索引说「存在」、数据表空 → 懒加载打库发现没有 → 偶发加载失败（靠 4.3 自愈兜） |
| 只删索引表 | 数据表变成孤儿（没人引用），占内存直到 `CleanOrphans` |

第二种危害小（孤儿数据不影响业务），第一种要立刻能自愈——所以 4.3 那条路径必须写。

## 6. 现有实现对照

| 能力 | 现状 | 位置 |
|---|---|---|
| 数据表 `e:{table}:{id}` | ✅ Hash + 回源 + 孤儿清理 | `pkg/cache/idtable.go`（`LoadEntity`/`CleanOrphans`） |
| 索引表 ZSET `by_owner:{table}` | ✅ | `pkg/cache/index.go`（纯 Redis 操作）+ `owner_index.go`（构建/回源） |
| 启动全量建索引 | ✅ keyset 分页 + 临时 key + RENAME + ready | `OwnerIndex.BuildOne`（`server.go` `buildOwnerIndexes`） |
| 索引未就绪/Redis 故障降级 | ✅ 回落 MySQL（不返回空列表冒充「没有」） | `OwnerIndex.Members` |
| 批量加载（pipeline + 一条 IN） | ✅ | `OwnerIndex.LoadBatch` |
| 登录按归属展开 | ❌ v3.9 删除（无消费者，且与模块形态不匹配） | 见 §4.2 末尾的说明 |
| 读时自愈（4.3） | ✅ | `OwnerIndex.Expand` → `Index.Remove(missing...)` |
| 定时对账（数量不一致→重建） | ✅ 10 分钟 | `OwnerIndex.Reconcile`（`maintainOwnerIndexes`） |
| 全量预载（公会类） | ✅ `preload_all` → 整表搬实体 hash | `IDTable.Preheat` |
| mappings 声明 | ✅ 启动校验查错+查重 | `config.IDTabConfig.Mappings`（`idtab` 段） |
| 运行时增删索引（ZADD/ZREM） | ✅ 有真实调用方（mail 投递 / 删除） | `OwnerIndex.AddEntity`/`RemoveEntity` |
| 按需展开（点开功能才加载） | ✅ 首个消费者：邮件列表 | `mail.listRows` → `OwnerIndex.Expand` |
| 缓存行失效（行还在、字段变了） | ✅ 领取附件后作废该行 | `OwnerIndex.DropEntity` |
| 指标 | ✅ size / ready / 对账不一致 / 构建耗时 | `metrics.OwnerIndex*` |

**第一个真实消费者：邮件（v3.8）**

`mail` 是这套结构唯一形态完全匹配的功能——`player_id` 单一归属、新增/删除只动
自己那一份。接入方式就是四步，其余模块可照抄：

```go
// 1. 组装层注入（server_start.go）——未配 mappings 时 nil，行为与接入前一致
s.mailMod.SetOwnerIndex(s.ownerIdx["mail"])

// 2. 新增：先落库，再登记索引（顺序不能反，构建期只从库里取材）
mailID, err := m.repo.Insert(ctx, mailModel)
if err == nil { m.index.AddEntity(ctx, playerID, mailID) }

// 3. 读取：Expand（索引 → 批量取 → 残留自愈），失败回落 SQL
rows, removed, err := m.index.Expand(ctx, playerID)
if err != nil { return m.repo.ListByPlayer(...) }   // 回落

// 4. 变更（行还在、内容变了）：作废缓存行，下次读回源拿最新值
m.index.DropEntity(ctx, mailID)
//    删除（行没了）：摘索引 + 作废缓存
m.index.RemoveEntity(ctx, mailID); m.index.DropEntity(ctx, mailID)
```

配置（`idtab.mappings`）：

```yaml
mappings:
  - {table: mail, by: player_id, key: id}
```

### 6.1 与早期设计的两处差异（已实现时修正）

1. **key 名**：`by_role:{table}` → `by_owner:{table}`（实现口径，见 `keygen.OwnerIndexKey`）。
   与 `idtab:{table}`（Set，存在性）是两套 key、两套 ready——同一张表可能两个结构都建。
2. **顺序**：`IDTable.LoadEntity`（单条读）保持「先数据表，miss 再查索引」——命中率高时省一次往返；
   登录批量读走「先索引后数据」（`LoadBatch`）——先拿 id 列表才能合批。两种都正确，场景不同。

## 7. 最容易踩的三个坑

| 坑 | 现象 | 原因 |
|---|---|---|
| **漏配 mappings** | 功能列表为空，但库里有数据 | 没配 `by`/`key`，索引没建，`Expand` 只能回落 SQL（慢但不至于错）|
| **member 用了复合键但删除时拿不到归属** | 删不掉，索引残留 | 单 member 能表达就别用复合 |
| **给一对一功能配了 `by_owner`** | 白多一份索引，还多一处可能不一致 | 只有一对多才需要（签到/属性/当前实现的伙伴都是单行 JSON，别配） |

## 8. 与落库通道的关系

**只有数据表会落库**（标脏 → 合批 → MySQL）。索引表是由 `(id, 归属者)` 派生的结构，由「启动构建 + 增删时同步维护 + 读时自愈 + 定时对账」保证与库一致，不走落库通道。

一封新邮件的完整时序（`mail.Deliver`，Kafka 消费路径）：

```
MailMsg 消费
  ├─ INSERT INTO mail (...)                     ← ① 数据（MySQL，模块直写）
  ├─ ZADD by_owner:mail {player_id} {mail_id}   ← ② 索引（不落库）
  └─ （业务无内存态）下次 onList 时 Expand 回填 e:mail:{id}
```

**注意 ② 的顺序**：先落库再 ZADD。索引构建只从库里取材，反过来（先 ZADD 后落库）
会让「启动构建期间新增的行」漏进索引；而「先落库」时构建必然能扫到它。

> 现状注记（v3.9）：邮件是唯一的真实消费者，走**按需展开**（点开邮箱才
> `Expand`）。曾有的「登录展开」入口（`Prefetch.OwnerRows`）已整条删除——
> 零消费者，且与当前模块形态不匹配（见 §4.2）。现在的形态是：
>
> - 启动构建索引 → 增量维护（Add/Remove）→ 对账重建，这条链一直在跑；
> - 读取只有一条路：谁需要，谁在用到的时候调 `Expand`。

### 8.1 SQL 从哪来（v3.13）

**业务代码里不再出现 SQL 字符串**，也不再持有数据库驱动。写语句只有两个来源：

| 来源 | 适用 | 位置 |
|---|---|---|
| `tools/gendb` 从 `sql/schema` 生成 | 规则形态：单行 CRUD、按列查/删/计数、行锁、部分列更新 | `pkg/model/*_gen.go` |
| `pkg/flush` 的合批构建器 | 多行合批 UPSERT / DELETE（列名取 `model.Col*` 常量） | `pkg/flush/batch.go` |

需要新语句时，在 `sql/schema/game.sql` 的表前加注解，而不是在手写 SQL：

```sql
-- @findby:account_id                → FindPlayerByAccountId
-- @update:progress level,exp,coin   → UpdatePlayerProgressByPK（只 SET 声明列）
-- @lockby:id                        → LockPlayerById（SELECT ... FOR UPDATE）
-- @deleteby:id,player_id            → DeleteMailByIdPlayerId（复合条件删除）
-- @countby:player_id,status         → CountMailByPlayerIdStatus
```

注解里的列名在**生成期**校验：拼错直接 `gendb` 失败，而不是运行时 1054——
这是「schema 是唯一真相」的落点。另一个收益是可空列：可空 `VARCHAR` 现在映射
`sql.NullString`（与可空时间列映射 `sql.NullTime` 同一条规则），零值写 NULL，
`mail.biz_id` 这类「可空 + 唯一键」的列不再需要用空串硬扛（历史 1062 的根因）。

生成器覆盖不了的**只读**查询（JOIN / 聚合）保留手写，但必须满足两条：
集中在仓储层、登记在 `docs/功能实现状态.md` 的「手写 SQL 例外清单」并配 sqlmock 测试。

分层边界因此变成：

```
service / module   ← 业务规则，零 SQL、零驱动
player.Repository  ← 玩家落库（生成函数 + flush 构建器）
module/xxx.Repo    ← 该模块的表访问（生成函数 + 少量登记过的 JOIN 读）
```

### 8.2 快照必须完整：同步落库后「重建」而不是只删（v3.13.1）

A 类同步落库（充值）成功后，库里的版本已推进，Redis 副本必须失效。早先的做法是
直接 `Drop`，靠「下一次提交」重建——但提交只写 `DirtyFields()`，于是 hash 会以
**残缺形态**重建：只有这次变过的字段（比如 `profile`），没有 `items`。

- 对本人加载无害：`LoadCached` 会比对库版本，发现副本落后就重建。
- 对跨玩家只读有害：读到的是**空背包**，而不是可回源的 miss——「他真的没道具」
  和「快照缺字段」无法区分。

现在的做法是 `Drop` + `Seed`（`Actor.resyncCache`）：用内存整份重建，版本取刚推进
的库版本。代价只有一次 HSET 批量，换来「副本要么不存在、要么完整」这条不变量。

### 8.3 跨玩家只读（PeerReader）

展示类需求（好友列表显示对方等级、公会成员显示名字）走 `module.Context.Peers`：

```go
v, _ := c.Peers.View(c.Ctx, targetID)        // nil = 玩家不存在
vs, _ := c.Peers.ViewMany(c.Ctx, friendIDs)  // 一次 pipeline + 一条 IN
```

| 规则 | 原因 |
|---|---|
| Redis 优先，miss 回落 MySQL | 副本比库新（库是异步落库）；但副本只覆盖「有快照」的玩家 |
| **不回填** | 读一眼就写回会把「浏览资料」变成写放大，还要处理并发 Seed 的版本冲突 |
| 只暴露展示字段 | 「能读」不等于「该读」：不给背包/邮件明细 |
| 批量走 pipeline | 50 个好友逐个 `HGETALL` 就是 50 次 RTT |
| 改别人状态仍须发消息 | 直读别人内存是数据竞争，Actor 串行保证会当场失效 |

## 9. Redis 故障：熔断（快速失败）

### 9.1 为什么需要它

Redis 故障有两种形态，伤害完全不同：

| 形态 | 表现 | 单条命令耗时 |
|---|---|---|
| 进程死了 / 端口不通 | 连接被立即拒绝 | 毫秒级 |
| **网络黑洞（丢包/半开连接）** | 命令发出去没有回应 | **等满超时（默认 5s）** |

第二种才是真问题。一次登录要串行发十几条 Redis 命令，每条等 5s，登录 P99 直接破表；而**所有降级路径本来都是好的**——读回落 MySQL、写只告警——却因为每条命令都在等超时，把降级拖成了不可用。

熔断要解决的就是这一点：故障确认之后，**命令不再发出去**，降级路径立刻生效。

### 9.2 三态状态机

```
       连续失败 ≥ threshold
closed ────────────────────► open
  ▲                            │
  │  探测成功                   │ 冷却 cooldown
  │                            ▼
  └──────────────────────── half_open
        探测失败 ──────────────► open（冷却重新计时）
```

| 状态 | 行为 | 进入条件 |
|---|---|---|
| `closed` | 全部放行，统计连续失败 | 初始 / 探测成功 |
| `open` | **全部拒绝**（返回 `ErrBreakerOpen`，命令不发） | 连续失败达阈值 / 半开探测失败 |
| `half_open` | 只放行 `probes` 个探测 | `open` 持续满 `cooldown` |

三个容易做错的点，实现里都处理了：

1. **`redis.Nil` 不是失败** —— key 不存在是正常业务结果（`EXISTS`/`HGET`），算作故障会让正常业务把熔断器打穿。
2. **`open` 状态下的迟到成功不关闭熔断** —— 那是熔断打开前发出的在途请求，让它关闭会造成「刚打开就关」的抖动。只有 `half_open` 的探测成功才算恢复。
3. **半开名额用 CAS 发放** —— 冷却到期时多个 goroutine 同时醒来，只有一个能把状态推进到 `half_open`，其余继续拒绝，避免「刚到期就被一波流量打穿」。

### 9.3 挂在哪里

**go-redis 的 Hook**（`ProcessHook` / `ProcessPipelineHook`），不是包一层 Client：

- `UniversalClient` 有几十个方法，逐个包一遍既容易漏，又会把 Pipeline/事务的语义搞乱；
- Hook 是库提供的唯一「所有命令都必经过」的切面，`ProcessHook` 返回 error 时库不会执行命令；
- pipeline 整批算一次判定——一次网络往返的成败是整体的，逐条统计会让一次批量失败直接把计数冲过阈值。

### 9.4 各条路径拿到熔断后的行为

| 路径 | 熔断打开时 |
|---|---|
| `IDTable.Exists` | 回落 MySQL（已有降级） |
| `OwnerIndex.Members` | 回落 MySQL（已有降级） |
| `Repository.LoadCached` | 回源 MySQL 重建（已有降级） |
| `Store.Sync`（副本同步） | 只告警，内存权威不受影响 |
| `AcquireLease`（登录令牌） | 登录失败——令牌拿不到就没有写权限，这是正确的拒绝 |

也就是说：**熔断不需要任何业务代码配合**，它只是让既有降级路径从「等 5s 后降级」变成「立刻降级」。

### 9.5 配置与指标

```yaml
redis:
  circuit_breaker:
    threshold: 5      # 连续失败多少次打开；-1 = 关闭
    cooldown: 5s      # 打开后多久进入半开
    probes: 1         # 半开放行的探测数
```

不写这一段 = 默认开启（5 / 5s / 1）。`threshold: -1` 关闭。

| 指标 | 含义 |
|---|---|
| `redis_breaker_state{service}` | 0=closed 1=open 2=half_open |
| `redis_breaker_opened_total{service}` | 打开次数（频繁增长 = 故障在抖动或阈值偏低） |
| `redis_breaker_rejected_total{service}` | 被快速拒绝的命令数（这些请求没发往 Redis） |

告警建议：`state > 0` 持续 1 分钟；`rate(opened_total[10m]) > 3` 说明在反复抖动，该调阈值或查网络。

### 9.6 已知取舍

- **恢复延迟最多一个 `cooldown`**：`open` 期间不主动探测，Redis 恢复了也要等冷却到期。这是用「最多 5s 的额外不可用」换「不把恢复中的 Redis 再打垮」。
- **阈值太低会抖**：间歇性故障（比如丢包率 20%）下 `closed ↔ open` 会反复切换，每次切换都有一次探测往返。`opened_total` 是判断依据。
- **不算半开超时**：探测请求自身如果卡在超时上，会在 `cooldown` 之后才被判定失败。极端情况下恢复被推迟一个 `cooldown + timeout`。

## 10. 落库通道收敛：从两条到一条（v3.7）

### 10.1 删了什么

早期有两条落库通道，靠「Redis 是不是权威」区分：

| 通道 | 数据源 | 组成 | 状态 |
|---|---|---|---|
| **内存 → flusher → MySQL** | Actor 内存 | `pkg/flush` + `SaveMsg` + `repo.Save` | ✅ 唯一保留 |
| Redis 队列 → Worker → MySQL | Redis 快照 | `Store.Commit` + 脏 ZSET + `Worker` + `cmd/flusher` | ❌ 整条删除 |

删除清单（一次性，无残留）：

```
pkg/writebehind/worker.go          整个文件（476 行）
pkg/writebehind/store.go           Commit / Pending / Ack / DropQueue / commitScript / dirtyKey
pkg/writebehind/types.go           Partitions / Partition
cmd/flusher/                       独立落库进程
internal/game/server_start.go      startWritebehind（进程内 worker 启动）
internal/game/server.go            wbWorker 字段与停机排空
pkg/config.FlushConfig             DisableInlineWritebehind
deploy/docker-compose.yaml         flusher 服务
scripts/{build,docker-up,run-all}.sh  对应条目
```

### 10.2 为什么能删

内存权威（v3.5）之后，`Store.Sync` **只写副本、不入队**，而 `Store.Commit`
（唯一往队列写的方法）在改造后**零调用方**。也就是说队列自始至终是空的：

- 进程内 Worker 每 60s 扫一次空队列；
- 独立 `cmd/flusher` 扫同一个空队列，还多一个部署单元、一份 Redis 连接。

留着的唯一价值是「万一有路径误入队不至于永不落库」，但那条路径已经不存在了。

### 10.3 顺带修正的两件事

1. **key 格式简化**：`wb:{player-N}:state:{id}` → `wb:{player-<id>}:state:<id>`。
   hash tag 里原本的 `N = id % 10` 只为「state 与 dirty key 同 slot」服务——
   队列删了，tag 直接用玩家 id 更直观（同玩家的 state/epoch 仍在同 slot，
   `Sync` 的 Lua 多 key 操作不受影响）。**这是一次性数据失效**：升级后
   所有玩家重新冷启动加载一次。
2. **`Drop` 与 `Reset` 合并**：队列在时两者语义不同（Drop 连队列一起清、
   Reset 保留队列只删快照）；队列没了，实现是同一行 `DEL`，合成一个 `Drop`，
   注释里写清两种用途（同步落库后 / 副本落后重建前）。

### 10.4 现在只有一条路

```
内存改 → 标脏 → flusher 分片到点 → SaveMsg → Actor 用内存写 MySQL
                                        └─ 只写变过的表（§1.1）
```

**取舍**：放弃了「跨进程共享落库」的可能——如果将来要让独立进程承担落库，
内存数据必须序列化后传过去，而内存是权威，那个进程的可用性会变成数据正确性
的一部分。当前规模（千人级在线、17 TPS 量级）不需要这个复杂度；真到需要时，
更可能的做法是让 `game` 按玩家分片，而不是把落库拆出去。
