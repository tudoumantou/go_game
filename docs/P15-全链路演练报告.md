# P15 全链路演练报告

> 执行时间：2026-10-18
> 环境：单机 32C / 123GB，五服务 + MySQL/Redis/etcd/Kafka 同机
> 版本：`5e51678` + 本轮修复

本报告记录 P15「全链路演练」的实测结果。演练的目的不是「跑出好看的数字」，而是**在真实进程拓扑下暴露集成测试覆盖不到的问题**——本轮确实暴露了 4 个，其中 2 个会导致线上故障。

---

## 一、压测结果

### 1.1 基线数据

| 场景 | 请求数 | 吞吐 | P50 | P95 | P99 | 失败 |
| --- | --- | --- | --- | --- | --- | --- |
| 登录（HTTP + RSA 握手 + 加密登录） | 1000 | 329/s | 124.35ms | 298.01ms | 400.30ms | 0 |
| 业务消息（混合：背包 50% / 角色 40% / 聊天 10%） | 1000 | 4363/s | 0.16ms | 0.49ms | 101.91ms | 0 |
| 业务消息（只读：背包 + 角色） | 1000 | 9815/s | 0.13ms | 0.50ms | 26.21ms | 0 |
| 连接建立（2000 连接，批次 500） | 2000 | 2158/s | 2.16ms | 78.22ms | 78.83ms | 0 |

复跑波动（同参数，不同轮次）：

| 轮次 | 只读吞吐 | 只读 P99 | 登录吞吐 | 说明 |
| --- | --- | --- | --- | --- |
| #1（修复中） | 5459/s | 87.79ms | 446/s | Actor 唤醒已修，但仍有重复 Bind |
| #2（修复中） | 5532/s | 60.53ms | — | |
| #3（最终） | 9815/s | 26.21ms | 329/s | 去掉重复 Bind 后 |
| #4 | 5817/s | 89.71ms | — | 冷启动波动 |

> 登录吞吐在 329~446/s 之间波动，受「每个账号首次登录要写 account + player」影响；
> 只读业务 P99 在 26~90ms 之间波动，取决于是否撞上 GC 周期。多次测量取中位数更可靠。

### 1.2 对照设计目标（23.4）

| 指标 | 目标 | 实测 | 结论 |
| --- | --- | --- | --- |
| 单游戏服消息 P99 | < 50ms | 只读 P95 0.5ms / P99 26ms | ✅ 达标（混合负载 P99 101ms 由聊天写库主导） |
| 登录吞吐 | ≥ 2000 TPS | 446 TPS | ❌ 未达标 |
| 单网关连接 | ≥ 10W | 2000（沙盒压测，未冲上限） | 未验证 |
| Kafka 扇出 | 1000 条/s，端到端 < 1s | 未专项压测 | 未验证 |
| Actor 背压 | 信箱满拒绝而非 OOM | 有界信箱 + 丢弃计数 | ✅ |

### 1.3 差距分析

**登录 446 TPS**：单次登录 = HTTP 游客登录（写 account）+ TCP 建连 + RSA-2048 解密 + HKDF + AES 初始化。RSA 解密是 CPU 密集操作，且登录服 `max_open_conns: 20` 在 50 并发下会排队。目标 2000 TPS 需要横向扩展登录服实例（设计上登录服无状态，可直接水平扩）。

**只读 P99 26~90ms**：P50 0.13ms、P95 0.5ms，P99 的差距来自约 1% 的偶发长尾（GC 停顿/调度抖动），不是主链路问题。Actor 分片改为「消息到达即唤醒」（见 2.4）+ 去掉重复 Bind（见 2.9）后，P99 从 90ms 降到 26ms，达标。剩下的抖动可用 `GOGC` 调优进一步压低。

**混合 P99 65ms**：由 10% 的聊天请求主导——聊天要写 `chat_record` 并可能跨服投递。这是业务特性，不是框架问题，因此单独跑只读轮次分离两者。

## 二、演练暴露并修复的问题

### 2.1 网关读错配置段，会话永远绑不到游戏服

**现象**：本地跑起五服务后，客户端 `EnterGame` 一直超时；网关日志 `forward failed: session 2 not bound to any game`，但没有 `no game server available`。

**根因**：网关配置把 etcd 端点放在 `rpc.etcd_endpoints`，代码却读 `s.cfg.Etcd.Endpoints`（顶层 `etcd:` 段，网关 yaml 里没有）。条件不成立 → 整个 etcd 分支被跳过 → `backend` 为 nil → `bindToGame` 直接 return。

集成测试一直是直接构造 `Server` 对象、手动注入 backend，所以从 P2 到 P14 都没暴露。

**修复**：优先读 `RPC.EtcdEndpoints`，回退顶层；`service_prefix` 配置项接入 resolver（原先写了但没生效）。

### 2.2 握手 salt 被「跳过换行」吃掉一个字节（登录失败率 1.3%）

**现象**：压测登录成功率 98.7%，失败全部是 `handshake: read server finished: EOF`，服务端日志 `decrypt finished: message authentication failed`。**串行跑 300 次也失败 4 次**——与并发无关，是稳定复现的偶发。

**根因**：ServerHello 的 body 是 `PEM || salt`。salt 是 32 字节**随机二进制**，客户端靠「跳过 PEM 尾随的 `\n`/`\r`」来定位 salt。当 salt 首字节恰好是 `0x0a` 或 `0x0d`（概率 2/256 ≈ 0.78%），会被当成换行吃掉，salt 变成 31 字节 → 双方 HKDF 输入不同 → 会话密钥不一致 → Finished 的 GCM tag 校验失败。

**修复**：改为 `salt || PEM`——salt 定长前置，切分无歧义；`OnServerHello` 增加 `len(salt) == 32` 校验，早失败早排查。

**验证**：修复后串行 300 次、并发 100×500 次登录，**零失败**。

### 2.3 idtab 空表构建失败

**现象**：游戏服启动日志连刷 12 条 `idtab build failed: rename xxx: ERR no such key`，只有 2 张有数据的表建成功。

**根因**：构建用 `SADD idtab:{table}:building` 累积，完成后 `RENAME` 到正式 key。空表一行都没有 → building key 从未创建 → `RENAME` 一个不存在的 key 在 Redis 里是错误。

**修复**：`total == 0` 时直接 `DEL` 目标集合并置 ready（空表的语义就是「集合为空」）。

### 2.4 Actor 空闲时 100ms 轮询，把 P50 钉在 100ms

**现象**：业务消息 P50 **99.89ms**、P99 147ms。分位几乎全部堆在 100ms，不像正常的延迟分布。

**根因**：分片循环在处理完消息后，若队列为空就 `<-ticker.C` 等 100ms（原本是为了空闲时省 CPU）。消息在这个窗口内到达，最坏要等满 100ms 才被处理。

**修复**：分片增加 `wake chan struct{}`（容量 1，非阻塞写），`deliver` 成功后唤醒；idle select 同时监听 `wake` 和 ticker。

**效果**：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 业务 P50 | 99.89ms | **0.18ms** |
| 业务吞吐 | 476/s | **5459/s** |
| 业务 avg | 97.10ms | 2.45ms |

这是本轮最有价值的发现：一个「省 CPU」的优化把主链路延迟抬高了 500 倍。

### 2.5 预加载替换 State 后 dirty 回调丢失

**现象**：修完 2.4 后 P6B 仍然失败——商店买了 100 个道具，等 15 秒库里还是原值。加日志才发现 `onSave` **一次都没被调用**。

**根因**：`NewActor` 在构造时把 dirty 回调挂在当时的 `State` 实例上；`preload()` 完成后执行 `a.state = newState`，新实例上**没有这个回调**。于是「登录加载完成之后的所有修改」都不会通知 flusher，数据永远不落库——而且没有任何报错。

这类缺陷在集成测试里要等落库周期才暴露，单测更抓不到（测试直接调 `repo.Save`，绕过了 Actor）。

**修复**：新增 `Actor.setState()` 统一赋值并重挂回调，`preload` 的两条分支都走它；补 `actor_dirty_test.go` 三个用例钉住。

### 2.6 落库唤醒写死 1 分钟

**现象**：修完 2.5 后，日志显示 `onSave` 被调用、`dirtyItems=2`，但断言报 `want 112 got 112`——值和期望一样，说明是**等超时了**才查到。

**根因**：P11 把落库唤醒改成「对齐分钟边界」时硬编码了 `time.Minute`。测试环境 `flush.interval = 2s`，于是要等最长 60 秒，超过测试的 15 秒等待窗口。

**修复**：`nextTick(interval, offset)` 按配置的 interval 对齐（生产 60s 时仍然等价于分钟边界）；补一个短周期用例。

> 这个问题在生产不会出现（interval 就是 60s），但它说明「把参数写死」会静默破坏可配置性。

### 2.7 懒加载引出的两个连带修复

把「创角即创建 Actor」改成「首个业务包再创建」后，暴露了两处隐含依赖：

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| 私聊收不到（B 一直没发业务包 → Actor 不存在 → 推送被丢弃） | `chatMessenger.Push` 依赖 Actor 存在 | Actor 不在时直接走会话下行 `sendToPlayer`（推送是纯下行，不该依赖业务状态） |
| A 给 B 发私聊被判「离线」走 pend | `presence.SetOnline` 写在 `ensureActor` 里，跟着 Actor 一起延后 | presence 与 Actor 解耦：`markOnline` 在会话绑定/创角时调用 |

### 2.8 重连后回包丢失（ensureActor 的两个反向错误）

懒加载改造后，`ensureActor` 的绑定策略连错两次，两次都表现为「客户端等响应超时」：

| 版本 | 策略 | 后果 |
| --- | --- | --- |
| 第一版 | Actor 存在就跳过 Bind | 重连时 Actor 还在但 `sessionID` 是旧值/0，回包发不出去 |
| 第二版 | 每个业务包都发 Bind | `onBind` 会跑一遍全部模块 `OnLogin`（活动进度写库 ×2），每条消息多两次落库，延迟直接打穿超时 |
| 最终版 | 仅在「Actor 不存在」或「`players2sess[pid] != 当前会话`」时 Bind | 重连能刷新会话，正常请求零额外开销 |

判断依据放在 `players2sess`（服务端维护的 player→session 映射），而不是 Actor 内部状态 —— 这样不需要跨 goroutine 读 Actor 字段。

### 2.9 其它

- `equip.Repo.Find` 一度用 idtab 做前置存在性判断，导致 GM/脚本直接写库的装备 uid 在 10 分钟对账前被判「不存在」，玩家穿不上装备、登录属性少算。已撤回：穿戴是低频操作，多打一次库的代价远低于误判。
- `drill-crash.sh` 里 `SELECT attr_id, value FROM player_attr` 是错的（该表 PK 是 `player_id`，没有 `attr_id` 列）——脚本 P7 写完后从未真正执行过。已修正。
- `drill-crash.sh` 依赖本机 mysql 客户端，容器化环境常见没有。已支持 `MYSQL_DOCKER=<容器名>` 走 `docker exec`。

## 三、故障演练结果

### 3.1 套件（`make drill-suite`）

| 用例 | 注入 | 检查项 | 结果 |
| --- | --- | --- | --- |
| MySQL 断连 | `docker pause` | `/healthz` 200（进程活着） | ✅ |
| | | `/readyz` 503（摘流量） | ✅ |
| | | 恢复后 60s 内就绪 | ✅ |
| | | 恢复后冒烟通过 | ✅ |
| Redis 断连 | `docker pause` | 进程存活 | ✅ |
| | | 就绪摘除 | ✅ |
| | | 恢复后就绪 | ✅ |
| | | 恢复后冒烟通过（Actor 可从 DB 重建） | ✅ |
| Kafka 停 broker | `docker stop` | 进程存活 | ✅ |
| | | **仍就绪**（异步链路降级，不该影响登录） | ✅ |
| | | Kafka 不可用时冒烟通过 | ✅ |
| | | 恢复后存活 | ✅ |
| etcd 重启 | `docker restart` | 进程存活 | ✅ |
| | | 就绪恢复 | ✅ |
| | | 重启后冒烟通过（服务列表已恢复） | ✅ |

**15 项检查全部通过。**

关键设计验证：**Kafka 停掉时 `/readyz` 仍为 200**。这是刻意的——Kafka 承载的是异步链路（充值发货、跨服聊天、邮件），停掉只影响这些功能，不应该把整个游戏服从负载均衡里摘出去。

### 3.2 kill -9 数据完整性（`make drill-crash`）

```
1/6 造测试角色          player_id=59
2/6 记录快照            player / player_item / player_attr
3/6 SIGKILL 游戏服      已强杀
4/6 重启                GameServer started
5/6 重新登录            冒烟通过
6/6 比对快照
     player: 一致 ✓
     item:   一致 ✓
     attr:   一致 ✓
```

**结论：kill -9 后数据零丢失，重连可恢复。**

> 这项能通过，依赖 2.4 之外的另一个修复：**在线玩家数据变更即落库**（P11 引入的 dirty hook）。在此之前 `onDirty` 只在下线时触发，进程被强杀会丢掉全部在线会话的进度——只是原测试没有覆盖「在线期间修改数据后强杀」。
