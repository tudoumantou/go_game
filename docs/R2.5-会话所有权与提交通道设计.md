## 1. 问题：两个机制放错了层

### 1.1 CAS 放错了层

Actor 模型的前提是**数据所有权唯一**：资产在我的 Actor 里，别人要扣就发消息过来排队。同一时刻只有一个执行者，进程内不存在并发写。

那 CAS 在防什么？只有一个场景：**两个 Actor 同时存在**——

```
玩家在 A 节点掉线（Actor 按 Tier-2 保留 90s）
  → 在 B 节点重连（新 Actor 拉起）
  → A 的残留消息仍在处理，B 也在处理
```

这个"所有权"问题，`presence.TrySetOnline` 已经在**登录时**用一次原子抢占回答过了。但快照写入又在**每条消息**里做了一次 `expected version` 比对——同一个问题检查两遍，且两套判据不一致：

| | presence | 快照 CAS |
|---|---|---|
| 判据 | owner（nodeID）是否是我 | 数据版本是否严格相等 |
| 时机 | 登录一次 | 每条消息 |
| 冲突含义 | "别人持有" → 拒绝绑定 | "别人改过数据" → **回滚业务 + 重载** |

版本冲突的真实含义只是"我可能不是 owner 了"，不需要回滚业务，只需要**拒绝写入**。

### 1.2 bufferReplies 渗透进了控制流

```go
receiveCached:  a.bufferReplies = true / false      // 手工开关
send():         if a.bufferReplies { 入队 }          // 拦截
onGrantItems:   if msg.Done != nil && !a.bufferReplies   // 业务分支检查
onSave:         同上
```

"提交成功才回包"是**提交通道的职责**，现在被拆进了消息处理流程的四个位置。业务模块虽然看不到这个字段，但流程控制被它切碎了。

### 1.3 三条路径的成本（每条有状态消息）

| 步骤 | Items map 分配 | Ext 深拷贝 | JSON 序列化 |
|---|---|---|---|
| `clone()`（回滚备份） | 2 | 2 | 0 |
| `marshal(before)` | 1 | 1 | 1 |
| 业务 | — | — | — |
| `marshal(after)` | 1 | 1 | 1 |
| `Commit`（真正写 Redis） | 0 | 0 | 1 |
| **合计** | **4** | **4** | **3** |

**三次序列化里，只有第三次是真正要写进 Redis 的**——前两次只是为了回答"改没改"。

而且：`clone` 出的 `previous` 在失败路径上先被 `setState(previous)` 回滚，紧接着下一条消息又 `LoadCached` 整个覆盖——

```go
defer func() {
    if !completed {
        a.setState(previous)      // ① 回滚
        a.cacheReload = true      // ② 标记下条消息前重载
    }
}()
// 下一条消息：
if a.cacheReload {
    state, _, _ := a.repo.LoadCached(ctx, a.playerID)
    a.setState(state)             // ③ 把 ① 的结果覆盖掉
}
```

**① 的结果在 ③ 立刻被丢弃。clone 的唯一作用是被丢弃。**

## 2. 目标设计

一句话：**所有权在会话层用围栏令牌声明一次，业务路径只负责改内存和一次提交。**

```
BindMsg
  → lease.Acquire(playerID, nodeID)  → token（epoch，单调递增）
  → Actor 持有 token，整个会话不变

消息到达
  → 业务改内存（无 clone、无备份、无比对）
  → HasDirty() 判断有没有改
  → 有改：一次序列化 → Commit(snapshot, token)
        ├─ 成功：gate.Commit() 刷回包
        └─ 失败（token 过期）：gate.Discard() + needReload
  → 无改：gate.Commit() 直接刷（纯读消息照常回包）
```

## 3. 详细设计

### 3.1 围栏令牌：epoch

**Key 结构**：

| Key | 类型 | 含义 |
|---|---|---|
| `online:{pid}` | string + TTL | 当前 owner（nodeID），沿用 presence，**不参与令牌校验** |
| `wb:{player-N}:epoch:{pid}` | int64 + TTL 7d | 所有权代号，每次 AcquireLease 自增 |
| `wb:{player-N}:state:{pid}` | hash | `version` + `data`，沿用 |

> **实施偏差①**：epoch 最初打算并入 `presence.TrySetOnline`，但 `online:*` 与
> `wb:{player-N}:*` 在 Redis Cluster 下属于不同 slot，无法放进同一个 Lua。
> 改为 writebehind 自己持有 `AcquireLease`，全部落在 `{player-N}` 同一 slot。
> 职责反而更清晰：presence 管「谁在线」，epoch 管「谁的写有效」。

**Acquire（扩展 tryOnlineScript，加一个 KEYS[2]）**：

```lua
-- KEYS[1]=online:{pid}  KEYS[2]=epoch:{pid}
-- ARGV[1]=nodeID  ARGV[2]=ttlMs
local cur = redis.call('GET', KEYS[1])
if cur and cur ~= ARGV[1] then
  return {0, cur, 0}                  -- 别的节点持有，拒绝
end
local epoch = redis.call('INCR', KEYS[2])
redis.call('SET', KEYS[1], ARGV[1], 'PX', ARGV[2])
return {1, ARGV[1], epoch}
```

- **跨节点**：`cur ~= 我的 nodeID` → 拒绝；
- **同节点重连**：`cur == 我的 nodeID` → 放行且 `epoch+1`——**旧 Actor 的 token 立即失效**，这是现在的实现缺的一环（同节点顶号靠 sessionID + kick，有窗口）；
- **首次登录**：`cur` 为空 → 放行，epoch 从 1 开始。

### 3.2 Commit：判据从"版本相等"换成"令牌有效"

```lua
-- KEYS[1]=player_state:{pid}  KEYS[2]=dirty zset  KEYS[3]=epoch:{pid}
-- ARGV[1]=token  ARGV[2]=data  ARGV[3]=pid  ARGV[4]=score
local epoch = tonumber(redis.call('GET', KEYS[3]) or '0')
if tonumber(ARGV[1]) ~= epoch then return -1 end   -- 已被接管
local ver = redis.call('HINCRBY', KEYS[1], 'version', 1)
redis.call('HSET', KEYS[1], 'data', ARGV[2])
redis.call('ZADD', KEYS[2], 'NX', ARGV[4], ARGV[3])
return ver
```

三个变化：

| | 现在 | 改后 |
|---|---|---|
| 调用方传 | `expectedVersion`（上次读到的） | `token`（会话级常量） |
| Redis 校验 | `version == expected` | `token == epoch` |
| 版本号角色 | **并发控制工具** | 仅是**落库顺序编号**（HINCRBY 自增） |

**版本号从"控制变量"降级为"序号"**，这是整个简化的关键：Actor 不再需要记住"我上次读到哪个版本"，也不再需要 `LoadCached` 返回版本给它。

`ZADD NX` 保留：已在脏队列中的玩家不刷新分数，保证落库顺序与首次入队顺序一致。

### 3.3 提交通道：commitGate

```go
// internal/game/player/commit_gate.go

// commitGate 提交通道：提交窗口内的下行先暂存，提交成功才真正发出。
//
// 为什么不在业务代码里：业务只负责产生回包，是否"延后到提交成功"是
// 提交通道的策略。业务模块不该知道提交成不成功，更不该分支处理。
type commitGate struct {
	staging []func()
	active  bool
}

// Begin 进入提交窗口（此后 Send 只入队）。
func (g *commitGate) Begin() {
	g.active = true
	g.staging = g.staging[:0]
}

// Send 窗口内入队，窗口外立即执行。
func (g *commitGate) Send(fn func()) {
	if !g.active {
		fn()
		return
	}
	g.staging = append(g.staging, fn)
}

// Commit 刷出全部暂存动作（提交成功后调用）。
func (g *commitGate) Commit() {
	for _, fn := range g.staging {
		fn()
	}
	g.Reset()
}

// Discard 丢弃暂存（提交失败时调用）：客户端收不到"成功"，
// 由它重试；服务端不会出现"回了成功但没落库"的假成功。
func (g *commitGate) Discard() { g.Reset() }

func (g *commitGate) Reset() {
	g.active = false
	g.staging = g.staging[:0]
}
```

Actor 的 send 统一走 gate：

```go
func (a *Actor) send(msgID uint32, body []byte) error {
	a.gate.Send(func() {
		if a.sendFunc == nil || a.sessionID == 0 {
			return
		}
		_ = a.sendFunc(a.sessionID, msgID, body)
	})
	return nil
}
```

**Done channel 回执也进 gate**：`GrantItemsMsg.Done <- err` 包成闭包入队，提交成功才回执。`onGrantItems` / `onSave` 里那些 `!a.bufferReplies` 分支全部删除。

### 3.4 消息流程改造

```go
// 改造后
func (a *Actor) receiveCached(ctx *actor.Context) {
	// ① 会话归属：token 为空说明未 Acquire（不该发生），按失败处理
	if a.token == 0 {
		a.cacheFailure(ctx, errNoLease)
		return
	}
	// ② 待重载优先：上次提交失败过，先回到权威状态
	if a.needReload {
		if err := a.reload(); err != nil {
			a.cacheFailure(ctx, err)
			return
		}
	}
	if !a.loaded {
		if err := a.preload(ctx); err != nil {
			a.cacheFailure(ctx, err)
			return
		}
	}

	// ③ 业务：无 clone、无 before 序列化
	a.state.ClearDirtyAll()
	a.gate.Begin()
	a.receive(ctx)

	// ④ 提交：脏标记判断，一次序列化
	if a.state.HasDirty() {
		if err := a.repo.cache.Commit(ctx, a.state.snapshot(), a.token); err != nil {
			a.gate.Discard()
			a.needReload = true          // 不回滚：下条消息前重载
			a.cacheFailure(ctx, err)
			return
		}
	}
	a.gate.Commit()
}
```

对比现状：删掉了 `clone()`、两次 `json.Marshal`、`bytes.Equal`、`defer` 回滚、`finishPending`。

### 3.5 删除 cachePending / finishPending

`cachePending` 的存在理由：**Commit 结果未知**（网络超时）时不知道 Redis 写没写，于是保留内存快照，下次用版本比对判断。

有了 token 之后，这个判断变简单了：

```
Commit 超时（结果未知）
  → 标记 needReload
  → 下条消息前 LoadCached：
      ├─ 读到了我写的数据（version 比上次成功的高）→ 直接用
      └─ 没读到（version 还是旧的）→ 用旧数据，本次改动丢失
  → 两种情况下客户端都没收到"成功"（gate 已 Discard），会重试
```

**前提**：重试必须幂等。当前所有走快照路径的业务都有幂等依据（`ClaimBiz` 业务键 / 「今天已领」这类事实去重 / 可重放的纯计算），而不可重放的消息（充值发货）走的是 `CommitItems` 的 MySQL 事务，不经过这条链路。

因此可以删除：

| 删除项 | 原因 |
|---|---|
| ~~`cachePending` / `finishPending`~~ **（保留）** | 见下 |
| `cacheVersion` 字段 | 改由 token 表达会话归属；版本只用于 writebehind Ack |
| `RollbackAware` 接口及实现（`Thin` 默认实现 + 2 个模块显式实现） | 没有回滚概念了，模块只需保证幂等；`Registry.IsRollbackable` 一并删除 |
| `Thin.Rollbackable` / `Registry.IsRollbackable` | 同上 |
| `ThinGuard(RequireCache)` 的部分语义 | 保留（它防的是"缓存没就绪就处理写请求"），但不再与回滚耦合 |

## 4. 前提条件：dirty 必须完整

用 `HasDirty()` 替代 JSON 比对的前提是**所有写路径都标脏**。当前缺口：

| 方法 | 现状 | 要做的 |
|---|---|---|
| `AddExp`（升级改 profile） | ❌ 不标脏 | 加 `markChanged("profile")` |
| `SetProfile` | ❌ 不标脏 | 同上 |
| `SetAttr` | ❌ 不标脏 | 加 `markChanged("attr")` |
| `SetAttrStruct` | ❌ 不标脏 | 同上 |
| `SetSceneID` / `SetExt` / `AddItem` / `RemoveItem` / `MarkDirty` | ✅ 已标 | — |

**统一入口**：State 内部所有写方法最后都调 `s.markChanged(module string)`，由它同时置 `dirty[module]` 和 `dirtyItems`（道具场景）。禁止业务层直接改字段。

**测试锁**：每个写方法一个用例，断言调用后 `HasDirty() == true`。这是"删掉全量比对"的安全网——没有它，漏标脏就是静默丢数据。

> **实施偏差②**：`cachePending` 最终**保留**。原方案认为它可以用"失败即重载"替代，
> 但充值发货（`GrantItemsMsg`）的事实已经写进 MySQL（R2.3 的「MySQL 先行」），
> 此时丢掉 Redis 快照会与事实分叉——必须保留待提交快照，下次 `finishPending` 补提。
> 结论：**普通消息「失败即重载」，不可重放消息「保留补提」**，两条路径并存。
> 同理保留「能否丢弃」的判断接口。它原本叫 `RollbackAware`，语义已从「能否回滚」
> 变成「失败后能否安全丢弃内存改动」，**已重命名为 `DiscardableAware`**
> （方法 `Discardable`、注册表 `IsDiscardable`）。

## 6. 失败矩阵

| 故障 | 现在 | 改后 |
|---|---|---|
| 别的节点接管了 | version 冲突 → 回滚 + 重载 | token 过期 → 拒写 + 重载（**无需回滚**） |
| Commit 超时（结果未知） | `cachePending` 保快照，下次比对 | 标记 `needReload`，下条消息重载；客户端未收到成功，重试 |
| Redis 不可用 | 所有写失败，回错误码 | 同上（语义不变） |
| 进程崩溃 | 已提交的在 Redis，未提交的丢 | 同上（语义不变） |
| 同节点顶号 | sessionID 比较 + kick（有窗口） | **epoch+1，旧 Actor 立即写不进去** |
| 漏标脏（代码 bug） | JSON 比对兜底，仍能提交 | **会丢提交** ← 靠 §4 的测试锁防御 |

## 7. 验证方案

**单测**：
- `Acquire` 三次：首次 / 跨节点拒绝 / 同节点重连 epoch+1；
- `Commit` 旧 token 被拒、新 token 成功、version 单调递增；
- `commitGate`：窗口内不执行、Commit 刷出、Discard 丢弃；
- `State` 每个写方法标脏（§4 的测试锁）。

**集成**：
- 模拟双 Actor：A 持有后 B Acquire，A 的 Commit 必须失败且不影响 B；
- Commit 超时注入 → 下条消息触发重载 → 状态与 Redis 一致；
- 现有 P15 全链路演练全部通过。

### 8.3 分字段存储（B 阶段）

快照从「整份 JSON 塞在一个 `data` field」改为「一部分一个 field」，Redis 仍是权威，
只是把 Hash 的结构用起来：

```
wb:{player-N}:state:{pid}
  ├─ version     = 42
  ├─ profile     = {"name":"hero",...}
  ├─ attr        = {"hp":8000,...}
  ├─ items       = {"1001":10,...}
  ├─ grants      = {"recharge:order-1":true}
  └─ ext:signin  = {"days":[1,2,3]}
```

提交时只序列化并写入变化的字段（`State.DirtyFields()`），删除的模块状态显式 `HDEL`。

**实测**（100 道具 + 5 模块 Ext）：

| 场景 | 改造前（整份） | 改造后（分字段） |
|---|---|---|
| 改签到/任务状态 | 23,059 ns / 314 allocs | **9 ns / 0 allocs** |
| 改背包（100 件） | 23,059 ns / 314 allocs | 19,926 ns / 302 allocs |

Ext 变更几乎零成本——`Ext` 存的就是 `json.RawMessage`，提交时直接引用写出，
不再二次序列化。这是当初把模块状态设计成 RawMessage 的红利。

**升级兼容**：早期实现会在 `Load` 时识别旧的整份 `data` 格式，返回 `Record.Legacy`
让 Actor 强制全量提交一次完成迁移。该分支**已删除**——本项目是独立 demo，
不存在需要兼容的历史数据；`Load` 现在只认分字段格式，`Seed` 也改为逐字段写入
（与 `Commit` 同一套布局，否则冷启动写完会被读成空状态）。

> 若将来从旧版本升级，需要先跑一次数据迁移（把 `data` 拆成字段），
> 而不是恢复这段代码：迁移脚本能一次做完，运行期兼容只会把复杂度长期留在热路径。

**这一步暴露的第二个 bug**：`onGrantItems` 直接写 `state.appliedGrants` 而不走
`ClaimBiz`——整份序列化时它碰巧被写进去了，分字段后 grants 不在脏字段里，幂等键
随之丢失，Kafka 重投会二次发奖。已改为统一走 `ClaimBiz`（它负责检查+置位+标脏）。

### 8.4 字段按需序列化（C 阶段）

分字段存储解决了「只写变化字段」，但调用方仍要先构造整份 `Snapshot`——只为取其中一个字段，却把 100 件道具和三张 map 复制一遍。

改成 `Commit` 接 `FieldSource` 接口（`Field(name)` / `Fields()`），由 `*State` 实现、按字段现取现序列化：

```go
// 之前
snap := a.state.snapshot()                       // 4.3µs，复制整份状态
store.Commit(ctx, snap, fields, removed, token)

// 之后
store.Commit(ctx, a.playerID, a.state, fields, removed, token)
```

| 路径 | ns/op | allocs |
|---|---|---|
| 旧：`snapshot()` 再取字段 | 4,393 | 14 |
| 新：`State.Field()` 直接取 | **18** | **0** |

`snapshot()` 保留给两个确实需要整份副本的场景：pending 补提（「上次那条消息的完整结果」）与冷启动 Seed。两者都在异常/初始化路径上，不在热路径。

**校验的收窄**：`Snapshot.Validate` 原先对整个快照校验（背包范围 + 每个 Ext 模块）。改成 `validateField` 只校验本次写的 Ext 字段——核心字段的写入源是 `State`，`AddItem`/`RemoveItem`/`Grant` 已在入口保证非负与 int32 上限；在提交处复检要把 items 反序列化一遍（约 5µs），与优化目的相反。

### 8.5 行为变化清单（对业务/运维可见）

| 变化 | 影响 |
|---|---|
| 提交失败后内存不回滚，改标记重载 | 玩家可见结果不变（下条消息前重置）；`TestSpendResetsToAuthorityWhenCacheFails` 覆盖 |
| 同节点顶号也会换令牌 | 旧 Actor 的残留消息立即写不进去（原先有窗口） |
| 令牌失效后提交直接拒绝 | 返回 `ErrConflict`，Actor 转 `cacheReload`，不重试提交 |
| `Presence` 的 Lua 未改动 | 网关读在线状态的路径完全不变 |

## 9. 明确不做的

| 不做 | 理由 |
|---|---|
| 增量提交（只写变化的模块） | 需要合并冲突解决，复杂度远超收益；KB 级全量序列化可接受 |
| 去掉快照（改内存权威 + 定时刷库） | 会丢最后一段进度、跨节点读失效、writebehind 失去输入 |
| 去掉 Redis 权威 | 破坏 R2.1 契约与 P0 跨节点 |
| lease 心跳续约独立实现 | 复用现有 `RefreshOnline`，TTL 一起续 |
