# 配置热更新（R10.3 / R10.4）

> 状态：库能力与验证已完成；线上接入（下发服务、灰度、审计）尚未接入。
> 代码入口：`pkg/gamedata/tables.go`（`Cur` / `Replace` / `LoadDir` / `Rollback`）。

## 1. 能做什么，不能做什么

| 能 | 不能 |
|---|---|
| 用外部 JSON 覆盖**指定表**，其余表沿用当前快照 | 重新读编译期 `embed` 改配置——那读到的永远是同一个内容 |
| 事务性：一张表不合法，整批不生效，旧快照保留 | 跨节点自动广播——每个进程各自应用，运维要保证各节点拿到同一份输入 |
| 回滚到上一个快照（保留一层） | 回滚到任意历史版本（没有版本仓库） |
| 读取无锁：`Cur()` 一次原子读 | 修改已构造的快照（快照不可变） |

**协议、消息号、DDL 不在热更新范围内**：它们编译进二进制，改号必须发版并同步客户端（见 `pkg/codec/msgids_gen.go` 的兼容基线）。

## 2. 数据流

```
configs/gamedata/xml/*.xml
        │  make gen-data（校验 → 生成 Go + 内嵌 XML）
        ▼
编译期快照（embeddedVersion = XML 内容哈希）
        │
        │  运行期：外部 JSON 目录（运维下发 / GM 后台导出后修改）
        ▼
gamedata.LoadDir(dir) ──► Replace(patch) ──► 构造新 Tables ──► 校验 ──► 原子换指针
                                                    │失败
                                                    └──► 返回错误，current 不变
```

## 3. 输入格式

一张表一个文件，文件名即表名，内容是该表的行数组；列名与生成的 `Cfg` 结构体 `json` tag 一致：

```json
// item.json
[
  {"id": 1001, "col1": "金币", "col2": 999999, "col3": 1},
  {"id": 1002, "col1": "经验药水", "col2": 99, "col3": 10}
]
```

用生成器导出模板（导出的就是当前编译期配置，改完即可下发）：

```bash
go run ./tools/gendata -in configs/gamedata/xml -out pkg/gamedata -json-out /tmp/gamedata-hotfix
```

## 4. 应用与回滚

```go
ver, err := gamedata.LoadDir("/etc/game/hotfix/20261019-01") // 读 *.json 并原子应用
if err != nil {
    // 输入非法：整批未生效，线上仍是 ver 之前的版本
}

cur := gamedata.Version()   // 形如 b96a91050f8a8362 或 b96a91050f8a8362+9f2c1d4e
name, _ := gamedata.MsgName // 协议号反查（与热更新无关，顺带一提）

if _, err := gamedata.Rollback(); err != nil {
    // 没有上一版本可回滚
}
```

只改一张表时不必重传全部：

```go
gamedata.Replace(map[string][]byte{"item": raw})
```

## 5. 校验规则（替换时执行）

| 规则 | 失败后果 |
|---|---|
| 表名必须存在（拼错文件名） | 整批拒绝，避免「以为更新成功」 |
| JSON 可解码 | 整批拒绝 |
| 主键唯一 | 整批拒绝（重复主键会让 ByID 索引静默覆盖） |
| 表非空 | 整批拒绝（空表通常是下发内容写错） |
| `patch` 非空 | 拒绝，空批次视为调用方 bug |

**这些是运行期防线**；生成期还有更细的校验（列一致、引用完整、非负），见 `tools/gendata/validate.go`。两道都要有：生成期拦住提交进仓库的错，运行期拦住下发到线上的错。

## 6. 版本语义

| 场景 | 版本形态 |
|---|---|
| 启动 | 编译期 XML 内容哈希（16 位），如 `b96a91050f8a8362` |
| 热更新后 | `编译期哈希 + 本次内容哈希前 8 字节`，如 `b96a91050f8a8362+9f2c1d4e` |
| 回滚 | 回到上一版本的字符串 |

版本派生只保留一层（`base+hash`），反复热更新不会让版本串无限变长。同一批内容无论下发顺序如何，得到同一版本。

## 7. 读取方约定

1. **每条消息内查一次配置**，不要跨消息缓存 `*Cfg` 指针。热更新后旧指针仍指向旧快照——消息内自洽，但跨消息会读到过期值。
2. 需要多处使用时，在同一次处理内取到局部变量再传递。
3. 当前全部模块都符合该约定（`grep gamedata.Get` 均为「进函数查一次」）。

## 8. 领取记录不受热更新影响

已经发生的领取，回看时必须是**当时发的东西**，不能被新配置改写：

| 模块 | 做法 |
|---|---|
| 签到 | 快照里存 `claimed_rewards`（道具 ID → 数量），回看读事实 |
| 邮件 | 附件存在 `mail` / `mail_attachment` 行里，是投递时的事实 |
| 任务/活动/副本 | 即时发放，没有「回看历史奖励」的界面；重复领取靠状态位拦截 |

规范：**任何可回看的领取记录，存奖励事实（道具 / 数量），不要存配置 ID 再去查表**。配置 ID 会随版本漂移，事实不会。

## 9. 未做的部分

- **下发通道**：没有 HTTP/GM 端点调用 `LoadDir`，也没有审计日志与灰度。库能力已就绪，接入面留给运维侧。
- **多节点一致性**：各进程独立应用，没有「全服配置版本对齐」检查。若需要，可在节点心跳里带 `gamedata.Version()`，中心服比对后告警。
- **配置差异预览**：`Replace` 只返回版本，不返回「哪些行变了」。
