## 3. 故障演练

### 3.1 kill -9 演练（已执行，2026-10-19 23:20）

环境：本地五服务 + Docker 中间件（MySQL 8.0 / Redis / Kafka / etcd）。

```
==> 造测试角色  player_id=4
==> 记录演练前快照  (player, item, attr)
==> SIGKILL 游戏服（PID 658764）
==> 重启游戏服（PID 660344），等待就绪
==> 重新登录校验
  player: 一致 ✓
  item:   一致 ✓
  attr:   一致 ✓
```

**结论**：在「操作已提交到 Redis 并落库」的路径上，kill -9 后重启数据一致、重连可恢复。
这不改变恢复边界：Redis 已提交但尚未落库的窗口仍依赖 worker 从脏队列重放，
重放失败时该窗口的数据会丢失（R1.3 已明确，不拿本次结果覆盖）。

### 3.2 换主演练（已执行，2026-10-19 23:19）

双中心服实例（center-01 / center-02 共用 etcd leader key）：

```
9201 is_leader=1（center-01）  9203 is_leader=0（center-02）
kill -9 center-01
→ center-02 在 18s 后 gs_center_is_leader=1（etcd 租约 10s + 检测间隔）
→ 接管后第一个 tick 写入 activity_instance 2 行（两个活动各一期）
```

**结论**：leader 强杀后 18s 内完成接管，活动调度由新 leader 继续执行；
`activity_instance` 以 instance_id 为主键，重复调度不会产生重复行。

### 3.3 中间件注入演练（已执行，2026-10-19 23:29）

`./scripts/drill-suite.sh`：MySQL 断连、Redis 断连、Kafka 停 broker、etcd 重启，共 15 项检查。

结果：**15/15 通过**。要点：

| 注入 | 关键结论 |
|---|---|
| MySQL 断连 | 进程存活；`/readyz` 503 摘流量；恢复后 60s 内就绪并冒烟通过 |
| Redis 断连 | 进程不崩；就绪摘除；恢复后 Actor 可从 DB 重建 |
| Kafka 停 broker | 仍就绪（异步链路降级），登录与业务不受影响 |
| etcd 重启 | 服务列表自动恢复，冒烟通过 |

### 3.4 滚动发布（已执行，发现问题）

双游戏服实例（game-01/game-02）注册在 etcd，循环压测期间对 game-01 发 SIGTERM：

| 指标 | 值 |
|---|---|
| 请求总数 | 7100 |
| 失败 | 45（0.63%） |
| 加 `register_drain: 3s` 后重测 | **仍 45** |

**结论**：失败不是路由滞后造成的。玩家会话（Actor）绑定在实例内存里，
实例下线必然断开这些连接；`register_drain` 只能保证新连接不再路由过来。

**已做的服务端改进**：

| 改动 | 作用 |
|---|---|
| 关闭时 `kickAllSessions` | 摘注册后立即给所有在线会话推 KickNotify，客户端可马上重连，不用等请求超时 |
| 网关转发失败即断客户端连接 | 后端流已断时不再让客户端对着死连接重试，直接关闭连接触发重连 |

**仍未验证**：`loadtest` 不支持断线重连，所以失败数没有下降（仍是 45）。
要证明「零失败」需要一个会重连的压测客户端——这是测试工具的限制，不是服务端未处理。
真实客户端收到 KickNotify 后会断开重连，重连期间的那一次请求仍然会失败，
这是有状态长连接的固有成本，只能缩短、不能消除。

## 4. 压测（已执行，单机）

环境：单机五服务 + Docker 中间件（MySQL 8.0 / Redis / Kafka / etcd），
`./bin/loadtest` 直连 127.0.0.1:9001。

| 场景 | 规模 | 结果 |
|---|---|---|
| 建连保持 | 1000 连接 / 15s | 0 失败；建连 2111/s；P50 16ms / P95 54ms / P99 56ms |
| 建连保持 | 3000 连接 / 10s | 0 失败；建连 2224/s；P50 5ms / P95 43ms / P99 44ms |
| 业务消息 | 50 玩家 × 20 轮（背包/角色/聊天混合） | 1000 请求 0 失败；3912/s；P50 0.2ms / P95 3.9ms / P99 74ms |
| 登录 | 300 次 / 并发 30 | 0 失败；583/s；P50 47ms / P95 86ms / P99 92ms |

**这些是单机实测值，不能直接外推为生产容量**：同一台机器上服务、中间件、压测客户端互相争抢；
3000 连接时延迟反而下降，说明瓶颈还没到网关，而是客户端所在机器的调度。
判据已达标（登录 P99 < 500ms、业务 P99 < 200ms），但**未做 1w+ 连接与多实例横向对比**。

执行与判定标准：

```bash
LOGIN_N=2000 BIZ_N=200 CONN_N=5000 ./scripts/bench.sh
```

| 指标 | 判定 |
|---|---|
| 登录吞吐 | 在目标并发下 P99 < 500ms，错误率 < 0.1% |
| 业务消息 | 背包/角色信息混合 P99 < 200ms |
| 连接保持 | 目标连接数下内存增长线性、无 FD 泄漏 |
