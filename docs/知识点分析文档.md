# 知识点分析文档

这里用“概念 → 本项目位置 → 为什么需要 → 怎么验证”的顺序学习。不要把库名字记成答案，重点说明它消除了哪类失败，又保留了什么边界。

## 1. 一条请求里的知识点

```text
HTTP JSON → 随机 Token → Redis TTL → TCP 分包 → RSA/HKDF/AES
 → Session 状态机 → etcd → gRPC stream → Actor mailbox
 → Module 接口 → State → SQL 事务 / Write-Behind → 回传
```

每个箭头都有输入验证、超时、所有权转移或失败传播的问题。能解释这些边界，比只背一张架构图更接近理解项目。

源码节选：[internal/game/module/module.go](../internal/game/module/module.go)。这是现有包中的片段，依赖同文件类型，不是可单独运行的完整程序。

```go
func (r *Registry) Dispatch(ctx *Context, msgID uint32, body []byte) error {
	m, ok := r.route[msgID]
	if !ok {
		return fmt.Errorf("%w: %d", ErrNoRoute, msgID)
	}
	return m.OnMessage(ctx, msgID, body)
}
```

这里 `map[uint32]Module` 保存接口值，Dispatch 在运行时选择模块。错误使用 `%w` 保留 ErrNoRoute，调用者可以 errors.Is 判断“协议未接入”，不必比较英文字符串。

## 3. channel 与内存模型

channel 传递的是值：指针值仍指向原对象，slice 值仍引用原底层数组。把对象放进 channel 并不等于把对象冻结。共享对象的并发访问需要串行所有权或同步；Go 的保证由 [内存模型](https://go.dev/ref/mem)定义。

```go
// 教学片段：快照解决“发送后继续修改同一 map”的问题。
snapshot := make(map[int32]int64, len(items))
for id, n := range items { snapshot[id] = n }
// 前提：复制过程本身也处在锁内或 Actor 所有者线程内。
select {
case jobs <- snapshot: // 消费方之后独占这个快照。
case <-ctx.Done():    // 取消必须能解除等待。
    return ctx.Err()
}
```

nil channel 会永久阻塞普通收发；关闭的 channel 可以不断读出零值，因此接收要检查 ok；通常由拥有发送生命周期的一方关闭。Send 与关闭并发不能靠 sync.Once 自动解决，Once 只防止重复 Close。

## 4. Mutex、RWMutex、atomic、WaitGroup

Mutex 保护一个不变量及其检查修改过程；RWMutex 允许多个只读者，但返回可写指针后锁已经失效；atomic 适合计数器和状态位，不能把“检查余额并扣款”的多步规则自动组合成事务。

Preloader 使用 WaitGroup 等五个查询完成，不代表这五次查询共享同一 SQL 快照。各 goroutine 写自己的结果字段，主 goroutine Wait 后再读；如让多个 goroutine 共同 append 同一个 slice，仍需额外同步。

ActorSystem 使用分片 goroutine；目前 shardFor 实际为 FNV 后取模，不能照注释误讲成位掩码。调度循环中的一轮预算与遍历顺序还影响公平性。

## 5. Context 的传播

网络请求使用 request.Context，SQL 使用 QueryContext / ExecContext；取消是一种协作信号，不会撤销已经提交的 SQL。后台工作需要清楚区分“随请求结束取消”和“提交后必须继续完成”。

当前 player.preload、onSave 等用 context.Background，调用方取消不会自然传播进这些工作。停服清理则反过来不能直接继承已取消的运行 context，需要独立超时。

## 6. 网络知识与安全边界

TCP 是字节流，codec 定义边界；Protobuf 定义字段，MsgID 决定类型；加密保证密文完整性并隐藏内容，身份认证决定你信任谁；Token 和会话保存账号身份，邮件 Repo 还要校验资源归属。

Replay Seq、请求重试 ID、biz_id、数据库主键是四种不同机制。重放旧包、断线重发业务、Kafka 重投、两条 SQL 插入同一事实，不可用一个 seq 全部解决。

## 7. 数据库知识

`sql.Open` 创建池句柄，PingContext 才验证连接。Query 结果要 Close，并检查 rows.Err；参数占位符保护值绑定，动态表名/列名仍应限制来源。长事务占连接和锁，会把登录预加载等其他路径一起拖慢。

| 机制 | 本项目例子 | 它保护什么 |
|---|---|---|
| 唯一索引 | player.uk_name | 并发创角不能产生相同名字 |
| 事务 | player + player_attr | 两张表共同提交 |
| 行锁 | mail.TakeAttachments | 对同一邮件的领取竞争 |
| UPSERT | player_item | 依唯一键合并同玩家道具 |
| 增量写 | State.DirtyItems | 减少背包全量重写 |
| 索引 | mail(player_id,status) | 降低查询扫描范围 |

事务中的锁读与普通一致性读取不同，参见 [MySQL 锁定读](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)。不要只因看见 FOR UPDATE 就宣布跨表、跨 Redis、跨进程的一切副作用都原子了。

## 8. Redis 的四个角色

Token 是带 TTL 的身份映射；Presence 是玩家→节点的在线路由；IDTable 是存在性索引，构建未完成要回退 DB；Deduper 是 topic+biz_id 的 SETNX 标记。

Redis 暂时不可达时，每个功能要单独决定拒绝、重试或回退。不能统一“缓存故障就忽略”，例如把 Token 查失败当作验证成功会破坏身份边界。

## 9. Kafka 与副作用

生产者发送、broker 接收、消费者 Fetch、业务提交、offset commit 是不同阶段。手动提交有助于决定处理顺序，但业务提交后提交 offset 前崩溃仍会重投。

现有去重通常先 SETNX，失败时 Forget。SETNX 成功后进程直接崩溃、业务尚未执行时，去重标记会暂时阻止重新处理。需要数据库业务事实或可恢复处理中状态，不能只调整 TTL。

## 10. 数据生成与静态配置

XML → gendata → *_gen.go + 内嵌 XML；DDL → gendb → model CRUD；proto → buf → Go 消息与 gRPC。编译时生成不等于运行时热更。热更要额外解决版本一致、原子切换和正在运行的战斗使用哪个配置版本。

协议注释 `MsgID: 2001` 当前不是自动路由注册机制。代码生成完成后仍需要 module.MsgIDs、注册模块以及机器人客户端方法。

## 11. 观察系统而不是猜测

每个指标先明确单位和语义：请求耗时、队列深度、累计丢弃数、待脏玩家数和 Kafka lag 不是同一量。P99 会比平均值更容易暴露慢 SQL、分片阻塞和慢客户端。

优化前做基线，改变后用同一负载比较。当前 readiness 覆盖有限，Flusher 的成功可能只确认 SaveMsg 入队，指标名也需要与实际成功点对齐。

## 12. 新增签到的事务能力

当前七日签到已接入 `module.Context.CommitItems`，由 Actor 在同一事务中写领取事实和背包，提交成功再更新内存。Commit 返回未知结果时通过 needsReload 阻止旧背包保存，并重载收敛。它是特定功能的新能力，不能自动修复旧邮件领取或普通 Flusher 的确认语义。详见[签到实战](新增功能开发流程（以签到为例）.md)。
