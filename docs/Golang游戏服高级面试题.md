# Golang 游戏服高级面试题（100）

题目针对当前 go_game 源码。每题给出回答主线，不把示例仓库的设计目标包装成已完成的生产保证。学习时先独立回答，再打开每组源码入口，补充具体函数与失败场景。

回答结构建议：先说结论 → 指出状态所有者/提交点 → 给一个反例 → 说明如何验证。性能问题没有本机实测就不报容量数字。

## Go 并发与所有权

源码入口：[pkg/actor/system.go](../pkg/actor/system.go)。

### 1. goroutine 多就意味着游戏服并发能力强吗？

不一定。网络连接可以并行，角色规则仍需归属；同一 Actor 分片上同步 SQL 会让其他角色一起等待。先观察调度耗时与队列，再谈增加 goroutine。

### 2. 一玩家一 Actor 是一玩家一 goroutine 吗？

当前不是。玩家 Actor 有自己的行为与信箱，多个 Actor 被分片循环调度；goroutine 数主要受 shard 与网络/后台任务影响。对象数和执行线程数是两个维度。

### 3. 为什么玩家 map 加 RWMutex 后仍可能有竞态？

锁只保护查找期间的 map。取出的 *State 若在锁外被另一个 goroutine 修改，字段仍需要一致的所有权或同步。返回副本和经 Actor 投递比暴露可写指针更清楚。

### 4. channel 发送 []byte 后可以立即复用数组吗？

只有消费者不再引用原底层数组才可以。slice 在发送时复制头部而非数据。网络缓存会前移或覆盖时，应先复制包体或明确转移独占所有权。

### 5. sync.Once 能保证 Send 与 Close 并发安全吗？

它只能保证关闭逻辑执行一次，不能防止发送者已经取出队列后与关闭竞争。邮箱终止需要统一生命周期协议，或保证发送/关闭处在同一同步边界。

### 6. 带 Ack 的消息为什么常用容量 1 的 channel？

调用者超时离开后，处理者仍可写一次结果而不永久卡住。但仍要明确只写一次、谁关闭、不复用；容量 1 本身不是通用防泄露方案。

### 7. atomic 能替代扣物品的锁吗？

单个原子计数适合指标，不会自动把检查配置、校验数量、扣除、标脏组合为业务事务。多字段不变量仍需 Actor 所有权、锁或事务。

### 8. context.Cancel 会撤销已经完成的奖励吗？

不会。取消是协作通知，SQL 已提交或 Actor 已生效的副作用仍存在。客户端超时后用同一业务键重试，服务端要能查到已经完成的事实。

### 9. recover 后继续处理一定安全吗？

不一定。它保护执行循环不退出，却无法撤销 panic 前的部分修改。需要明确角色状态是否已损坏、是否隔离/重载，以及是否可重放这条业务。

### 10. WaitGroup.Wait 证明了五个查询数据一致吗？

只证明 goroutine 完成与结果可读取，不证明它们处于同一数据库事务快照。预加载并行查询会分别借连接，需要根据业务决定是否接受跨查询时间差。

## TCP、编码与加密

源码入口：[pkg/crypto/session_cipher.go](../pkg/crypto/session_cipher.go)。

### 11. 为什么不能把一次 Read 当作一个消息？

TCP 提供字节流，不保存 Write 边界。需要累计缓存并按 Length 拆帧，同时处理长度字段半包、消息半包和多帧连包。

### 12. 本项目 Length 算不算自己？

不算。Length 是 MsgID 两字节、Seq 四字节与 Body 长度之和；完整 TCP 帧还要加长度前缀两字节。编码与解码必须遵守同一约定。

### 13. 为什么使用大端？

它是协议明确选择的网络整数表示，不依赖宿主 CPU 字节序。双方只要一致即可；不能通过直接序列化 Go struct 内存替代编码，因为还存在对齐和布局差异。

### 14. protobuf 能解决粘包吗？

不能单独解决当前 TCP 流边界。它描述一个消息内部字段，外层帧负责知道该取多少字节；数字 MsgID 决定应按哪种 protobuf 类型解码。

### 15. RSA、HKDF、AES 在握手里各做什么？

RSA-OAEP 用于保护客户端的 pre-master，HKDF 根据 secret 与 salt 派生固定长度会话密钥，AES-GCM 处理后续消息的保密与完整性。它们不是三个可互换的加密名字。

### 16. 为什么 AES-GCM 还需要 Seq？

nonce/认证标签保护一次加密使用和完整性，业务连接还需记录已经接受的序号以拒绝重放。GCM 解密成功不代表该消息以前没有执行过。

### 17. 64 位窗口允许什么？

允许最近窗口内尚未见过的序号，并拒绝重复位和太旧序号。它不等于任意乱序重排器，也不负责把已经接受的业务请求按顺序执行。

### 18. 为什么加密体里还放 MsgID 与 Seq？

当前 SessionCipher 保护并从加密体读取这些字段；外层仍保留传输头。读机器人和 Router 的实际处理方式，不能自行只加密 protobuf 后宣称协议相同。

### 19. 收到 ServerHello 公钥就可信了吗？

仅从未认证连接收到公钥，不能单独证明服务器身份。当前自定义握手需要另行考虑信任来源；不能把它直接称为具有完整 TLS 身份保证。

### 20. 网关 write_queue_size 配了就有异步写队列吗？

没有这种推论。当前 Conn.Send 同步 Write，writeLoop 只等待关闭。参数、设计和实现应分别核对，再以慢客户端测试判断阻塞传播。

## 账号、会话与权限

源码入口：[internal/login/service/auth_service.go](../internal/login/service/auth_service.go)。

### 21. 游客登录的 Token 是 JWT 吗？

当前不是。它由 crypto/rand 生成，编码后作为 Redis key 的一部分，映射 account_id 并带 TTL。login_rsa 配置字段不代表该主链路已签名。

### 22. HTTP 响应 player_id 为什么不能直接当角色？

这是兼容字段，目前与 account_id 同值。真正角色由 Game 创角事务产生，可能与账号数值恰好相同，也可能完全不同，不能依赖巧合。

### 23. 加密成功等于登录成功吗？

不等于。加密阶段建立共享密钥，鉴权阶段通过 Token 确认账号，进游戏阶段再查角色与加载 State。这些状态必须分别验证。

### 24. 角色 ID 为什么不应由领取邮件请求决定？

身份应来自已经绑定的 Context.State，客户端只指定目标资源 ID。Repo 仍检查邮件 owner 是否等于当前玩家，防止资源越权。

### 25. 空 device_id 当前怎样处理？

handler 会使用 anonymous，而不是直接返回参数错。学习工程可以改为拒绝，但文档必须区分现状与改进；匿名回退也不能作为可信设备认证。

### 26. 一个账号一个角色是否有数据库兜底？

当前 RoleService 先查账号是否已有角色，player.account_id 只是普通索引。两个并发请求可能绕过应用检查；需要对应唯一约束或其他串行机制。

### 27. 名字校验为什么还要唯一索引？

应用检查无法防两个并发请求同时看到名字可用。数据库唯一索引负责最终竞争，驱动重复键错误再映射为业务重名响应。

### 28. Token TTL 能解决抢登吗？

TTL 只控制有效期限，不自动作废旧 Token、关闭旧 Session 或裁决哪个设备保留。抢登需要账号会话版本和旧连接清理等单独策略。

### 29. 会话与连接为什么不合为一个对象？

连接负责字节、地址和关闭；会话负责身份、握手状态和业务映射。分开后更容易讨论重连与逻辑会话，但仍需真实实现 TTL、替换和清理。

### 30. 断线后一定会触发 Game.OnUnbind 吗？

应逐条检查 EOF、错误、显式 UNBIND 与 defer 清理。当前 Channel 对 EOF 直接返回，不能只凭 unbindStream 删除流索引就推导业务在线状态已清理。

## gRPC、发现与服务边界

源码入口：[internal/game/rpc/game_server.go](../internal/game/rpc/game_server.go)。

### 31. ClientConn、stream 和 TCP 连接是什么关系？

ClientConn 管理 gRPC 目标与底层连接，HTTP/2 可复用多个流。当前每玩家会话一个 Channel stream，不等于每玩家新建一个独立 ClientConn。

### 32. BIND 为什么必须第一帧？

先建立流与会话身份，后续才能正确路由与下行。没有 BIND 的业务帧不应被猜测处理，也不能信任每帧任意携带的 session_id。

### 33. 服务注册路径在哪里看？

看 registry.go 实际构造 `/services/<service>/<node>`。配置中的 service_prefix 注释不一定被主路径使用；不要照设计字符串查询一个不存在的前缀。

### 34. 注册地址为何不能是 0.0.0.0？

0.0.0.0 是本地所有接口的监听概念，不是其他容器应拨号的服务地址。当前 Compose Game 使用 game:9100；更通用方案应拆监听和公布地址。

### 35. etcd 租约与心跳解决什么？

保活让注册信息随服务失活过期，减少发现旧节点。它不保证应用所有依赖健康，也不让已经建立的 stream 自动完成玩家状态迁移。

### 36. Watch 前为什么还需要 List？

Watch 主要观察变化，客户端还需要当前快照。可靠实现还要把快照 revision 与后续 Watch 衔接，处理断线和 revision compact，而不只循环监听。

### 37. gRPC Send 返回就代表业务提交吗？

不代表。它属于传输层进度，不是对端 Actor 已处理或 SQL 已提交。需要协议层响应或明确的业务提交确认。

### 38. 流 map 加锁就允许任意并发 Send 吗？

锁仅保护查找和增删映射。对同一流的发送并发与顺序要独立约束，通常使用每流单写者或发送锁，并考虑停止时正在写的任务。

### 39. 跨服节点为什么不需要被 Gateway 发现？

客户端请求先到 Game，Game 再按分组/配置建立 CrossService。Cross 面向游戏节点提供房间能力，不承担外部玩家登录接入。

### 40. 启动成功为何先看到 DNS 零地址告警？

业务容器和 DNS/目标监听可能尚未就绪，连接有退避重试。短暂告警后建立流是预期恢复路径；长期持续则查服务名、网络与目标状态。

## Actor、模块与预加载

源码入口：[internal/game/player/actor.go](../internal/game/player/actor.go)。

### 41. 网络消息和 Actor 消息为什么两套类型？

网络需要稳定序列化协议与数字 ID；进程内消息可以使用 Go 类型表达 Bind、Save、Grant。两者在 Game 入口转换，避免把网络细节传遍状态逻辑。

### 42. 为什么建角协议不完全走玩家 Module？

没角色时就没有可用玩家 State，建角是会话级账号操作。1010/1020 在 Game 入口处理，再创建/绑定 Actor。已有角色重进也需走该入口。

### 43. Module 是每个玩家创建一次吗？

当前在 Game.Start 注册并共享。玩家私有字段应在 State 或按 player_id 索引的状态里；共享 Module 上放 currentPlayer 会造成跨玩家污染。

### 44. Registry 如何避免每次遍历全部模块？

注册时生成 msgID→Module 索引，Dispatch 直接查表。行为事件则按 EventAware 分发，二者不是同一套广播规则。

### 45. MsgID 注释会自动接好路由吗？

当前不会。buf 生成消息与 gRPC 代码；Module.MsgIDs 和 Registry.Register 仍需手工接入。生成器配置里的 TODO 不能当作已实现能力。

### 46. OnBind 成功日志意味着预加载完成吗？

不一定。bindPlayer 先发 BindMsg 后返回，Actor 之后执行预加载；当前发送者 PID 为空，Respond 没有建立 RPC 等待屏障。

### 47. 五查询并行是一次数据库往返吗？

不是。它们是独立查询，可能各占连接；理想耗时接近最慢项，但还受池等待、SQL 和网络影响。共同完成不代表相同事务快照。

### 48. 预加载替换 State 为什么值得检查？

构造时给旧 State 设置的 dirtyHook 不会自动转移到新对象。当前 `preload` 通过 `Actor.setState` 安装新 State 并重绑 dirtyHook；测试仍应验证在线变化进入 dirty 集合（见 `actor_dirty_test.go`）。

### 49. Actor 内禁止阻塞在当前实现中完全做到吗？

没有。onBind 的加载和 onSave 的 SQL 都可能阻塞该分片。接口注释描述目标，优化需要快照、I/O worker、完成消息与版本确认共同设计。

### 50. 收到 SaveMsg 为何还不能认为落库成功？

消息可能尚在队列、被丢弃或执行失败。当前 persistPlayer 发送后返回 nil，必须补 Commit 后 Ack 才能把调度完成与持久化完成对齐。

## SQL、约束与事务

源码入口：[pkg/db/db.go](../pkg/db/db.go)。

### 51. sql.Open 做了网络连通验证吗？

不一定，它主要创建池句柄。当前 pkg/db.New 随后用 PingContext 验证；连接失败应关闭已创建资源并返回可定位错误。

### 52. MaxOpen 越大越快吗？

不一定。过大可能把 MySQL 打满、增加锁竞争；过小又让查询排队。看 DB.Stats、慢查询和事务时间，以实际并发需求调整。

### 53. 为什么事务内不能顺手用 r.DB.Exec？

它可能借另一条池连接执行事务外 SQL，回滚不会覆盖这条写入。需要共同提交的语句必须走同一个 tx。

### 54. defer Rows.Close 以后还要 rows.Err 吗？

要。迭代中途可能发生错误，Next 返回 false 不只意味着正常结束。Close 负责释放资源，不代替传播读取错误。

### 55. SELECT FOR UPDATE 保护什么？

它在事务中锁住相关记录，串行竞争同一事实。锁是否足够还取决于索引、隔离级别和全部写入路径，不能保护 Redis 或已发客户端通知。

### 56. 邮件为什么同时校验 owner 和 status？

owner 防止越权，status 防止同一资源重复领取。两种条件保护不同不变量，不能只靠客户端隐藏别人的邮件 ID。

### 57. UPSERT 为什么依赖唯一索引？

冲突必须由主键或唯一键识别。player_item 的 player_id+item_id 唯一键使同种堆叠更新，而不是每次插入一个重复行。

### 58. CREATE TABLE 注释写分片键就分表了吗？

没有。当前许多 Repo 仍用固定表名。分库分表需要真实路由、迁移、跨表查询和运维机制，不能从注释推导已部署 512 张表。

### 59. Commit 错误等于肯定回滚吗？

网络错误可能使调用者无法知道数据库是否已提交。应按稳定业务键查询/重试，让结果收敛；不能立即再发一份新业务 ID 奖励。

### 60. 生成 model 等于迁移数据库吗？

不是。gendb 生成 Go 结构和 CRUD，已有数据库还需执行受控 DDL。Docker 初始化目录也只在空数据库卷首次初始化时执行。

## Write-Behind 与恢复

源码入口：[pkg/flush/flusher.go](../pkg/flush/flusher.go)。

### 61. dirty 集合是消息日志吗？

不是。它把同一玩家多次修改合并为待保存状态，无法重建每一次历史动作。需要审计与故障重放的业务应有独立事实记录。

### 62. 加载和 AddItem 为什么要分开？

初始化不应制造一次真实发奖或无意义全量回写。Repo.Load 使用 SeedItem；其他加载路径还应核对回调与标脏，不能只看一个函数。

### 63. 为什么归零物品不能只从 map 删除？

数据库行仍存在。dirtyItems 需要保存已触碰 ID，即使当前数量为零，保存时才能生成 DELETE，避免重登复活。

### 64. 保存失败应什么时候清脏？

只有本次版本提交成功后清；失败保留或重新标脏。异步保存期间的新修改不能被旧确认一并清除，需要版本化或快照归属。

### 65. 当前 FlushAll 是否一定清完全部玩家？

不能这样保证。它每片调用一次 flush，单次只取 batch；再加持久回调只投 SaveMsg，名字中的 All 不等于 SQL 已全部提交。

### 66. interval 改成 5s 是否就每 5 秒保存？

当前 nextTick 按分钟边界算下一次时刻，配置与实际调度不完全一致。先对调度函数写可控时钟测试，再修改参数与承诺。

### 67. Write-Behind 会不会丢掉回包后的进度？

进程在持久提交前崩溃就可能丢，具体窗口由调度、队列和失败重试决定。受控下线保存不能覆盖 kill -9。

### 68. 墓碑删除的价值和边界是什么？

让物理删除集中合批、失败可回填。没有注入 DeleteFn 时当前实现会丢弃墓碑并计指标，不能假定所有登记都会最终删除。

### 69. 什么时候需要 Outbox？

当数据库事实与外部消息必须可恢复关联时，可在同一事务写事实与 outbox，由投递器重试发布。它解决提交和发布的缺口，消费者仍需业务幂等。

### 70. 怎样证明停服保存可靠？

停止接收后，等待已接受消息和每个保存 Commit 确认，覆盖超过 batch、SQL 失败与超时；重启后重新查询验证。仅调用 FlushAll 或看到 stopped 日志不足。

## Kafka、Redis 与幂等

源码入口：[pkg/mq/kafka.go](../pkg/mq/kafka.go)。

### 71. biz_id 应每次重试重新生成吗？

不应。它代表同一业务事实，重复投递要复用。每次换 ID 等于告诉消费方这是另一笔操作，破坏去重。

### 72. partition key 与 biz_id 一样吗？

用途不同。key 用于分区和相关事件路由，biz_id 用于业务识别；它们可相同但不必相同。选择玩家 key 仍需明确同玩家事件的执行顺序。

### 73. 手动 commit 带来什么？

允许把 offset 提交放在业务处理之后。业务提交后、offset 提交前崩溃仍会重投，所以并不能只靠手动 commit 得到一次性副作用。

### 74. Redis SETNX 为什么不能证明一次且仅一次？

去重标记和业务提交不在同一事务。标记后副作用前崩溃会阻止重试，副作用后的回滚标记又可能重复，需要可恢复业务事实。

### 75. Forget 幂等键能修复所有失败吗？

只能让已知处理失败再次尝试，无法在进程骤停时主动运行，也不能分辨提交结果未知。部分副作用已发生时删键还可能放大重复。

### 76. 死信写入失败后应提交吗？

需要先有可靠转交确认，否则原消息提交后就可能没有恢复来源。当前 Consumer 忽略 DeadLetter 错误并继续提交，是需要修正的边界。

### 77. Kafka 是离线玩家背包数据库吗？

不是。它传业务事件，离线暂存、最终存档与补投是应用责任。已消费 offset 也不证明玩家物品最终保存成功。

### 78. Presence 指向节点就一定在线吗？

只是带时效的路由线索，可能过期或清理滞后。发送方需处理节点不可达与玩家已离线，不能把一个 Redis 值当作端到端送达凭据。

### 79. IDTable 未构建完可以返回不存在吗？

不能随意这样做，否则把索引未就绪当作实体不存在。当前设计保留 ready 状态和 DB 回退，需要检查所有使用路径是否遵守。

### 80. 为什么 Kafka 本机连 9093 而不是 9092？

Compose 配置双 listener，broker 返回给宿主机的地址必须可达；内部 kafka:9092 只在容器网络解析。bootstrap 可连不代表 advertised 地址可用。

## 玩法与跨服

源码入口：[internal/game/module/battle/battle.go](../internal/game/module/battle/battle.go)。

### 81. item_uid 当前始终是实例主键吗？

背包使用路径把它转为配置 itemID，体现当前堆叠简化。装备 UID 则是实例标识，不能把两个模块的同名字段不加辨别地共用。

### 82. bag.Use 现在会给所有物品执行完整效果吗？

不会。当前主要做配置检查、扣除、标脏、事件和背包通知。具备 AddExp 能力不代表该分支已经调用；需要针对道具类型扩展效果系统。

### 83. 任务为什么由行为事件推进？

减少 bag→quest 的直接依赖。bag 发 use_item，quest 订阅更新进度。事件的可靠性仍依赖执行与持久化，不能把进程内 Emit 当成消息日志。

### 84. 装备加成为什么登录时重算？

它可从已穿装备与配置重建，避免把派生 bonus 当作基础值长期累积。重算前清旧值，并测试重复登录不会重复叠加。

### 85. 组队成员上限为何不是玩家 Actor 能保证？

多个玩家的 Actor 会并行操作同一队伍。上限是共享实体不变量，需要锁定队伍事实或其他单一所有者，而不是每玩家各自检查。

### 86. 当前签到怎样避免直接 SQL 覆盖在线背包？

当前签到使用 Actor 注入的 CommitItems，把领取事实和背包一起提交，成功后才同步内存。若采用邮件奖励是另一种方案，必须单独解决邮件领取的提交窗口，不能混称同一实现。

### 87. Cross 房间与玩家完整存档是什么关系？

Cross 接受快照与战斗操作，Game 仍负责角色长期状态。迁移战场通信不等于搬迁玩家所有数据；结算回到 Game 还需幂等。

### 88. 当前战斗结果上报等于服务端全权模拟吗？

不是。应分别看结果校验、奖励白名单和房间超时。要做防作弊或完整回合引擎，需要额外实现规则、确定性重放与可信状态。

### 89. leader 为什么不能解决所有一致性？

它协调需要单主执行的任务，不能自动让其他 Repo、Redis 和客户端通知进入同一事务。leader 丢失和切换仍需防重复任务与处理半完成状态。

### 90. 参考项目的行军和 AOI 如何接入？

当前没有完整对应实现，可新增持久任务状态、坐标与空间索引，定时消息发给所属 Actor，恢复时按业务键补结算。它是扩展设计，不是替换几个函数名。

## 测试、部署与演进

源码入口：[scripts/docker-up.sh](../scripts/docker-up.sh)。

### 91. 普通 go test ./... 覆盖 integration tag 吗？

不覆盖带 integration 构建约束的测试。需要显式 -tags=integration 和 Docker，报告结果时区分普通单测、集成与冒烟。

### 92. 连接压测成功证明玩法容量吗？

不能。conn 模式主要测接入和保活，smoke 才触及部分业务。完整容量还需活跃率、消息大小、SQL、Actor、P99 和错误数据。

### 93. healthz、readyz、smoke 有什么差别？

分别偏向进程响应、实现定义的依赖检查与真实业务路径。readyz 没查到的依赖仍可能坏，业务代码也可能在探针 200 时出错。

### 94. 为什么当前 Docker 采用命名配置卷？

部署时发现宿主机目录共享等待，改用 docker cp 写入命名卷避开该依赖。它带来文件快照语义，配置改动后需要同步和必要的进程重启。

### 95. 私钥 0600 与 nonroot 镜像如何配合？

Gateway 使用启动用户的 UID/GID，复制密钥保留所有者。不能为了读到密钥把整个目录改为全员可写；也要避免把私钥 COPY 入镜像层。

### 96. 重新 docker-up 会自动升级已有表吗？

不会。首次空 MySQL 卷才跑初始化脚本；已有库应显式迁移。卷保存数据，镜像保存程序，二者版本演进需要协调。

### 97. stop_grace_period 设置大就会优雅保存吗？

不会。入口必须真进入 Shutdown，执行系统必须仍能处理保存，确认必须代表 Commit。当前 ctx.Err 路径和 SaveAck 缺失都需要先修正。

### 98. 如何定位 P99 升高？

先分接入、Actor 排队、处理时间、DB 等待、内部流与客户端写出；对照指标和 profile。不要看到慢就同时加 shard、加连接池、加 goroutine。

### 99. 生成代码和业务代码怎样一起维护？

修改 proto/XML/DDL 的源，再生成对应产物；SQL 迁移单独管理。检查生成差异与模块注册，不能手改 pb.go 后寄希望下次生成不会覆盖。

### 100. 怎样判断真的能从零实现这个项目？

能独立定义身份、协议与状态所有权；写出一条从客户端到提交再回传的闭环；测试重复、越权、超时与崩溃；还能指出未解决的边界，而不只复述目录名。
