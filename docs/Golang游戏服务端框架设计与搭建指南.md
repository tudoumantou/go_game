# Golang 游戏服务端框架设计与搭建指南

目标是在理解状态归属、请求链路和持久化边界的前提下，亲手搭建与当前项目对应的五服务后端。第一天就把五个进程和四个中间件全部写出来，会让每一次失败都变成跨系统排查；因此教程按可验证闭环推进。

## 1. 先写下四个约束

1. 客户端不能决定自己操作哪个账号或角色。身份必须从已验证会话获得。
2. 同一角色的状态修改必须有唯一的执行归属，先用单消费者理解，再实现分片 Actor。
3. 成功必须有定义：收到、入队、内存生效、SQL 提交是不同阶段。
4. 所有队列和后台任务都要有容量、失败行为和停止办法。

## 2. 分阶段搭建

| 阶段 | 做出来的东西 | 需要的依赖 | 验收 |
|---|---|---|---|
| A | 工程、配置、日志 | Go / YAML / zap | 配置错误能明确退出 |
| B | 长度包、TCP echo、Protobuf | net / codec | 半包、连包均可正确解析 |
| C | 应用握手、Token 登录 | RSA/AES、Redis、MySQL | 未鉴权操作被拒绝 |
| D | 单进程玩家消息循环 | channel / map | 同玩家串行、不同玩家隔离 |
| E | 模块、建角、背包、存档 | SQL 事务、静态表 | 创角后能查询和使用物品 |
| F | 网关与 Game 拆分 | gRPC / etcd | BIND 后双向请求回传 |
| G | 邮件、充值、聊天 | Kafka、业务幂等 | 重试不会随意扩大副作用 |
| H | Center 与 Cross | 注册、匹配、房间 | 两个角色能进入同一房间 |
| I | 监控、容器与回归 | Prometheus / Docker | 冒烟、故障与重启验证 |

教程章节顺序为方便阅读，内部通信放在 Actor 前讲清协议边界；练习时允许暂时使用进程内接口，等单进程闭环稳定后再替换成 gRPC。

## 3. 服务拆分按职责，不按代码量

Login 管账号与 Token；Gateway 管连接和加密；Game 管角色和玩法；Center 管协调；Cross 管房间。拆服务会增加网络失败、身份传递和可观测成本，不会自动提高性能。

最小实验只需要“客户端 → 一个游戏进程 → 内存状态”。先抽象 Sender 和 Repo 接口，就能在不重写玩法的情况下逐步替换网络和数据库实现。

## 4. 从一条协议反推框架

假设要实现“使用经验道具”：

```text
请求 UseItemReq(item_id, count)
  → 从会话获取 player_id
  → 投递给玩家 Actor
  → 验证 count > 0 与配置可使用
  → 检查背包数量
  → 扣除物品并增加经验
  → 标脏 / 发行为事件
  → UseItemResp + 必要的等级推送
```

这条链路要求协议、身份、路由、状态、规则、持久化、回包七种能力。先做出这条纵向链路，比先造几十个空模块更容易判断架构是否可用。

## 5. 把变化点变成能力接口

教学片段，放在练习工程自己的业务包中，说明“业务依赖能力”这一原则：

```go
// 不让玩法模块持有 net.Conn：连接断开和序列化不是背包规则。
type ReplyFunc func(msgID uint32, body []byte) error

// 不把 *sql.DB 传遍所有函数：业务先说明需要什么数据能力。
type Inventory interface {
    GetItemCount(itemID int32) int64
    RemoveItem(itemID int32, count int64) bool
}

// 返回 bool 表达“规则拒绝”，网络和数据库错误另行传播。
func TryConsume(bag Inventory, itemID int32, count int64) bool {
    if itemID <= 0 || count <= 0 { // 客户端输入永远先校验。
        return false
    }
    return bag.RemoveItem(itemID, count) // 检查与扣除交给同一状态所有者。
}
```

接口应围绕调用方需要的能力设计。当前 `module.PlayerState` 更宽，方便多个模块复用；新功能可进一步收窄。不要为了“面向接口”给每个函数都造一层没有用途的抽象。

## 6. 并发、事务与幂等分别解决什么

Actor 让一个角色的消息串行；事务让同一数据库内的一组写入共同提交；唯一键让重复业务事实不能出现两份；Redis SETNX 能减少重复处理，却不与 MySQL 跨系统原子提交；Kafka 负责消息输送，消费完成仍需业务定义。

它们必须配合。例如邮件状态已经提交、奖励尚未写入背包时崩溃，即使同一 Actor 全程没有并发，依然存在业务缺口。

## 7. 让每个阶段能独立验证

- 纯函数测边界：长度、序号、日期、奖励配置。
- 状态机测非法顺序：未握手、未鉴权、未建角。
- 存储测原子性：第二条 SQL 失败后第一条是否回滚。
- 网络测真实链路：机器人从 Login 到 Gateway 再到 Game。
- 恢复测持久性：不能只看在线回包成功，还要重读数据库或重启后查询。

当前仓库的 benchmark 数字和设计目标不能当作容量承诺。先记录固定环境下的基线，再调整一个因素。

## 8. 什么时候加入新玩法

当“角色信息”已能经 Actor 到客户端，新增模块通常不需要改网关业务规则，但需要显式注册 MsgID 和 Module。协议号来自约定，不是 proto 注释会自动完成分发。

从[签到实战](新增功能开发流程（以签到为例）.md)开始练习：先做查询与七日历法，再把签到事实与背包奖励放入同一事务，最后写重复请求与提交后断线的测试。
