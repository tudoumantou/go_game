# R9 场景 Actor 与 AOI —— 结构设计

> 状态：方案稿，未实施。
> 前置约束来自计划 R9.3：**场景内存由场景 Actor 管理，玩家 Actor 不能跨 goroutine 修改场景实体**。

## 1. 现状

| 项 | 状态 |
|---|---|
| `pkg/actor` | **通用的**：`Spawn(id string, actor Actor)`，`Actor.Receive(ctx *Context)`，消息是 `any`。不绑定玩家 |
| `actor.System` | 按 `id` 做 FNV 哈希分片；`scene:1` 与 `1001` 天然落在不同分片，跨 shard 消息走 `Send` 投递 |
| `internal/game/scene/` | 空目录，只有 `.gitkeep` |
| `configs/gamedata/xml/scene.xml` | 只有 `id` + `col1=名字`，**没有尺寸、人数、格宽** |
| `player.scene_id` / `Profile.SceneID` | 字段已存在，**零引用** |
| 坐标 | 无任何字段 |
| 4000–4999 消息段 | **完全空闲**（当前占用 1xxx/2xxx/3xxx/5xxx/6xxx/7xxx） |
| 心跳 | 只有网关层的客户端心跳（`MsgIDHeartbeatReq`），**没有玩家 Actor ↔ 场景 Actor 的内部心跳** |

结论：不需要改 `pkg/actor`，场景 Actor 直接挂在现有 System 上即可。

## 2. 结构

```
                    ┌──────────────────── actor.System（1024 分片）────────────────────┐
客户端 ── 网关 ──▶  │  Shard A: player:1001  (玩家 Actor)                              │
                    │            │  EnterScene/MoveTo/LeaveScene（Send，异步投递）      │
                    │            ▼                                                      │
                    │  Shard B: scene:1      (场景 Actor)                               │
                    │   ├─ grid   九宫格索引                                            │
                    │   ├─ ents   playerID → {x,y,视野集合,PID}                         │
                    │   └─ subs   playerID → *actor.PID（广播目标）                     │
                    │            │  EntityAppear/Move/Leave（Send 回玩家）              │
                    │            ▼                                                      │
                    │  Shard A: player:1001 → 回包客户端                                 │
                    └───────────────────────────────────────────────────────────────────┘
```

玩家 Actor 只做三件事：**转发协议 → 场景**、**场景推送 → 回包**、**下线 → 通知离场**。它不持有可写的位置。

场景 Actor 是位置的唯一权威。两个 Actor 之间只有消息，没有共享指针——这是 R9.3 那条约束的落地方式。

## 3. 权威边界（最容易做错的地方）

| 数据 | 权威 | 玩家 Actor 里的副本 |
|---|---|---|
| 坐标 x/y | **场景 Actor** | 只读缓存，用于落库采样，不可参与判定 |
| 所在场景 | 玩家 Actor（`Profile.SceneID`） | 以「最近一次 `SceneEntered` 的 sceneID」为准 |
| 视野内实体 | **场景 Actor** | 不持有 |
| 名字/等级（广播用） | 玩家 Actor，进场景时随消息带上 | — |

**切场景时会出现短暂的「双份实体」**：旧场景的 `LeaveScene` 与新场景的 `EnterScene` 是两条独立消息，跨 Actor 没有全局顺序，旧场景可能仍认为玩家在场。

处理方式不是加锁，而是**按当前 sceneID 过滤推送**：玩家 Actor 只接受 `Scene.Push{SceneID}` 且 `SceneID == 自己当前场景` 的推送，旧场景的残留推送直接丢弃。旧场景的幽灵实体由心跳超时清理（见 §6.3）。

## 4. 消息契约

### 4.1 Actor 间消息（内部，不占客户端协议号）

| 消息 | 方向 | 载荷 |
|---|---|---|
| `EnterScene` | 玩家 → 场景 | `PlayerID, PID, Name, Level, X, Y` |
| `SceneEntered` | 场景 → 玩家 | `SceneID, X, Y, Entities[]{ID,Name,Level,X,Y}` |
| `EnterRejected` | 场景 → 玩家 | `Reason`（场景满 / 坐标非法） |
| `MoveTo` | 玩家 → 场景 | `PlayerID, X, Y, ClientSeq` |
| `MoveRejected` | 场景 → 玩家 | `X, Y`（当前权威坐标，客户端回滚） |
| `LeaveScene` | 玩家 → 场景 | `PlayerID` |
| `SceneHeartbeat` | 玩家 → 场景 | `PlayerID`（每 30s） |
| `EntityAppear` / `EntityMove` / `EntityLeave` | 场景 → 玩家 | 实体快照 / `ID,X,Y` / `ID` |
| `SceneSync` | 场景 → 玩家 | 全量实体快照（重连、漏包补拉） |
| `QueryPos` | 玩家 → 场景 | 请求当前坐标（下线前采样） |

### 4.2 客户端协议（4000 段）

| 号 | 消息 | 说明 |
|---|---|---|
| 4001/4002 | `SceneEnterReq/Resp` | 进入指定场景；Resp 带场景 ID、自己的坐标、人数 |
| 4003/4004 | `SceneMoveReq/Resp` | 上报**目标坐标**（不是方向），Resp 只回 code |
| 4010 | `SceneEntityNotify` | 实体出现/移动/离开（三类合一，带类型枚举） |
| 4020/4021 | `SceneSyncReq/Resp` | 主动全量同步（客户端发现自定义序号断档时用） |

移动用「目标坐标」而不是「方向 + 步长」：方向式需要服务端跑同样的运动积分，两端浮点误差会让位置长期漂移；目标式由服务端直接采纳并钳制，简单且可校验。

## 5. AOI：用视野集合差集，不是格坐标差集

实体进入某个格子后，视野 = 周围 3×3 格。

**错误做法**：跨格时比较「旧格坐标集合」与「新格坐标集合」，差集推 Enter/Leave。
**为什么错**：A 在格 (5,5)、B 在格 (6,5)，两者相邻可见。A 移到 (6,5) 时，旧 3×3 与新 3×3 的格坐标差集不为空，但 B 始终在 A 的视野里——会误发一对 Leave/Enter，客户端出现实体闪烁。

**正确做法**：

```go
oldView := setOf(entitiesIn(a.oldCells))   // 旧视野内的实体集合
newView := setOf(entitiesIn(a.newCells))   // 新视野内的实体集合
for id := range newView - oldView { push EntityAppear to a }
for id := range oldView - newView { push EntityLeave  to a }
// 对称：对进入/离开视野的每个实体，反向推 a 的 Appear/Leave
```

即以「实体集合」为差集单位。同一格内移动不触发任何 Enter/Leave，只推 `EntityMove`。

**不变量**（验收要断言的）：
1. 同一对实体，`Appear` 与 `Leave` 必须成对，且不重复。
2. 玩家 A 看到 B ⇒ B 也看到 A（视野对称，格子边界内保证）。
3. 离开场景/断线后，场景内其他玩家必收到该实体的 `Leave`。

## 6. 生命周期

### 6.1 进入

```
客户端 SceneEnterReq → 玩家 Actor
  → 校验场景存在、玩家当前无场景（或先走切场景）
  → EntryScene 消息投递给 scene:<id>
场景 Actor：
  → 人数上限校验（scene.xml）
  → 坐标钳制到地图边界
  → 加入 grid，计算视野集合
  → 回 SceneEntered（含视野内实体快照）
  → 向视野内其他玩家推 EntityAppear
玩家 Actor：回 SceneEnterResp，更新 Profile.SceneID
```

### 6.2 移动

```
SceneMoveReq(x,y) → 玩家 Actor → MoveTo 投递场景
场景 Actor：
  → 边界校验（钳制而非拒绝，避免客户端撞墙卡死）
  → 速度校验：dist > maxSpeed × Δt → 拒绝并回权威坐标
  → 更新 grid，若跨格 → 走 §5 的差集
  → 同格 → 只向视野内推 EntityMove
  → 自己回 MoveAck（带权威坐标与服务端序号）
```

速度校验用「上次移动时间戳 + 最大速度」，超速时**钳制到合法位置**而不是直接拒绝：拒绝会在丢包时让客户端反复卡住。钳制同时记一次指标，用于识别外挂。

### 6.3 断线清理（三条路径，缺一不可）

| 路径 | 触发 | 可靠性 |
|---|---|---|
| 正常下线 | 玩家 Actor 收到 `UnbindMsg` → 发 `LeaveScene` | 高 |
| Actor 终止 | `Terminate` 前发 `LeaveScene` | **可能失败**（信箱满 / 对端已终止） |
| 心跳兜底 | 场景 90s 未收到该玩家任何消息 → 强制移除 | 最终一致 |

心跳兜底不是可选项：`actor.Send` 在对端终止后返回 `ErrActorGone`，前两条路径都可能静默失败，没有兜底就会留下永久幽灵实体——它会占名额、会向别人广播、还会挡住自己重进场景。

### 6.4 重连

重连走「进场景」同一条路径（不是恢复旧会话）：玩家 Actor 从快照取 `Profile.SceneID` 与缓存坐标 → 重新 `EnterScene` → 拿到全量 `SceneEntered`。这样不需要「断线期间位置保留」的复杂语义。

### 6.5 限频

客户端移动消息限频（默认 10 次/秒，令牌桶），超出直接丢弃并计数。不加限频时，一个恶意客户端就能占满场景 Actor 的邮箱。

## 7. 持久化：只存场景归属，不存坐标

| 数据 | 存放 | 落库时机 |
|---|---|---|
| `SceneID` | `Profile.SceneID`（已有字段 → `player.scene_id`） | 进/切场景时标脏 |
| `x/y` | **不持久化** | — |

位置**不落库**，重登后回到客户端自己指定的落点。理由：

1. 位置不是资产。绝大多数 MMO 重登回绑定/主城，而不是精确坐标。
2. 若落库，要么每次移动标脏（R2.1 契约是「一条消息 = 一次 CAS」，每秒 10 次移动就是 10 次 Redis 写），要么加 30 秒定时采样——两者都要引入额外的快照字段与定时器。
3. R9.1 是「最小闭环」，先把链路跑通；需要「副本内断线回原位」时再加 `Ext["scene_pos"]` 采样，届时只动场景模块。

**已知限制**：玩家下线再上线，坐标由客户端重新指定，服务端不记忆。

## 8. 失败与降级

| 场景 | 处理 |
|---|---|
| 广播时目标信箱满（R1.1 会拒绝） | 记指标 `scene_push_rejected`，**不重试**。玩家 Actor 发现服务端序号断档 → 主动请求 `SceneSync` 全量同步 |
| 场景 Actor 信箱满 | 进入/移动消息投递失败 → 回「场景繁忙」；玩家停在原地，客户端可重试 |
| 场景 Actor panic | 由 shard 恢复；场景实体全部丢失，在线玩家下次移动时因「实体不存在」被要求重新进入 |
| 人数超限 | `EnterRejected`，玩家留在当前场景（不踢下线） |
| 坐标非法（NaN/负数/超界） | 钳制；钳制前后差异过大时按超速处理 |

广播不重试是刻意的：信箱满说明消费不过来，重试只会加剧拥堵。AOI 的正确性兜底是「全量同步」，而不是「保证每条推送必达」。

## 9. 落地拆分

四个提交，每个都可独立验证（对应计划 R9.1–R9.4）：

| 提交 | 内容 | 验收 |
|---|---|---|
| **R9.1 场景骨架** | `scene.xml` 扩列（宽/高/格宽/人数上限）、`scene.proto`（4001–4010）、`SceneActor`（进入/离开/移动/边界与速度校验）、位置落库、`module/scene` 做协议转发 | 两人进同一场景互见；越界被钳制；人数上限拒绝；重登回原位 |
| **R9.2 AOI** | 网格索引、视野集合差集、`EntityAppear/Move/Leave` 三件套、序号 | 相邻格跨格**不误发** Leave；同格只推 Move；三人交叉移动 enter/leave 成对 |
| **R9.3 生命周期** | 心跳兜底、断线清理、`SceneSync` 全量同步、切场景交接、限频 | 强杀客户端后 90s 内实体消失；切场景不出现双份；限频生效 |
| **R9.4 跨服场景** | 暂不做 | 标注为后续（现有 `internal/cross` 是战斗房间，不是地图） |

`internal/cross/scene/` 保持空目录（计划 R9.4 明确要求「不把跨服战斗房间误认为地图/AOI」）。

## 10. 已确定的决策（2026-10-19）

| 问题 | 结论 |
|---|---|
| 坐标与碰撞 | **整数格坐标**，无碰撞、无寻路，只做边界钳制 + 速度校验 |
| 移动协议 | **目标坐标 + 服务端钳制**（不做方向式） |
| 人数上限 | **30，写在 `scene.xml`（可配置）** |
| 位置落库 | **不落库**（见 §7），重登由客户端指定落点 |
| 队友/公会广播过滤 | 暂不需要 |

## 11. 明确不做

- 寻路（A* / NavMesh）、碰撞体、地形高度
- 服务端战斗演算与防作弊判定（计划里已单列为另一个后续设计）
- 同屏人数压测结论：R9 验收要求「不预先承诺未经实测的 MMO 容量」，容量靠机器人实测后另写
- 跨服地图（`internal/cross/scene` 保持空）
- 客户端预测与插值：协议设计留了 `ClientSeq` 和服务端序号，但客户端侧的平滑属于客户端工作

### R9.2（2026-10-19）已完成：九宫格 AOI

| 项目 | 落地 |
|---|---|
| 索引 | `grid: 格键 → 实体集合`，格键 = `cx<<32\|cy`；空格子即时回收 |
| 视野 | 3x3 格内实体集合（越界邻居跳过，地图边缘视野自然变小） |
| 差集 | `newView - oldView` / `oldView - newView`，**以实体集合为单位** |
| 推送 | 新增可见双向 Appear、离开可见双向 Leave、仍在视野只推 Move |
| 限频 | 每实体每秒 12 次移动，超出回 4007（按实体计，不按连接） |

**为什么不用「格坐标差集」**：A 在格 (5,5)、B 在 (6,5) 时相邻可见，A 移到 (6,5) 后
两份 3x3 的格坐标差集非空，但 B 始终在视野内——会误发一对 Leave/Appear，客户端实体闪烁。
`TestAdjacentCellNoFlicker` 专门守这条。

广播量实测：10 人分散在 5 列格子里，某玩家移动只推 3 条（视野内），不是全场景 9 条。

### R9.3（2026-10-19）已完成：生命周期

| 能力 | 实现 |
|---|---|
| 心跳 | 玩家 Actor 每 30s 向场景发 `HeartbeatMsg`（`player.SceneLink` 接口注入，player 包不认识 scene） |
| 兜底清理 | 场景每 30s 扫一次，90s 无消息的实体被移除并向视野内广播 Leave |
| 重连同步 | 绑定时由服务端主动 `Resync` 推一次全量视野，不等客户端发现断档 |
| 下线清理 | `OnLogout` 发 `LeaveMsg`（三条清理路径之一，另两条见上） |
| 切场景 | 先离旧场再进新场；推送按当前 `SceneID` 过滤，窗口期不串场 |

**心跳兜底不是可选项**：`actor.Send` 在对端终止后返回 `ErrActorGone`，
「下线时通知离场」这条路本身可能静默失败，没有兜底就会留下永久幽灵实体——
它占名额、向别人广播、还挡住自己重进。

**已知限制**：位置不持久化（§7）；重登后由客户端指定落点。

**速度校验**：`30 单位/秒 + 10 单位容忍`。超速时**不移动**、回权威坐标，而不是钳制到合法距离——钳制会让外挂靠高频小步前进绕过限制。
