# 02 目录结构与模块地图

> 这份文档是仓库的「地图」：每个目录放什么、模块怎么分、新增功能该往哪落。读完能回答三个问题——代码在哪、为什么在那、新模块怎么加。

## 1. 顶层目录

```text
game_study/
├── api/proto/          # 协议唯一定义处（buf 管理），按服务分目录
├── cmd/                # 七个进程的 main 入口，只做装配，不放业务
├── configs/            # 各服务 × 四环境（dev/test/docker/prod）的 yaml
│   └── gamedata/xml/   # 策划配置表源文件
├── deploy/             # docker / k8s / 监控（grafana + prometheus rules）
├── docs/               # 全部文档：架构研究（00-总览…80-优化与展望）、R2.x 契约、开发流程、各阶段方案、功能状态
├── internal/           # 业务代码，按服务分目录（Go internal 语义：仅本模块可用）
├── pkg/                # 公共能力，可被 internal 与 test 复用
├── sql/                # schema / migrations / seed 三段式
├── test/               # integration（带 tag）/ benchmark / robot 压测
├── tools/              # gendata / gendb / genmsgid / keygen / loadtest / newmodule
└── scripts/            # 构建与运维脚本
```

分层的规则很直接：**`cmd` 只装配、`internal` 按服务自治、`pkg` 放跨服务复用的能力、`api/proto` 是唯一协议源**。CI 第一步就是校验「`pkg/pb`、`pkg/gamedata`、`pkg/model` 这些生成物与源一致」，手改生成代码会直接挂（见 [60-测试体系/04](../60-测试体系/04-集成测试与CI.md)）。

## 2. internal/ 按服务划分

```text
internal/
├── center/     # 中心服：leader match rank milestone scheduler stats archive relay registry
├── common/     # 跨服务共用：constant（消息号/常量）、errcode（错误码口径）
├── cross/      # 跨服战斗
├── game/       # 游戏服：server_* 装配、player/、module/、scene/、rpc/、mq/、flusher/
├── gateway/    # 网关：router conn session backend
├── login/      # 登录服：handler service repo mq
├── scenemap/   # 独立 RPG 场景框架：aoi grid mgr room battle bridge gameplay entity
└── worldmap/   # SLG 地图：domain application runtime store view rpc spatial
```

`internal` 的语义是「仅 `game_study` 模块内可用」——服务之间不互相 import internal，跨服务一律走 proto + gRPC。这条边界让七个进程可以真正独立编译、独立部署。

## 5. 新增一个模块的正确姿势

`tools/newmodule` 是 `make new-module` 脚手架（提交 `c629225` 引入，当时顺带把 `server.go` 从 1397 行砍到 465 行），一条命令生成模块骨架：目录、`Data` 定义、`persist.go` 注册、handler 桩、测试文件。约定流程：

1. `make new-module name=xxx` 生成骨架；
2. 在 `api/proto/game/v1` 加协议，`make gen` 生成 pb 与消息号；
3. 业务逻辑写在模块文件里，handler 用 `module.Typed` 绑定（**不要手动回包**，有静态检查守着，见 [60-测试体系/03](../60-测试体系/03-约定测试与AST守护.md)）；
4. 用 `moduletest` 写单测，覆盖至少「正常路径 + 每个错误分支 + 幂等」；
5. `go test ./... && go test -tags integration ./...`。

## 6. 小结

地图的使用方法：**先按服务找 `internal/<服务>`，再按职责找子包；协议改动一律从 `api/proto` 开始；新增模块走脚手架**。每个包的深入内容在对应分层文档中，本文只建立空间感。
