# 01 工程骨架与最小可运行程序

[上一章](00-总览与阅读顺序.md) · [课程总览](00-总览与阅读顺序.md) · [下一章](02-配置日志错误码与数据库.md)

## 这一章做出什么

先在独立练习目录做出一个能编译、能等待信号、能正常退出的 Go 程序，再对照当前仓库理解入口如何装配服务。本章的最小程序无需数据库、Redis 或 Docker；现有仓库的 `cmd/game` 会连接真实依赖，两者运行条件不同。

完成后应能解释：module、package、二进制和进程分别是什么；为什么业务不写在 main 中；为什么收到退出信号还需要显式清理资源。

## 前置条件与源码入口

需要理解 Go 的 package、函数、import 和基本错误处理。本项目 [go.mod](../../go.mod) 声明 `module game_study`、`go 1.22`；具体依赖版本以该文件为准。

| 文件 | 本章重点 |
|---|---|
| [cmd/game/main.go](../../cmd/game/main.go) | 参数 → 日志 → 配置 → 运行 context → New → Start → Shutdown |
| [internal/game/server.go](../../internal/game/server.go) | 服务内部组件的创建、启动和关闭 |
| [scripts/build.sh](../../scripts/build.sh) | 构建目标、平台和版本注入 |
| [scripts/run-all.sh](../../scripts/run-all.sh) | 本机多进程启动顺序及日志位置 |
| [Makefile](../../Makefile) | 构建、生成、测试和部署命令 |

先在**现有仓库根目录**检查工具链：

```bash
go version
go env GOROOT GOTOOLDIR GOOS GOARCH
go build ./cmd/...
```

最后一条编译当前所有入口，验证代码能构建，不会启动服务，也不会将六个可执行文件输出到 `bin/`。仓库已提交生成代码，首次编译无需先安装 buf 或执行 `make gen`。

## 一、在练习目录创建最小程序

以下命令只在独立练习目录执行。不要在已有仓库再次执行 `go mod init`。

```bash
mkdir -p ~/go_game_lab/cmd/game
cd ~/go_game_lab
go mod init game_study
```

将下面的**完整教学实现**保存为练习工程中的 `cmd/game/main.go`：

```go
package main

import (
    "context"
    "log"
    "os"
    "os/signal"
    "syscall"
)

func main() {
    // 将 Ctrl-C / SIGTERM 转为 context 取消通知。
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()

    log.Println("game starting")
    <-ctx.Done() // 阻塞等待；不使用空循环占满 CPU。
    log.Println("game stopping")
}
```

在**练习工程根目录**执行：

```bash
go fmt ./cmd/game
go run ./cmd/game
# 看到 game starting 后按 Ctrl-C，应出现 game stopping。
```

接着构建并直接运行二进制：

```bash
mkdir -p bin
go build -o bin/game ./cmd/game
./bin/game
# 按 Ctrl-C，确认退出；随后检查上一条命令的退出码。
echo $?
```

预期退出码为 `0`。验证信号与退出码时优先运行构建后的二进制，便于直接观察目标进程。

这个程序只有生命周期，没有监听端口、加载配置或创建角色。不要用它的成功退出推断完整游戏服已经可用。

## 二、按职责扩展工程骨架

先创建实际需要的包，不必一次建立所有空目录。随着后续章节推进，工程会形成下面的边界：

```text
cmd/game/main.go           读取启动参数，装配并驱动服务生命周期
internal/game/server.go   Game 服务内部的组件组装
internal/game/player/     玩家 Actor、状态与存档
internal/game/module/     背包、签到等玩法
pkg/config/               YAML 配置加载
pkg/log/                  日志封装
pkg/db/                   MySQL 连接池与事务封装
configs/game/             Game 各环境配置
```

- `cmd` 下每个目录是独立的 `package main`，有自己的 `main()`。
- `internal` 由 Go 限制外部导入范围；业务分层和避免循环依赖仍需自行设计。
- `pkg` 在本项目中放基础组件与生成物，目录名本身没有特殊的语言权限。
- `configs` 是运行时文件，不会因为编译了 Go 程序就自动进入二进制。

`module game_study` 决定仓库内的 import 前缀，例如 `game_study/pkg/config`，不要求磁盘目录也叫 game_study。一个目录内的 Go 文件共同构成一个包；不同 `cmd` 目录都叫 main 不冲突。同一目录写两个 `main()` 才会重复定义。

两个二进制即使导入同一个包，运行后也各有自己的内存。Login 的全局 map 不会被 Game 自动共享，跨进程通信需要后续章节的 HTTP、gRPC 或中间件。

第 02 章再引入配置、日志和数据库依赖，按需要添加实际 import 后执行 `go mod tidy`。不必在第一章把整份项目依赖复制到练习工程；也不要用 `go get ...@latest` 代替与当前项目版本的核对。

## 三、对照当前仓库的六个入口

当前仓库有五个服务入口和一个独立落库入口，构建脚本会生成六个程序：

| 入口 | 职责 | 默认配置 |
|---|---|---|
| `cmd/login` | HTTP 游客账号、Token、选服与订单 | `configs/login/login-dev.yaml` |
| `cmd/gateway` | TCP 接入、握手、会话与消息转发 | `configs/gateway/gateway-dev.yaml` |
| `cmd/game` | 玩家 Actor 和玩法 | `configs/game/game-dev.yaml` |
| `cmd/center` | 中心注册、匹配、排行等协调逻辑 | `configs/center/center-dev.yaml` |
| `cmd/cross` | 跨服战斗房间 | `configs/cross/cross-dev.yaml` |

Flusher 不承载客户端请求。当前缓存持久化路径应结合 [第 10 章](10-增量存档与数据一致性.md)阅读，不能把它与 `pkg/flush` 的旧链路混为一谈。

阅读 `cmd/game/main.go` 时按下面顺序追踪，不要先陷入玩法实现：

1. `flag.String` 定义 `-config`，`flag.Parse()` 后取得实际路径。
2. 配置尚未加载时先创建默认 logger，确保配置错误也能输出日志。
3. `config.Load` 读取 YAML；成功后按 `cfg.Log.Level` 重建 logger。
4. `signal.NotifyContext` 建立运行 context。
5. `game.New(cfg)` 创建服务对象，`srv.Start(ctx)` 执行内部装配并等待运行结束。
6. 入口准备独立的限时 context，调用 `srv.Shutdown(shutdownCtx)` 清理资源。

`Start` 在当前实现中是阻塞调用，后面的语句要等它返回才执行。main 中的 `bootstrap done` 日志出现在 Start 之前，不能将这条日志当作依赖连接成功或服务已经就绪的证据。

**当前代码的退出边界**：Game.Start 等待运行 context 取消后返回 `ctx.Err()`，而入口遇到 Start 非 nil 错误会调用 `os.Exit(1)`，因此正常信号退出也可能跳过后面的 Shutdown。读者应区分“已实现 Shutdown 编排”与“入口确实执行了 Shutdown”；第 14 章继续分析该路径。本章的教学最小程序不包含这个分支。

`signal.NotifyContext` 只发出取消通知，不会自动等待业务、保存玩家或关闭连接。`os.Exit` 也不会执行 defer。清理使用新的 `context.Background()` 加超时，是因为运行 context 收到信号后已经取消，继续复用它可能令清理一开始就失败。

## 四、构建现有项目与启动现有项目

以下命令均在**现有仓库根目录**执行。

### 只构建，不启动依赖

```bash
# 编译全部入口，检查是否可以构建。
go build ./cmd/...

# 仅输出本机可运行的 Game 二进制。
mkdir -p bin
go build -o bin/game ./cmd/game

# 输出当前机器平台的全部六个二进制。
./scripts/build.sh "$(go env GOOS)" "$(go env GOARCH)"
```

`make build` 调用 build.sh，默认目标是 **linux/amd64**。在 macOS 上需要本机运行时，使用上面显式指定平台的命令；默认 Linux 构建用于目标部署环境。脚本为服务入口注入 `main.version`，并使用 `CGO_ENABLED=0`、`-trimpath` 等构建参数。

### 查看参数与实际运行

```bash
# 查看参数后退出，不会连接数据库。
go run ./cmd/game -h

# 启动真实 Game：需要配置中指定的依赖已经可用。
go run ./cmd/game -config configs/game/game-dev.yaml
```

配置默认路径及配置内的其他相对文件路径受当前工作目录影响。在本章统一从仓库根目录运行；将二进制复制到其他目录后，应同时核对配置、密钥等资源路径。

想先体验完整链路，可按 [第 15 章](15-Docker部署与故障排查.md)执行 `make docker-up`，就绪后运行 `make smoke`。本机多进程路线使用 `make dev`、数据库初始化/迁移、密钥准备、本机平台构建，再执行 `make run-all`；该脚本运行的是已有 `bin/*`，不会替你编译，日志写入 `bin/logs/`。两条路线的完整准备步骤以部署章节和脚本为准。

## 怎么验证与定位错误

| 现象 | 先检查 |
|---|---|
| `go.mod file not found` | 是否在正确的工程目录下执行 |
| `main redeclared` | 同一包是否有重复 main，而非不同 cmd 目录冲突 |
| 配置文件不存在 | 当前工作目录和 `-config` 路径 |
| 连接 MySQL / Redis / etcd 失败 | 是否误将真实服务当成无依赖教学程序运行 |
| macOS 无法执行 bin/game | 是否用默认 linux/amd64 构建覆盖了本机二进制 |
| `compile: version ... does not match go tool version ...` | `go version`、GOROOT、GOTOOLDIR 是否属于同一套工具链 |
| 信号退出后没有 stopped 日志 | Start 返回值、入口错误分支及 Shutdown 是否可达 |

本章通过标准：练习程序可独立编译，打印 starting；Ctrl-C 后打印 stopping 并以 0 退出；现有仓库可编译全部入口；能说明构建成功、进程启动、服务就绪和业务冒烟分别验证了什么。
