## 按顺序实现

先实现 profile 只读模块，MsgIDs 返回 2001，读取 Context.State 的快照，marshal PlayerInfoResp，Reply 2002。它没有 SQL，便于先验证 Module 路由与下行。

再实现 Registry：注册时构建 msgID→Module 索引，重复 ID 启动期报错，Dispatch 只调用命中的模块。不能把每个请求广播给所有模块；但行为事件可以分发给实现 EventAware 的模块。

第三步实现 bag.List 和 bag.Use。当前源码的 count<=0 会归一化为 1，超过配置上限会截到上限；这与“直接拒绝非法数量”的设计不同。学习工程可以选择拒绝，但要保持协议语义一致。

当前 bag.onUse 主要扣物品、标脏、发 use_item 事件及背包通知，并没有实现所有类型道具的效果系统。Actor 上下文有 AddExp 能力，不代表此分支一定增加经验。

第四步静态配置从 XML 生成强类型数据，再编译进程序。当前生成字段仍可能叫 Col1/Col2/Col3；先查 XML 注释与模块解释，再使用，不能凭列号猜含义。可以增加业务适配层，把 Col3 包装成 MaxUseCount()。

第五步模块对象按服务共享，玩家对象在 State 或 player_id 索引里。生命周期接口 OnLogin/OnLogout 处理每玩家变化，Init/OnSave 的实际调用位置也需核对，不能把有接口等于入口必定调用。

```go
func (r *Registry) Register(m Module) {
	for _, id := range m.MsgIDs() {
		if old, ok := r.route[id]; ok {
			panic(fmt.Sprintf("msgID %d registered by both %s and %s", id, old.Name(), m.Name()))
		}
		r.route[id] = m
	}
	r.modules = append(r.modules, m)
}
```

```go
func (s *State) RemoveItem(itemID int32, count int64) bool {
	s.mu.Lock()
	if s.items[itemID] < count {
		s.mu.Unlock()
		return false
	}
	s.items[itemID] -= count
	s.dirtyItems[itemID] = true // 归零也要标脏：落库时转为 DELETE
	if s.items[itemID] == 0 {
		delete(s.items, itemID)
	}
	s.mu.Unlock()
	s.notifyDirty()
	return true
}
```

## 逐段解释与知识点

Context 不是万能全局变量，它是一次玩家消息处理所需能力的集合：State、Reply、Emit、AddExp。依赖注入使测试时可以捕获回复而不启动网关。

RemoveItem 的检查与修改在同一锁范围，归零时删除内存项，但 dirtyItems 仍保留该 ID，以便存档生成 DELETE。只从 map 删除而不记脏，会让数据库旧道具在下次登录复活。

State.Items 返回 map 副本，避免序列化或模块遍历时暴露原可写 map。快照不是事务，跨多次 getter 的一致性仍依赖调用时的 Actor 所有权。

生成器生成的常量和嵌入文件随二进制版本固定；热更另需版本切换机制。

## 怎么验证与定位错误

先用 State + 捕获 Send 函数测 profile 返回值；背包测试覆盖未知物品、不可使用、数量不足、归零、count<=0 归一化与上限截断等当前语义。

改 XML 后运行 `make gen-data`，确认生成差异，再构建镜像。只在容器外编辑 XML 不会修改已编译常量。

## 独立练习与通过标准

写一个独立查询模块，只返回当前背包总种类数，不访问 SQL，不持有 Session。通过标准：注册冲突可见，回复能被测试捕获，协议错误不会误改状态。
