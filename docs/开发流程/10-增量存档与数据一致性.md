## 按顺序理解与实现

### 1. 先给成功定义边界

消息投递成功只代表接受了工作；Redis Commit 成功代表缓存状态已提交；MySQL 事务成功才代表这次 SQL 存档已完成。客户端成功响应的承诺要对应实际路径，不能笼统称为“已经落库”。

同一玩家修改一百次，可以合并为待保存的最新状态。脏队列不是一百条业务事件的历史日志；需要审计的订单、奖励事实仍应单独设计。

### 2. 缓存路径：快照与脏队列一起提交

`Store.Commit(ctx, state, expected)` 校验快照，用 Lua 比较期望版本，递增版本并写入快照、加入脏队列。相关 key 使用同一 hash tag。版本不匹配返回 `ErrConflict`，避免旧状态直接覆盖新状态。

阅读 Actor 的缓存路径时，跟踪业务处理前的状态、处理后的快照、提交失败的处理及响应发出的时机。Redis 请求超时可能是“未提交”，也可能是“已提交但回包丢失”，不能把两者都当作安全重试同一奖励的依据。

`LoadCached` 仅在缓存缺失时尝试 SQL 回源；Redis 故障或缓存损坏会返回错误，不会直接拿旧 SQL 代替最新状态。`Store.Seed` 也会拒绝“脏队列中仍有任务但快照缺失”的不安全回源。

### 3. Worker：SQL 成功后按版本确认

`Worker.FlushBatch` 的顺序是：取一批待处理 ID → 读取快照和版本 → `Persist` 在 SQL 事务中保存 → 对每条记录按版本 Ack。

SQL 版本行用于阻止旧 worker 倒写；Redis Ack 也必须核对版本。若 worker 保存版本 V 期间玩家已提交 V+1，就不能因为 V 保存成功而清掉新任务。SQL 失败保留 Redis 待处理项；SQL 成功而 Ack 失败则可能重放，必须依靠版本控制保证安全。

模块扩展通过注册的 Persister 落库；独立 flusher 使用空白导入加载 `internal/game/module/register`。这类 init 用于注册元数据，与在 init 中启动数据库、网络 goroutine 的副作用不同。

### 4. 非缓存路径：等待 Actor 的真实保存结果

下面是 [persistPlayer](../../internal/game/server.go) 中的当前源码节选，前面已处理缓存模式和玩家不在线的分支：

```go
done := make(chan error, 1)
if err := s.actorSys.Send(pid, &player.SaveMsg{Done: done}); err != nil {
    return fmt.Errorf("player %d save: %w", playerID, err)
}
waitCtx, cancel := context.WithTimeout(ctx, saveAckTimeout)
defer cancel()
select {
case err := <-done:
    if err != nil {
        return fmt.Errorf("player %d save: %w", playerID, err)
    }
    return nil
case <-waitCtx.Done():
    return fmt.Errorf("player %d save ack: %w", playerID, waitCtx.Err())
}
```

`SaveMsg.Done` 已经存在，不是待实现方案。Actor 的 `onSave(ctx, msg)` 回执 `savePlayer` 的结果；非缓存保存事务处理基础属性与增量物品，成功后清理相应脏标记。Send 拒收、保存错误或确认超时都会返回错误，Flusher 据此保留重试机会。

等待超时不表示事务一定没有提交，也不自动撤销已投递消息。回执 channel 容量为 1，Actor 使用非阻塞通知，避免等待方离开后拖住分片。

### 5. 排空与进程生命周期一起看

`pkg/flush.Flusher.FlushAll` 已循环处理多批数据，并在失败、超时或没有进展时返回错误；`writebehind.Worker.FlushAll` 也循环排空各分区。不要再用“每次只取一批”推断 FlushAll 只处理一批。

Game.Shutdown 已使用阶段编排：停止新工作、排空 Actor、处理待落库任务、关闭组件。但当前服务 Start 返回 `ctx.Err()` 与 main 的错误退出分支可能使 Shutdown 不可达，详见 [第 01 章](01-工程骨架与最小可运行程序.md)和[第 14 章](14-测试监控与优雅停服.md)。

独立 flusher 的 `Worker.Run` 收到取消后返回 nil，入口关闭连接；它没有在退出时自动调用 FlushAll。未处理任务仍需由保留的 Redis 数据和后续 worker 继续完成，不能推断所有 SQL 已在退出前追平。

Redis 已提交、MySQL 尚未提交是缓存路径中的正常时间窗口。能否在故障后恢复，取决于 Redis 数据和队列是否保留、worker 是否继续消费；进程内脏 map 不具备同样的重启恢复能力。Redis 的持久化与容灾配置也属于承诺边界。

## 怎么验证与定位错误

在仓库根目录执行与本章相关的组件测试：

```bash
go test ./pkg/flush ./pkg/writebehind ./internal/game/player
```

重点阅读保存回执测试 `actor_save_test.go`、缓存失败与未知结果测试 `cache_actor_test.go`，以及 `pkg/writebehind` 的 Store/Worker 测试。带 integration 标签的测试另需 Docker，不将普通单测结果当作真实中间件验证。

排障时按成功边界逐层检查：Actor 是否接收 → Redis 版本是否递增 → 脏任务是否存在 → SQL 是否提交 → Ack 是否清理同一版本。不要直接删除 dirty 队列或用旧 SQL 覆盖 Redis 来“修好”积压。

## 独立练习与通过标准

在练习工程完成三个场景：SQL 失败后任务仍在；保存 V 时提交 V+1 不会误清新任务；待处理数量超过 batch 时能排空。再注入一次回执超时，解释为什么超时不等于未提交。

通过标准：能逐一指出投递、缓存提交和 SQL 提交的确认点；保存失败可观测且可重试；停止路径有预算和错误回报。
