## 按顺序实现

先做任务。定义接受→进行中→可领取→已领取状态，use_item 等行为由 Emit 产生，quest 实现 EventAware 接收。协议处理与行为事件是两种路由，不要为了一个任务直接让 bag import quest。

第二步做装备。区分配置 equip_id 和实例 UID；同配置可以有多个实例。穿戴校验角色归属、部位与重复状态，再修改数据库/内存加成。登录先清 bonus 再重算，避免重连时重复叠属性。

第三步做技能。定义学习条件、当前等级、升级消耗和上限；扣背包与技能等级的持久化边界要放在一张时序图上，不能把两步独立成功当作一个原子技能升级。

第四步做活动与商店。活动用 progress 和 reward_mask 表达进度与领取，位图需要检查 bit 范围；商店用服务端配置决定价格与限购，拒绝客户端传奖励价格。当前实现混合 DB 与内存，应读清失败补偿。

第五步做公会/队伍。多个玩家可能同时加入最后一个空位，各自玩家 Actor 串行仍会彼此并发，必须依共享实体的事务/行锁/唯一约束保护容量和成员关系。

```go
func (m *Module) OnEvent(ctx *module.Context, evt module.Event) {
	if m.repo == nil {
		return
	}
	recs, err := m.repo.ListByPlayer(context.Background(), ctx.State.PlayerID())
	if err != nil {
		return
	}
	for _, cfg := range gamedata.QuestCfgList {
		if cfg.Col2 != evt.Type {
			continue
		}
		// 未接取的任务不推进
		rec, ok := recs[int32(cfg.Id)]
		if !ok || rec.Status != statusDoing {
			continue
		}
		target := int32(cfg.Col3)
		next := rec.Progress + int32(evt.Delta)
		status := statusDoing
		if next >= target {
			next = target
			status = statusDone
		}
		if err := m.repo.Upsert(context.Background(), ctx.State.PlayerID(), int32(cfg.Id), status, next); err != nil {
			m.logger.Warn("quest progress update failed", "quest_id", cfg.Id, "err", err)
			continue
		}
		if status == statusDone {
			m.logger.Info("quest completed", "player_id", ctx.State.PlayerID(), "quest_id", cfg.Id)
		}
	}
}
```

## 逐段解释与知识点

Module 在多个 Actor 间共享，跨角色状态必须有清楚的锁或数据库事实。玩家 A 的 Actor 与玩家 B 的 Actor 各自单线程，不能防止双方同时给队伍加成员超上限。

数据库表有唯一键不代表所有容量不变量被保护。例如“一个成员不重复”与“总成员<=5”需要不同规则。锁定共享父行后再查询数量，是一种可行策略，要配合所有写入路径遵守。

装备 bonus 是可重建派生值，基础属性是长期事实；将 bonus 保存成基础属性后再登录重算，容易重复累计。静态配置的 Col 字段适合加语义适配方法。

参考项目里的城池、领地建筑与内政不在本项目完整实现里。它们可以沿同样模式扩展：持久任务状态、资源规则、结束时间、消息调度、提交确认；不要仅换协议名字就认为完成。

## 怎么验证与定位错误

集成参考 TestP6BGameplayFlow 涉及多类玩法，执行前确认 Docker 与超时预算。对每个新模块至少覆盖合法、规则拒绝、越权、重复和存储失败。

装备验证：重连两次属性不重复；任务验证：一次 use_item 增加恰当进度；组队验证：并发加入最后一个空位只有一个成功；商店验证：失败不会留下扣费而未发货的不可恢复状态。

## 独立练习与通过标准

从“任务、装备、公会”选一个，不看处理函数先写业务不变量和 SQL 约束，再对照实现指出保证在哪里成立。通过标准：能区分单玩家串行、共享实体并发和跨系统提交。
