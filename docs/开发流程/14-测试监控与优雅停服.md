## 按顺序实现

第一步把验证分成纯函数、组件、数据库集成和真实客户端四层。一个 codec 测试不需要 Docker；一个真实唯一键并发测试不能只用 mock；端到端测试不适合定位每个算术边界。

第二步让依赖可替换。Clock 使零点测试不需等待；Sender 捕获响应；Repo 注入故障；带缓冲 Ack 与 timeout 让测试可结束。避免 Sleep 一秒后假设工作完成。

第三步每个功能先写不变量：同角色不可并行修改、名字不能重复、邮件归属不能越权、保存失败保留脏状态。测试应试图破坏不变量，不能仅把实现里的常量复制一遍再比较。

```bash
# 普通组件与业务单测。
go test ./...
# 有并发改动或定位竞态时，有针对性运行。
go test -race ./pkg/actor ./internal/game/player
# 集成测试自己启动容器，使用明确 tag 与较长超时。
go test -tags=integration -timeout 20m ./test/integration/ -v
```

第四步定义三种探测：healthz 说明进程可响应；readyz 根据实现检查依赖；真实业务冒烟验证身份、路由和存档。三个层次不能互相替代。

第五步指标至少包括连接量、消息耗时、Actor 积压/丢弃、DB 等待、dirty 数量、保存耗时/失败、Kafka lag/重试/死信、跨服状态。高基数玩家 ID 不宜作为 Prometheus label，单玩家排查放日志字段。

第六步实现正常停止：停止新接入与新投递 → 摘除发现 → 等待已接受工作 → 保存确认 → 关闭内部流/MQ → 停 Actor/worker → 关 DB/Redis/metrics。每一步有剩余超时预算。

```go
// 教学片段：清理不能继承已取消的运行 context。
stopCtx, cancel := context.WithTimeout(context.Background(), 60*time.Second)
defer cancel()
// Drain 应先让接入停止；Flush 应等待真实提交；随后 Stop workers。
// 如果任一步失败，报告“未完成”，不要把它改成一条成功日志。
```

R1.2/R1.3 已把这三个缺口补上：保存有真实回执并按超时重标脏、`FlushAll` 循环排空多批、游戏服关闭改为 `pkg/shutdown` 编排的阶段顺序（摘注册 → 停 gRPC/消费者 → `actor.System.Drain` 排空在途 → worker 与 flusher 确认落库 → 停 Actor → 关组件），单步失败会以聚合错误返回而不是只打一条 Warn。缓存权威模式下关闭时必须先排空进程内 worker 的 Redis 脏队列，只调 `flush.Flusher` 是空转。

以上描述的是 Shutdown 方法内部行为。当前 Game.Start 在取消后返回 `ctx.Err()`，而 cmd/game 将非 nil 返回值视为启动失败并 `os.Exit(1)`，因此信号路径可能跳过 Shutdown；有关闭编排不代表入口一定执行了它。独立 flusher 退出时也没有自动调用 FlushAll。

这仍不等于「kill -9 零丢失」：只有实际执行且成功完成关闭编排，才能确认相应排空步骤完成；SIGKILL 会留下「Redis 已提交、MySQL 未落库」的窗口，只能靠重启后 worker 从脏队列重放，或独立 flusher 补写。两类边界要分开陈述，别用优雅关闭的结论覆盖强杀场景。

## 逐段解释与知识点

表驱动测试让边界清晰，但案例必须表达不同业务规则。t.Parallel 仅用于依赖隔离的测试；共享数据库和全局 metrics 注册表要避免互相污染。

race 检测的是被执行到的并发访存；它不发现“合法顺序但业务重发奖励”的逻辑 bug。数据库锁行为与提交结果还需要集成与故障注入。

如果 readiness 回调只查 DB/Redis，Kafka 和 Cross 断线仍可能返回 200。指标统计点也要看实际代码：Flusher 成功点若只是入队，就不能用它证明存档延迟。

停止必须控制顺序。运行 ctx 一旦取消可能让 Actor 分片先退出，此时再发 SaveMsg 没有消费者。因此实际改造往往需要分开的接入 context 和执行/清理生命周期。

## 怎么验证与定位错误

先运行组件测试，再跑本地机器人，再按改动范围运行集成测试。人为制造慢 SQL、Send 拒收、Commit 错误、DLQ 失败和客户端断线；观察系统能否恢复、能否停止、会不会静默报成功。

关服测试在一次性练习库中提交超过 batch 的脏玩家，然后受控停止，重启读 SQL 核对；另外单独测试强制中止，明确可接受的数据损失窗口。

## 独立练习与通过标准

写一个 fake PersistFunc，前两次失败第三次成功，证明错误会返回且任务仍可重试。通过标准：没有无限等待，成功指标对应真实成功点，停止后资源无残留。
