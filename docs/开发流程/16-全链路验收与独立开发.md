## 按顺序实现

先给每个服务和关键提交点留可查日志字段，不打印凭据。按下面顺序跑，不在失败时同时改五个配置。

| 步骤 | 请求/事件 | 应观察到的事实 |
|---|---|---|
| 1 | 游客登录 | account_id 与 Redis Token 映射 |
| 2 | 连接 9001 | 收到 ServerHello |
| 3 | KeyExchange / Finished | 双方密钥就绪，业务密文可解 |
| 4 | HandshakeReq 带 Token | Gateway 得到 account_id |
| 5 | BIND | Game 建立 session→account |
| 6 | 1010，无角色 | 返回 2003，连接继续有效 |
| 7 | 1020 创角 | player/attr 事务提交 |
| 8 | Actor Bind | 加载 State、模块 OnLogin |
| 9 | 2001 | 2002 返回对应角色资料 |
| 10 | 邮件列表与领取 | 归属正确，重复领取回 5002 |
| 11 | 背包查询/使用 | 数量变化与脏状态可追踪 |
| 12 | 断开/重连 | 索引清理、已有角色不重复创建 |

```bash
# 普通最小闭环，产生一个开发角色。
make smoke
# 多设备验证会创建更多游客，不在正式数据环境随意执行。
DEVICES=2 ./scripts/smoke.sh
```

其次把每个“成功”分类：HTTP 返回 Token；Gateway 验证通过；Game 接受消息；Actor 内存生效；SQL 提交；客户端收到。这些不是同一时间点。日志中显示 bound 不足以证明所有 OnLogin 已成功。

再做负向链路：错误 Token、重放密文、非法角色名、越权邮件、数量不足、数据库超时、断线后迟到回包。每种失败应说明由哪个服务拒绝，客户端能否重试。

最后做跨服链路：两玩家匹配 → Center 分配 → Cross 建房/绑定 → 操作与结果回推 → Game 奖励与排行。不要用“Cross 已启动”替代两玩家真实房间验证。

独立扩展请读[签到实战](../新增功能开发流程（以签到为例）.md)。先画业务事实，再确定协议、唯一键、事务、模块注册与测试，最后才复制代码。

## 逐段解释与知识点

smoke 模式主要验证登录、握手、创角、进入游戏和角色信息；它不自动覆盖邮件、充值、每种玩法与所有崩溃边界。integration 中不同测试各自建立更完整验证，命令名要与源码 Test 函数一致。

机器人已实现项目的加密和封包约定，比随便用 curl/netcat 发原始 TCP 文本更适合作为业务客户端。扩展机器人应支持异步推送穿插，不能每次固定读取下一包当作当前响应。

当前 RoleService 应用检查一个账号一个角色，没有 account_id 唯一约束；当前普通保存确认、邮箱丢弃与停服路径仍有边界。七日签到另有 CommitItems 事务能力，不应与普通 Write-Behind 混同。验收时主动写出这些限制，才能区分“demo 跑通”和“所有故障下正确”。

## 怎么验证与定位错误

排查顺序：客户端拿到什么 → Login 是否发 Token → Gateway 握手/鉴权 → etcd 节点地址 → Channel 首帧 → Game 的会话映射 → Actor mailbox → Registry 路由 → Repo 提交 → 下行 stream → Gateway 写出。

每步只选择一种证据：日志、抓到的协议类型、数据库行或测试断言。不要仅凭 Started 日志推导后续全成功。对新功能还要确认生成代码、迁移与模块注册没有漏掉。

## 独立练习与通过标准

完成签到后不看教程再做“每日一次兑换道具”，自己列接口、时间规则和测试。通过标准：能从空请求说明到响应与数据库全部实现，解释重复、超时、崩溃与重连，并能指出尚未解决的保证。
