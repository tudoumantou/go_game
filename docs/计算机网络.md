# 计算机网络：沿本项目学通信

## 1. 先分清三层握手

TCP 建连让两端建立可靠字节流；RSA/AES 应用握手派生会话密钥；Token 鉴权把连接绑定到账号。完成 TCP 三次握手并不表示已经登录，完成加密也不表示这个客户端有权领取某封邮件。

TCP 建连可用 SYN → SYN/ACK → ACK 理解。正常关闭是两个方向分别发送 FIN 并被确认，ACK 与 FIN 可以合并，因此抓包不一定恰好四个包。RST 是异常中止。TIME_WAIT 通常出现在主动关闭方，用于处理旧报文与最后确认的可靠性。

## 2. TCP 为什么会有半包与连包

TCP 不保留应用消息边界。一次 Write 的字节可能被多次 Read 取出，多次 Write 也可能在一次 Read 中一起出现。这不是“TCP 把 protobuf 搞坏了”，而是应用必须定义帧。

本项目帧：

```text
Length 2 字节 | MsgID 2 字节 | Seq 4 字节 | Body N 字节
Length = 6 + N，不包括 Length 自身；整数使用大端。
```

`codec.Packet.MsgID` 是 uint16，内部 gRPC MsgId 常用 uint32。定义协议号时必须符合外层范围。两字节长度字段和项目的总包大小限制也约束最大消息，不要直接发送大型资源文件。


源码节选：[pkg/codec/packet.go](../pkg/codec/packet.go)。这是现有包中的片段，依赖同文件类型，不是可单独运行的完整程序。

```go
func EncodePacket(p Packet) ([]byte, error) {
	if len(p.Body) > constant.MaxPacketSize-HeaderSize-LengthFieldSize {
		return nil, fmt.Errorf("body too large: %d", len(p.Body))
	}
	length := HeaderSize + len(p.Body)
	buf := make([]byte, LengthFieldSize+length)
	binary.BigEndian.PutUint16(buf[0:], uint16(length))
	binary.BigEndian.PutUint16(buf[LengthFieldSize:], p.MsgID)
	binary.BigEndian.PutUint32(buf[LengthFieldSize+2:], p.Seq)
	copy(buf[LengthFieldSize+HeaderSize:], p.Body)
	return buf, nil
}
```

逐句理解：先限制 body 大小，避免 uint16 截断；一次分配完整帧；明确字段偏移；copy 复制字节而不是发送 Go 对象地址。DecodePacket 的输入不含长度字段，切片起点传错会使 MsgID 与 Seq 全部错位。

## 3. 读缓存的解析状态机

```go
// 教学算法片段：buf 是连接私有的累计接收缓存。
for {
    if len(buf) < 2 { break }             // 长度字段本身还没有收齐。
    n := int(binary.BigEndian.Uint16(buf[:2]))
    if n < 6 || n > maxBody { return errInvalidLength }
    if len(buf) < 2+n { break }           // 半包：保留缓存等下一次 Read。
    payload := buf[2 : 2+n]
    owned := append([]byte(nil), payload...) // 异步投递前取得自己的副本。
    dispatch(owned)
    buf = buf[2+n:]                       // 连包：继续尝试解析下一帧。
}
```

这段展示算法，`dispatch/maxBody/errInvalidLength` 由练习程序提供，不是直接替换源码。源码的 processReadBuf 在回调后把缓存剩余内容前移。如果回调把引用原缓存的切片留给其他 goroutine，就必须核对复制发生在哪里；“Send 到 channel”不会深拷贝切片。

## 4. 为什么有两份 MsgID / Seq

外层字段用于传输框架识别；加密体内还包含 MsgID 与 Seq，SessionCipher 解密后读取内部值并执行防重放。客户端必须按机器人代码的相同规则封包，不能只加密 protobuf 后忘记内部头。

AES-GCM 密文包含随机 nonce 和认证标签，验证失败应拒绝继续处理。64 位滑动窗口记录已接收序号；它防止重复使用已见序号，不代表支付、签到等业务已经幂等。重新登录后序号空间会变化，业务幂等键仍需跨连接稳定。

当前握手是项目自定义方案。仅从同一条未认证连接接收 RSA 公钥，不能单独证明对端是可信服务器；生产身份认证还需另外设计。此处重点是读懂实现，不把它称为 TLS 替代品。

## 5. HTTP、TCP 和 gRPC 的分工

| 链路 | 协议 | 谁发起 | 本项目用途 |
|---|---|---|---|
| 客户端 → Login | HTTP JSON | 客户端 | 游客账号与 Token |
| 客户端 → Gateway | 自定义 TCP | 客户端 | 长连接、握手和业务包 |
| Gateway ↔ Game | gRPC 双向流 | Gateway | 首帧 BIND、上下行业务帧 |
| Game ↔ Center | gRPC Report | Game | 上报、匹配与控制消息 |
| Game ↔ Cross | gRPC Channel | Game | 战斗快照、操作与结算 |
| 服务 → Kafka | Kafka 协议 | 生产者/消费者 | 异步事件 |

不需要把 Game 的内部帧再做一遍客户端握手加密。当前内部连接使用 insecure transport credentials，部署到不可信网络需补传输保护和身份验证。

## 6. 流控与慢客户端

gRPC 流控会约束发送速度，Send 返回不等于对方业务已经处理。应用仍要限制待发队列、超时和消息总量。参见 [gRPC 流控说明](https://grpc.io/docs/guides/flow-control/)。

当前 Gateway.Conn.Send 同步 raw.Write；writeLoop 只等待关闭，没有真正消费配置里的有界写队列。因此慢客户端可能让调用发送的 goroutine 等待写超时。设计文档中的队列模型需要进一步实现与测量。

TCP Write 还要考虑短写与错误。多 goroutine 对 net.Conn 的方法调用与“多条业务消息按希望的顺序发送”是两个问题；完整帧写锁、单写者以及序号分配/写出顺序需要共同设计。

## 7. 超时分别解决什么

| 超时 | 防止的问题 | 不能替代 |
|---|---|---|
| 建连超时 | 目标不可达一直等待 | 已连接后的请求超时 |
| 读 deadline | 对端长期不发送 | 应用业务心跳与在线租约 |
| 写 deadline | 慢客户端阻塞发送 | 写队列容量管理 |
| 请求 context | SQL/RPC 工作超过预算 | 已提交副作用的回滚 |
| etcd lease TTL | 服务掉线后发现信息滞留 | 玩家会话失效策略 |
| Token TTL | 登录凭据长期有效 | 业务权限和单设备策略 |

配置字段存在不代表所有读写路径都已设置 deadline。核对 `SetReadDeadline`、`SetWriteDeadline` 实际调用位置，比看 YAML 字段更可靠。

## 8. Docker 网络排查

容器名是容器网络里的 DNS 名称；`localhost` 是当前进程所在容器。Kafka 不仅需要能连 bootstrap 地址，还需要它返回的 advertised listener 对调用方可达。因此内部用 kafka:9092，宿主机工具用 127.0.0.1:9093。

```bash
# HTTP 健康检查不是用浏览器访问 TCP 网关。
curl --fail http://127.0.0.1:8080/healthz
curl --fail http://127.0.0.1:9101/readyz
# TCP 探测只证明端口能连接，之后还需完成应用握手。
nc -vz 127.0.0.1 9001
```

练习：将 codec 测试里的完整帧拆成每次 1 字节输入，再把三帧拼在一起输入。验收必须得到三条完整消息且无额外消息；随后测试长度不足 6、超长包和中途断开。
