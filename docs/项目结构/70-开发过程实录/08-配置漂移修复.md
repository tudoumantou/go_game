# 70-08 配置漂移修复

> 专题：三处「运营照表调数值、玩家侧毫无变化，而且不报错」的配置漂移。
> 涉及提交：`cda0e9e`。
> 结论：三处全部对齐配置表；顺带补了一个真缺口（技能可无限升级）；三处变异全部被抓。

## 1. 为什么比缺功能更坑

提交信息的原话：

> 运营照表调数值、玩家侧毫无变化，而且不报错——比缺功能更坑。

缺功能是「没有」；漂移是「看起来有」。策划在表里把技能升级消耗从 100 改成 300，线上毫无变化，排查方向只会往「缓存没刷」「服务器没重启」跑，没人想到是**代码根本没读那张表**。

## 2. 三处漂移实录

### 2.1 skill_upgrade：线性公式顶掉了查表

**旧实现**：`cost = skill.Col3 * level`。而 `skill.Col3` 只有 0 和 5 两个取值——无上限、无阶梯，`skill_upgrade` 表里的 100/300 完全没被读过。

**修复**：按 `Col1 = 当前等级` 查表取 `Col2`；查不到该行即已满级（新增错误码 `3206`）。

这同时补了一个**真缺口**：技能原本可以无限升级——没有满级概念，因为消耗公式里没有「上限」这个东西。

```go
// 修复后的判定（skill.go，意会）
row, ok := gamedata.GetSkillUpgradeCfg(int64(level))
if !ok {
	return errSkillMaxLevel // 3206：查不到该等级 = 已满级
}
cost := row.Col2 // 消耗以表为准：100 之后是 300 而不是 200
```

### 2.2 mail_template：模板表零引用

**旧实现**：邮件标题/正文直接用 Kafka 消息里的 `title/content`，模板表零引用——改文案必须改发送端代码、重新发版。

**修复**：「模板填默认值、消息非空则覆盖」：

```go
// 标题/正文优先用 mail_template 的配置，消息里非空则覆盖。
//
// 这样补偿邮件只需要下发「模板号 + 附件」，文案集中在配置表（运营可改）；
// 需要个性化（如「您反馈的问题已处理」）时仍可在消息里写死。
// 旧实现完全忽略模板表：改文案必须改发送端代码。
title, content := msg.Title, msg.Content
if cfg, ok := gamedata.GetMailTemplateCfg(int64(msg.TemplateID)); ok {
	if title == "" {
		title = cfg.Col1
	}
	if content == "" {
		content = cfg.Col2
	}
}
```

三个分支都有测试钉住：只给模板号（文案来自表）、消息写了就用消息的（个性化）、模板号查不到时**不能清空文案**（保留消息原值）。

### 2.3 shop：归属硬编码 1 号店

**旧实现**：`const defaultShopID = 1`，商品表第一列（`shop_id`）没被用——商品挂到别的商店，限购计数也记在 1 号店的键上，**限购会串**。

**修复**：按 `Col1` 取 shopID，并校验该商店存在：

```go
// shopExists 商店配置是否存在（shop 表是商品归属的权威）。
//
// 商品行第一列是 shop_id：归属到不存在的商店说明配置被改坏，
// 这种商品既不展示也不能买——否则玩家能绕过「商店下架」直接购买。
func shopExists(shopID int32) bool {
	_, ok := gamedata.GetShopCfg(int64(shopID))
	return ok
}
```

「删掉一个商店 = 它下面的商品全部下架」这个产品语义，是这次修复顺带确立的。

## 3. 测试手法：热更临时配置

后两条用例（商品挂 2 号店时计数键是 `"2:9"`、归属商店不存在时列表隐藏且购买被拒）用了一个巧妙手法——**`gamedata.Replace` 热更临时配置，测完恢复**：

```go
// 用例意会
gamedata.Replace(shopGoodsCfg, tempCfg)   // 临时把商品挂到 2 号店
defer gamedata.Replace(shopGoodsCfg, originCfg)
// …断言计数键是 "2:9"、归属商店不存在时不展示…
```

不需要改配置文件、不需要起容器，在单测里就能构造「配置被运营改坏了」的世界。这也是 gamedata 支持运行时热替换（[10-基础设施层/04](../10-基础设施层/04-游戏数据gamedata.md)）的额外收益。

## 4. 验证：三处变异

| 变异 | 期望 | 实际 |
| --- | --- | --- |
| 改回线性消耗（`Col3 * level`） | 满级拒绝/逐级查表用例失败 | 被抓 ✓ |
| 忽略 mail_template | 模板填充用例失败 | 被抓 ✓ |
| 计数硬编码 1 | 2 号店计数键用例失败 | 被抓 ✓ |

## 5. 经验沉淀

1. **「配置写了但代码没读」是一类bug，要有专门查法**。这次是逐个模块核对「表里的列是否都被引用」发现的；更系统的防法是给配置表加「引用守护」（谁声明这张表、哪些代码路径读它），见 [80-优化与展望/02](../80-优化与展望/02-后续优化清单.md)。
2. **修复漂移时顺手补真缺口**：skill 的修复顺带确立了满级概念——漂移的旧公式往往同时藏着「本该有的校验却没有」。
3. **坏配置要 fail 得可预期**：商店归属不存在 → 不展示也不能买，这是把「配置错了」翻译成确定的产品行为，而不是崩在中间。
