# 80-01 代码层优化扫描

> 这份文档记录一次「不动手、先扫描」的代码层优化评估：哪些值得做、每项的收益/风险/工作量，以及哪些**明确不做**。所有数字均为当前代码基线（`497e603`）实测。

## 1. 扫描方法

按四个维度过全仓：① 重复模式（同形态代码出现 ≥3 次）；② 命名与语义（标识符是否还匹配它的职责）；③ 封装边界（参数是否在爆炸、职责是否漂移）；④ 与历史的对照（`git log` 里做过的优化同类项是否还有漏网）。每条候选都过三道筛子：**收益可量化、风险可控、验证手段现成**——不过筛的不做。

## 2. 值得做：三项

### 2.1 合并 7 处相同的 `reply` 函数（净减约 40 行）

**现状**（实测）：7 个模块各有一份逐字相同的自由函数：

```text
internal/game/module/activity/activity.go:319   func reply(ctx *module.Context, msgID uint32, msg proto.Message) error
internal/game/module/copy/copy.go:204           同上
internal/game/module/equip/equip.go:272         同上
internal/game/module/partner/partner.go:302     同上
internal/game/module/quest/quest.go:289         同上
internal/game/module/shop/shop.go:229           同上
internal/game/module/skill/skill.go:204         同上
```

每份 7 行（marshal + `ctx.Send` + 错误包装），共 49 行。

**做法**：在 `module` 包加 `module.Reply(ctx, msgID, msg)`，7 处删除改调用。

**收益**：净减约 40 行；更重要的是**消灭一个 P0 隐患的复发面**——重复回包事故（[70-02](../70-开发过程实录/02-P0响应串号与幂等失效.md)）的写法温床之一就是各模块私有的 reply 包装，收拢到框架后，`convention_test.go` 的 AST 检查也能从「模式匹配私有名」升级为「认准一个入口」。

**风险**：低。纯函数搬迁，`go build` + 现有测试全覆盖。
**工作量**：半小时。
**注意**：通知类推送不走它（协议号不同、语义不同），只合并「回本请求响应」这一形态。

### 2.2 配置表列名语义化（36 张表、280 处引用）

**现状**（实测）：`configs/gamedata/xml` 下 36 张表，业务代码里 `Col1`~`Col5` 出现 **280 处**（`internal/` 16 个文件）。`skill.Col3` 到底是什么意思，只有打开 xml 对照才知道——这正是 [70-08](../70-开发过程实录/08-配置漂移修复.md) 三处漂移的认知根源：**读代码的人无法从代码看出「这列有没有被用上」**。

**做法**（两步，必须按序）：

1. **先出对照表给用户审**：`表名 × 列号 → 语义名 → 当前引用处`，一张 markdown 全量列清（这是用户明确要求的前置步骤，36 张表一次审完，避免改到一半发现语义理解错）；
2. 生成结构体字段改名：`cfg.Col3` → `cfg.Cost`（或 `CostDiamond`）。`tools/gendata` 的生成模板改一次，全表受益；调用点机械替换。

**收益**：可读性质变；漂移类 bug 的「发现成本」大幅下降（代码审查时 `Cost` 字段没用过是一眼可见的，`Col3` 不是）。
**风险**：中。280 处引用、生成模板改动，必须 `make gen` 后跑全量测试；语义名一旦取错（比如把「每日限购次数」命名成 `Limit` 实际是「每周」），比 `Col3` 更糟——所以第 1 步的人工评审不可跳过。
**工作量**：对照表 1~2 小时；替换 + 验证半天。

### 2.3 worldmap/spatial 引入 `Point`/`Rect`（消参数爆炸）

**现状**：`internal/worldmap/spatial` 与 scenemap 的格子计算里，坐标以 `(x, y int32)` 散传，「区域」以 `(x, y, w, h int32)` 四参传递——调用点 `inArea(px, py, ax, ay, aw, ah)` 这类形态可读性差且**参数顺序写反编译期不报错**。

**做法**：引入 `Point{X, Y}` / `Rect{X, Y, W, H}` 值类型 + 方法（`Contains`、`Overlap`、`Center`），把散参收窄为类型。scenemap 已有 `GridPos` 可作参照，保持同一风格。

**收益**：参数顺序错误从「静默算错」变成「编译不过」；距离/包含判断有单一实现。
**风险**：低~中。类型引入影响面局部，但 scenemap 与 worldmap 的坐标类型要对齐，先在一个包试点。
**工作量**：半天~1 天。

## 3. 明确不做：五项

| 项 | 为什么不做 |
| --- | --- |
| `codeOK`/`codeSuccess` 等常量合并 | 收益接近 0（常量合并不改变任何行为），却要碰所有模块的错误码定义——与 [70-09](../70-开发过程实录/09-错误码撞车与守护.md) 刚建立的白名单秩序冲突，风险不对称 |
| `Id`/`ID` 统一 | 280 处 Col 引用级别的机械改动，但不改变任何可观测行为；且 `model` 包字段名与 MySQL 列名有映射约定，大改要连带动 schema 注释与 seed。留作「下次大重构」事项 |
| `persist.go` 抽泛型基类 | 七个 `persist.go` 形态相似但 `toRow/fromRow/validate` 的语义各不相同（quest 整份 JSON、equip 分槽位、shop 计数 map），强行泛型会引入比样板更贵的间接层。当前「相似但独立」是正确的 |
| 长函数拆分 | 现有长函数（如 `mgr.run` 的 select 主循环）长而有注释、单一职责，拆开只会把「一屏看完的循环」变成五个跳来跳去的片段 |
| scenemap 9 处规格 TODO | 那些是「规格未到」的占位（时停延迟死亡、召唤超时、脱战恢复、buff 周期），不是技术债——按规格 [70-01](../70-开发过程实录/01-定时器测试flaky修复.md) 同源的纪律，没需求不写假实现 |

## 4. 优先级建议

```text
第 1 批（低风险高信号）  ：reply 合并（2.1）→ Point/Rect 试点（2.3）
第 2 批（需用户评审）    ：列名语义化（2.2，先出对照表）
第 3 批（持续）          ：文档与代码同步机制（见 80-02）
```

## 5. 小结

这一轮扫描的结论符合一贯的取向：**做「能降低未来 bug 发现成本」的优化（reply 收拢、列名语义化、坐标类型），不做「只让代码好看」的优化（命名统一、常量合并）**。三项待办都带验证手段（编译 + 全量测试 + 变异），随时可以启动。
