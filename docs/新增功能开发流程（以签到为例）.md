# 新增功能开发流程（以七日签到为例）

> **实现已简化**：签到现在是**周一到周日的单表签到**，状态只有已领取天数与奖励汇总，持久化由 `writebehind.RegisterFlat` 一行接入，模块只剩 `signin.go` 一个文件。当前实现与协议见[功能说明](signin.md)。
>
> 本文保留**从零实现一个完整功能**的教学路径（周期锚点、双表流水、手写 Repo/Persister、事务发奖）。这些是复杂玩法的通用手法，只是签到本身已经用不上——读到具体文件与表结构时，以 `signin.md` 和源码为准。

本章按**当前工作区已经接入的七日签到**，从需求重新走到协议、时间计算、表、模块、事务发奖、机器人和测试。简明规则见[功能说明](signin.md)。如果要练从零实现，请在独立练习工程分步重写，然后对照源码；不要在原项目再注册一组同名消息或重复占用 6601–6604。

## 1. 先把规则写清楚，再想文件

角色首次成功签到当天建立锚点；查询界面不开始周期。业务日期固定北京时间 UTC+8，每日零点切换。七个自然日为一轮，漏签不补、不延长，第八天回到新一轮第一天；离线几个周期仍按原锚点计算。

同一角色同一业务日只发一次；重复请求成功返回 already=true 和当时持久化的奖励快照。客户端不传角色、日期、档位或数量。奖励直接入背包，并且**签到事实与奖励后的背包数量在同一 MySQL 事务提交**。

示例：10 月 18 日首次成功，18 日第 1 档，19 日第 2 档；20 日没上线，21 日就是第 4 档，不能把漏签补成第 3 档；25 日新周期第 1 档。

先用纸写出这些反例，能避免把“连续登录七次”误实现为“七个自然日”。本章不会把现有邮件领取当作原子发奖能力，而是使用新增的 CommitItems。

CRUD 外还有三个批量函数，签名里的 `Querier` 同时接受 `*sql.DB` 与 `*sql.Tx`：

```go

DeleteXxxByPlayer(ctx, tx, playerID) error       // 整包替换（表有 player_id 时生成）
```

主键恰为 `(player_id)` 的表再加 `-- @flat:<模块名>`，生成 `XxxFlat`，模块侧
`writebehind.RegisterFlat` 一行接入持久化：校验、编解码、合批落库、冷启动全部由框架完成。
表名写错、列名写错、参数顺序错都会在编译期暴露，而不是等到线上报 SQL 错误。

先写状态编解码与纯函数的测试，再写业务编排。这样第一次遇到边界，不必同时排查 TCP 和 gRPC。

## 4. 用纯函数表示业务日


源码节选：[internal/game/module/signin/calendar.go](../internal/game/module/signin/calendar.go)。这是现有包中的片段，依赖同文件类型，不是可单独运行的完整程序。

```go
package signin

import "time"

// 使用固定 UTC+8，避免服务进程或容器的 Local 时区不同造成重复领取。
var businessZone = time.FixedZone("Asia/Shanghai", 8*60*60)

func businessDay(now time.Time) int64 { return (now.Unix() + 8*60*60) / 86400 }

func dayTime(day int64) time.Time { return time.Unix(day*86400-8*60*60, 0).In(businessZone) }

// cycleFor 按自然日推进，离线多个周期后仍保留原来的七日边界。
func cycleFor(anchor, today int64) (int64, int32) {
	if today < anchor {
		return anchor, 0
	} // 服务器时间回退时禁止提前领取。
	start := anchor + (today-anchor)/7*7
	return start, int32(today - start + 1)
}
```

逐句拆解：Unix 秒原点为 UTC，先加 8 小时再除以一天，得到北京时间自然日序号；它不是“距上次签到经过 24 小时”。dayTime 反向转换业务日开始时间，方便返回客户端倒计时。

`(today-anchor)/7*7` 找到已经完整经过的周期数；再加 anchor 保持长期锚点。`today-start+1` 得到 1–7 档。时间回退到锚点之前时返回 day=0，调用方拒绝提前领。

本项目刻意固定 UTC+8，不需要读取容器 Local 或系统 tzdata。这个除法写法适用于本项目现代正时间戳和固定时差，不能直接推广成支持所有历史日期与夏令时的通用日历算法。

New 可以注入 `func() time.Time`，测试不需要真的等待零点。教学测试矩阵：首次、第七日、第八日、漏签、离线 21 日、北京时间 23:59:59→00:00:00、服务器时间回退。

## 5. 先画表的不变量（教学版：锚点 + 流水）


本节及以下第 7–11 节保留**双表 + 手写 Repo/Persister** 的完整教学路径；当前签到已简化为单表
`player_signin`（`claimed_days` / `claimed_rewards` 两个 JSON 列），表结构以 `signin.md` 为准。

源码节选：[sql/schema/game.sql](../sql/schema/game.sql)（`player_signin` 表）。这里展示的是教学版双表设计，仓库中已不再包含 `signin_claim`。

```sql
-- 玩家七日签到锚点；epoch_day 是北京时间自然日对应的连续日序号。
CREATE TABLE `player_signin` (
  `player_id` BIGINT UNSIGNED NOT NULL,
  `anchor_day` BIGINT NOT NULL COMMENT '角色首个签到周期起点日序号',
  PRIMARY KEY (`player_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='角色签到周期锚点';

-- 奖励快照用于幂等重试，配置修改不会改变已领取事实。
CREATE TABLE `signin_claim` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `player_id` BIGINT UNSIGNED NOT NULL,
  `sign_day` BIGINT NOT NULL COMMENT '业务日序号',
  `cycle_start_day` BIGINT NOT NULL,
  `day_index` INT NOT NULL COMMENT '周期内第几天1-7',
  `rewards` TEXT NOT NULL COMMENT 'JSON实际奖励快照',
  `created_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_player_sign_day` (`player_id`, `sign_day`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='签到领取流水';
```

player_signin 每角色一行，保存首次成功日 anchor_day。signin_claim 是领取流水，唯一键 `(player_id, sign_day)` 约束同日一次，rewards 保存实际 JSON 奖励快照。

快照很重要：配置今天从 100 改成 200，重试昨天已提交的领取仍必须返回当时的 100，而不是按新表再算一次。只保存“已领=true”无法恢复原结果。

表存在不代表迁移执行过。新空数据库卷会初始化；已有库要先应用新增 DDL，再发布引用这两张表的代码。

## 7. Repo.Load 只查询，不开始周期


源码节选：[internal/game/module/signin/repo.go](../internal/game/module/signin/repo.go)。这是现有包中的片段，依赖同文件类型，不是可单独运行的完整程序。

```go
func (r *Repo) Load(ctx context.Context, playerID, today int64) (*view, error) {
	var anchor int64
	err := r.db.QueryRowContext(ctx, `SELECT anchor_day FROM player_signin WHERE player_id = ?`, playerID).Scan(&anchor)
	if errors.Is(err, sql.ErrNoRows) {
		return &view{Start: today, Day: 1, Claims: make(map[int64][]module.ItemGrant)}, nil
	}
	if err != nil {
		return nil, err
	}
	start, day := cycleFor(anchor, today)
	v := &view{Start: start, Day: day, Claims: make(map[int64][]module.ItemGrant)}
	rows, err := r.db.QueryContext(ctx, `SELECT sign_day, rewards FROM signin_claim WHERE player_id = ? AND sign_day >= ? AND sign_day < ?`, playerID, start, start+7)
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	for rows.Next() {
		var signDay int64
		var raw string
		if err := rows.Scan(&signDay, &raw); err != nil {
			return nil, err
		}
		rewards, err := decodeRewards(raw)
		if err != nil {
			return nil, err
		}
		v.Claims[signDay] = rewards
	}
	return v, rows.Err()
}
```

不存在锚点时构造“如果现在开始就是第一天”的视图，不 INSERT。这让“打开签到界面但没领取”不会偷偷消耗周期。

有锚点后只取当前周期 `[start,start+7)` 的记录，并解码持久化奖励快照。Rows.Close 与 rows.Err 都要处理，前者释放资源，后者传播迭代错误。

## 8. Repo.Claim 不自己提交事务


源码节选：[internal/game/module/signin/repo.go](../internal/game/module/signin/repo.go)。这是现有包中的片段，依赖同文件类型，不是可单独运行的完整程序。

```go
func (r *Repo) Claim(ctx context.Context, tx *sql.Tx, playerID, today, expectedStart int64, expectedDay int32, grants []module.ItemGrant) ([]module.ItemGrant, error) {
	if _, err := tx.ExecContext(ctx, `INSERT INTO player_signin (player_id, anchor_day) VALUES (?, ?) ON DUPLICATE KEY UPDATE player_id = VALUES(player_id)`, playerID, today); err != nil {
		return nil, err
	}
	var anchor int64
	if err := tx.QueryRowContext(ctx, `SELECT anchor_day FROM player_signin WHERE player_id = ? FOR UPDATE`, playerID).Scan(&anchor); err != nil {
		return nil, err
	}
	start, day := cycleFor(anchor, today)
	if day == 0 || start != expectedStart || day != expectedDay {
		return nil, errCycleChanged
	}
	var raw string
	err := tx.QueryRowContext(ctx, `SELECT rewards FROM signin_claim WHERE player_id = ? AND sign_day = ? FOR UPDATE`, playerID, today).Scan(&raw)
	if err == nil {
		stored, err := decodeRewards(raw)
		if err != nil {
			return nil, err
		}
		return stored, errAlready
	}
	if !errors.Is(err, sql.ErrNoRows) {
		return nil, err
	}
	snapshot := make([]snapshotReward, 0, len(grants))
	for _, g := range grants {
		snapshot = append(snapshot, snapshotReward{ItemID: g.ItemID, Count: g.Count})
	}
	encoded, err := json.Marshal(snapshot)
	if err != nil {
		return nil, err
	}
	_, err = tx.ExecContext(ctx, `INSERT INTO signin_claim (player_id, sign_day, cycle_start_day, day_index, rewards) VALUES (?, ?, ?, ?, ?)`, playerID, today, start, day, string(encoded))
	return grants, err
}
```

这是给调用方已有 tx 的方法。顺序是插入/复用锚点行 → 锁锚点 → 重算周期并对比预期 → 查当天唯一事实 → 保存奖励快照。tx 的开始、背包写入与 Commit 由 CommitItems 管理。

重算防止“先查视图、后事务”之间周期基础发生变化；重复时返回 stored 与 errAlready，让外层回滚本次发奖事务，再回复历史成功结果。**errAlready 是流程分支，不是客户端失败。**

所有 SQL 都使用传入 tx；中途用 r.db.ExecContext 会跳出共同事务。只有本次新增事实与背包都准备好才允许 Commit。

## 9. 通过能力接口把业务事务放进 Actor

Context 新增的能力相当于：

```go
// 接口形状，真实定义在 internal/game/module/module.go。
CommitItems func(
    context.Context,
    []module.ItemGrant,
    func(*sql.Tx) error, // 业务事实必须全部使用这个 tx。
) error
```

模块决定奖励与业务事实，但不拿 Player.State 的私有 map。Actor 注入的实现先保存既有变化，再调用 Repository.CommitItems；前置保存防止之后重载数据库时抹掉先前尚未提交的普通背包变化。


源码节选：[internal/game/player/grant.go](../internal/game/player/grant.go)。这是现有包中的片段，依赖同文件类型，不是可单独运行的完整程序。

```go
func (r *Repository) CommitItems(ctx context.Context, state *State, grants []module.ItemGrant, business func(*sql.Tx) error) error {
	dirty := state.DirtyItems()
	counts := make(map[int32]int64)
	for _, grant := range grants {
		current, ok := counts[grant.ItemID]
		if !ok {
			current = state.GetItemCount(grant.ItemID)
		}
		if grant.ItemID <= 0 || grant.Count <= 0 || current < 0 || grant.Count > math.MaxInt32-current {
			return fmt.Errorf("invalid item grant: item=%d count=%d", grant.ItemID, grant.Count)
		}
		counts[grant.ItemID] = current + grant.Count
		dirty[grant.ItemID] = counts[grant.ItemID]
	}
	tx, err := r.db.BeginTx(ctx, nil)
	if err != nil {
		return err
	}
	defer tx.Rollback()
	var id int64
	if err := tx.QueryRowContext(ctx, `SELECT id FROM player WHERE id = ? FOR UPDATE`, state.PlayerID()).Scan(&id); err != nil {
		return err
	}
	if err := business(tx); err != nil {
		return err
	}
	if err := saveDirtyItems(ctx, tx, state.PlayerID(), dirty); err != nil {
		return err
	}
	if err := tx.Commit(); err != nil {
		return fmt.Errorf("%w: %v", ErrCommitUnknown, err)
	}
	for id, count := range counts {
		state.SeedItem(id, count)
	}
	state.ClearItemsDirty()
	return nil
}
```

逐段理解：先在局部 counts 中计算奖励后数量，不改在线 State；BeginTx 后锁 player 主行，把角色级事务序列化；执行 business(tx) 写签到事实；saveDirtyItems 用同一 tx 保存背包；Commit 成功后才 SeedItem 同步内存并清已提交标记。

这里的“同一玩家 Actor”是前提。它防止旧 Write-Behind SaveMsg 在发奖事务中途执行；player 行锁对遵守同一约定的事务提供数据库级顺序。该方案没有实现同一角色由多个 Game 同时权威写入时的资产合并。

## 10. Commit 错误不能直接当回滚

网络断开可能让应用不知道提交结果。代码包装 ErrCommitUnknown，Actor 标记 needsReload，暂停用旧背包保存；下一条需要处理的业务前用相同 player 行锁等待旧事务结束，再从数据库重载背包。

阅读：[ReloadItems](../internal/game/player/grant.go)、[Actor.Receive](../internal/game/player/actor.go)。它只替换背包，不清掉装备派生属性或其他在线模块状态。无法重载时不继续处理可能扩大不一致的操作。

这比“重试整次发奖并重新生成业务 ID”更重要：同一天重试查持久化领取记录，若原来已提交就返回原奖励；没提交才重新执行。最终事实使未知结果收敛。

练习时画四个故障点：事务前、写事实后未提交、提交成功但响应丢失、Commit 返回未知结果。逐个解释内存能否修改、下一次重试读到什么。

## 11. Module 把所有步骤串起来


源码节选：[internal/game/module/signin/signin.go](../internal/game/module/signin/signin.go)。这是现有包中的片段，依赖同文件类型，不是可单独运行的完整程序。

```go
func (m *Module) OnMessage(ctx *module.Context, msgID uint32, body []byte) error {
	var req proto.Message
	switch msgID {
	case MsgInfoReq:
		req = &gamev1.SigninInfoReq{}
	case MsgClaimReq:
		req = &gamev1.SigninClaimReq{}
	default:
		return fmt.Errorf("signin: unexpected message %d", msgID)
	}
	if err := proto.Unmarshal(body, req); err != nil {
		return m.failure(ctx, msgID, err)
	}
	if m.repo == nil {
		return m.failure(ctx, msgID, fmt.Errorf("signin repository unavailable"))
	}
	dbctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	today := businessDay(m.now()) // 每个请求只采样一次，防止处理途中跨零点。
	v, err := m.repo.Load(dbctx, ctx.State.PlayerID(), today)
	if err != nil {
		return m.failure(ctx, msgID, err)
	}
	if msgID == MsgInfoReq {
		return reply(ctx, MsgInfoResp, &gamev1.SigninInfoResp{State: render(v, today)})
	}
	if stored, exists := v.Claims[today]; exists {
		return reply(ctx, MsgClaimResp, &gamev1.SigninClaimResp{Already: true, Rewards: protoRewards(stored), State: render(v, today)})
	}
	if v.Day < 1 || v.Day > 7 {
		return m.failure(ctx, msgID, fmt.Errorf("server business date precedes signin anchor"))
	}
	grants, err := rewardsForDay(v.Day, gamedata.SigninRewardCfgList)
	if err != nil {
		return reply(ctx, MsgClaimResp, &gamev1.SigninClaimResp{Code: codeConfig, State: render(v, today)})
	}
	for _, g := range grants {
		if ctx.State.GetItemCount(g.ItemID) < 0 || g.Count > math.MaxInt32-ctx.State.GetItemCount(g.ItemID) {
			return reply(ctx, MsgClaimResp, &gamev1.SigninClaimResp{Code: codeBagLimit, State: render(v, today)})
		}
	}
	if ctx.CommitItems == nil {
		return m.failure(ctx, msgID, fmt.Errorf("atomic item persistence unavailable"))
	}
	var stored []module.ItemGrant
	err = ctx.CommitItems(dbctx, grants, func(tx *sql.Tx) error {
		var err error
		stored, err = m.repo.Claim(dbctx, tx, ctx.State.PlayerID(), today, v.Start, v.Day, grants)
		return err
	})
	already := errors.Is(err, errAlready)
	if err != nil && !already {
		return m.failure(ctx, msgID, err)
	}
	if already {
		grants = stored
	}
	v.Claims[today] = grants
	if err := reply(ctx, MsgClaimResp, &gamev1.SigninClaimResp{Already: already, Rewards: protoRewards(grants), State: render(v, today)}); err != nil {
		return err
	}
	if !already {
		changes := make([]*gamev1.ItemChange, 0, len(grants))
		for _, g := range grants {
			changes = append(changes, &gamev1.ItemChange{ItemUid: int64(g.ItemID), ItemId: g.ItemID, Count: int32(ctx.State.GetItemCount(g.ItemID)), Change: 1})
		}
		return reply(ctx, 3010, &gamev1.BagChangeNotify{Changes: changes})
	}
	return nil
}
```

按顺序读：解析空请求 → 建 DB 超时 → 每请求只取一次 today → Load 视图 → 查询直接回复 → 已领取直接返回快照 → 校验 day、配置与背包上限 → CommitItems 内调用 Repo.Claim → 处理 errAlready → 返回领取结果 → 新发奖才推 3010。

源码用 context.Background 再加 5 秒预算，不直接传播 Actor 运行 context。这是当前生命周期选择，不是所有功能都必须照抄；练习时要说明停服中这 5 秒由谁等待。

Module.Init 有配置校验，但还要检查 Server 是否调用 Registry.InitAll；“写了 Init”不等于启动期一定校验。请求路径也校验奖励，因此不要只依赖一个未必调用的生命周期钩子。

## 12. 注册、机器人与验证

当前 Game.Start 在数据库分支注册 `signin.New(signin.NewRepo(s.database), s.logger)`。MsgIDs 只注册 6601、6603 请求；响应由 Reply 发出，不再次路由到模块。

机器人已新增 SigninInfo/SigninClaim 方法，复用登录、握手、封包与加密。新协议不需要网关写一条“签到专属转发规则”，但仍要有模块注册与合法会话。

```bash

go test ./internal/game/module/signin ./internal/game/player
```

测试至少检查：首次查看不建锚点；同日重复不加物品；不同角色隔离；UTC+8 零点切换；漏签档位正确；第八天循环；离线跨周期；一日多种奖励；写入失败回滚；成功后重载仍幂等；配置变化后返回原快照。

## 13. 从这个功能提炼通用开发流程

需求不变量 → 空请求与可信身份 → 确定业务日期/幂等键 → 静态表 → 表约束 → 纯逻辑测试 → Repo 事务片段 → Actor 原子能力 → Module 编排 → 注册 → 机器人 → 迁移与故障回归。

独立练习：做“同一角色每天最多兑换一次”的新功能，不复用签到协议号。先写兑换事实与消耗/奖励同事务的设计，回答提交未知如何恢复，再写代码。通过标准不是接口能回 0，而是重复、超时、配置变化和重启后都能解释结果。

## 14. 持久化方式怎么选（FlatPersister 一期落地后）

写代码前先做一次判定，只看「状态形状」，不看玩法复杂度：

```text
状态需要落库？
├─ 否（纯内存 / 配置驱动）→ 什么都不写
├─ 一张玩家级单行状态表，字段直映、无派生列
│   → 建表注释加 -- @flat:<模块名>（PK 必须恰为 player_id）
│   → 模块包建 bind.go：writebehind.RegisterFlat("<模块名>", model.XxxFlat)
├─ 有界小集合、可整包替换（二期支持，当前仍手写）
│   → 手写 Persister
└─ 其余（多表 / 派生列 / 无界集合 / 差异删除 / 代理 id）
    → 手写 Persister（签到即参照实现）

所有模块：Ext 读写一律用 writebehind.LoadExt / SaveExt，不再自定义窄接口。
```

几条硬约束：

1. `@flat` 标在主键不是 `(player_id)` 的表上，gendb 直接报错退出——不允许生成编译不过的适配。
2. Flat 的 JSON 槽位格式就是生成结构体；日后迁移到手写 Persister 时，自定义 Data 的 json tag 必须与列名一致，旧快照才能直接读。
3. 持久化注册代码只放在模块包的 `bind.go`，`grep -r RegisterFlat internal/` 可一次列出全部 Flat 模块。
4. 从 Flat 切手写：删 bind.go、补 persist.go，无数据迁移、无停机。
